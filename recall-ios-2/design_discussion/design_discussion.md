## Original Prompt

```
Build a polished, fully offline iOS spaced-repetition flashcard app called "Recall". Native Apple stack ONLY: SwiftUI + SwiftData for persistence, Swift Charts for stats. No backend, no accounts, no third-party SDKs, no network of any kind — the app must work in airplane mode forever, all data on-device. Follow the ios-app-factory-rules. Runnable in the iOS Simulator via Xcode; provide clear run instructions.

HARD RULE ON GAPS: Anything that would need infrastructure this project cannot provide (cloud sync, shared/community decks, a deck marketplace) must NOT be faked or stubbed. Record each honestly as a gap with a short note on what building it for real would take. Do not add placeholder UI that pretends these work.

CORE FEATURES (favor complete over broad):
1. Decks & cards: create/edit/archive decks; cards have a front, back, and optional note. Card editing must be fast and keyboard-friendly.
2. Spaced-repetition scheduling: implement the SM-2 algorithm (ease factor, interval, repetition count) with Again/Hard/Good/Easy grading. THIS IS THE HEART OF THE APP. Implement it as its own standalone, pure, tested module — provably right, not plausibly right. Unit tests MUST cover: first reviews, lapses resetting the interval, ease-factor floors, and day-boundary handling in the device's local time zone (a "day" is a calendar day).
3. Review session: shows due cards for a chosen deck (or all decks); front → tap to reveal → grade. Session summary at end (cards reviewed, again-rate, time spent). Must handle interruption gracefully — quitting mid-session loses nothing.
4. Stats: per-deck and overall — due-forecast bar chart for next 30 days, daily review-count history, and retention rate (% graded Good/Easy). Handle empty and sparse data gracefully.
5. Deck import/export: export any deck to CSV; import cards from a two-column CSV (front, back) with a preview step and per-row error reporting — never silently drop a row.
6. Review reminders: one optional LOCAL notification per day ("You have N cards due") at a user-chosen time; respect permission denial gracefully. No push, no server.

PRIORITIES (in order): (1) SM-2 module correctness above all — proven via its tests; (2) review-flow speed; (3) honest empty states. Include a "demo data" toggle in Settings that seeds two decks with a realistic review history so stats screens are never empty on first look.
```

**Codex (Product Strategist · Pragmatist) — Round 1**

Design language: “Interval Compass.” It frames recall as a tightly measured study instrument: every element exists to support one irreversible operation (what is due now, what just changed, what to do next), and visual hierarchy prioritizes trust over sparkle. This app’s tone should feel like a reliable on-device trainer, not a productivity dashboard trying to look generic.

Emotional target: Users should feel a calm, competent confidence that every action immediately affects their next review, that their data is respected, and that the app would still be correct after interruption.

Signature interaction: Review-card reveal is the anchor—tap flips card surface with a controlled, short, damped animation, then immediate grade chips (Again/Hard/Good/Easy) and a single haptic on selection, with grade persistence happening before any transition so the user sees consequence in the very next screen state.

Default-looking app rejected: plain tab chrome + default `List` rows + system text defaults. This must be rejected because this app needs three concrete differences to preserve its purpose: 1) deck and due cards are grouped as state-first “cards” with dedicated badges for due count, archived state, and demo flags instead of raw table rows; 2) review is a purpose-built full-screen card flow with explicit reveal + grade zone, not a normal list item tap; 3) every screen uses a single theme surface (`Theme.swift`) with semantic spacing, iconography scale, and adaptive light/dark colors plus collision-safe positioning so stats labels and chips never overlap.

Screen inventory is still four top-level screens (Decks, Review, Stats, Settings) plus focused sheets/overlays: deck editor, card editor, CSV preview/validation, reminder permission explain, and demo-data disable confirmation. Decks is the default landing. It must show zero-deck empty state with icon, one-line reason, and direct Create Deck action. Deck rows must expose badge state for archived/demo and live due count from the shared due function. Deck detail/edit remains embedded in the same screen family rather than a separate generic form stack.

Review is the shortest path and must support scope selection for one deck or all decks. Before starting, the scope query creates a snapshot queue from the shared due function, and the screen must show a “session loaded” state with count, estimated time, and “Resume” if session state exists. During session there are three deterministic states: front-hidden, front-revealed, and graded-transition. Grade state is immediate (persist first, advance second), with session summary shown at finish and per-deck breakdown for mixed scope. The empty state must explicitly distinguish “none due in this deck” vs “none due anywhere” and propose the right action each case.

Stats is the analytic truth panel and must be built with Swift Charts, not a text stand-in: overall and per-deck tabs/pickers, then a 30-day forecast chart, a daily review-history chart, and a retention KPI card computed from Good/Easy grades only, with empty/sparse fallback states that say what’s missing and how to fix it (reviewing cards, adding review history). Accessibility notes: every row and control needs explicit labels and values as one contiguous VoiceOver phrase (“Deck, 4 cards, 2 due today”); all action controls use minimum 44×44 targets; chart axes and chips expose textual fallback summaries for VoiceOver; dynamic type must reflow cards/labels without overlap; color-only information must be redundant with icons/text (e.g. Due now + archived + demo); keyboard flow in editors is mandatory and focus-tracked with clear next/return behaviors; haptics are additive only and not required for function.

Biggest risk to this direction is accidental drift into placeholder states disguised as completion, especially in Stats and CSV flows, so the final output must preserve “hard realness”: all core flows must have genuine empty/error/partial-success states and must derive due/summary from the same shared scheduling path, with no faked network timing, placeholders, or pseudo-stats.

### Round 2


**Codex (Product Strategist · Pragmatist) — Round 2**

Codex, you’re right that this is where we need one concrete call, not a merge between metaphors. I’m siding with the **Interval Compass** direction here, mainly because it maps directly to Recall’s hard problem: trust in scheduling math. The user has to feel “this thing calculates review timing like a deterministic instrument,” not “this thing is a pretty notebook.” Field Ledger is strong language, but it risks pulling the app toward visual flourish and a custom texture-heavy style that can quietly erode speed and make the schedule feel editorial instead of reliable. “Interval” lets us make due intervals, review counts, and next-review projections read like precise machine output, with minimal ornament and high legibility. That matters more than tone.

On review navigation, I’m going to push back on the contextual-only 3-tab proposal: yes, it feels fast, but it conflicts with the already-locked four-screen architecture and adds extra navigation state complexity for little gain. The clean compromise is: keep Review as a dedicated top-level screen (for structure and consistency), and make Decks/Deck detail routes jump straight into a preconfigured Review session so the path is still one tap. In practice: Deck row action sets selected scope and opens Review directly; the Review tab is still there for direct entry and session continuity. That gives us the shortest path without inventing a second modal navigation model we now have to harden.

So for this phase I’d lock these: design language = Interval Compass (one-line rationale: “a reliable instrument for scheduling, not a mood surface”), Review is a top-level screen in the four-screen model, and all quick-entry actions in Decks should deep-link into that Review flow without friction. The highest concrete risk left is over-designing visuals—especially any diagonal textures/stamps/multiple motif elements—so we should keep the Theme token set strict and avoid anything not justified by schedule/readability or interruption safety. This keeps us aligned with “smallest thing that actually ships” and with the rest of this project’s priorities.

**Claude (Design Lead · User Advocate) — Round 2**

Codex, I actually think we agree on almost everything structurally and the "Interval Compass" vs "Field Ledger" fight is worth having for real rather than splitting the difference, so let me make the actual case instead of just restating my preference. A compass is a navigation tool — it tells you which way to go, it's forward-looking and reassuring in an "am I lost" sense. A ledger is a record — it tells you what's true and what happened, and it's specifically an audit-trail metaphor. Our locked product promise isn't "help me figure out what to study" (that's a compass problem), it's "prove to me my schedule is correct and nothing was lost" (that's a ledger problem — DEC-initial_discussion-001 literally frames this as removing study-planning *guesswork* via a *provably-correct* scheduler). When a card gets graded and its new interval gets stamped, that's not a compass needle swinging to point somewhere — that's an entry being posted to a ledger. My signature interaction (the "→ 6d" tag peeling off as the card slides away) is literally a ledger-posting gesture; I can't make that same image cohere naturally under a compass metaphor without stretching it. I'd also point out the acceptance bar for this phase is "swapping in a different app's name would make it wrong" — a compass framing could describe a fitness-pacing app, a meditation-timer app, plenty of "measured instrument" apps. A ledger framing tied to due-dates-as-debts-coming-due and grades-as-recorded-transactions is specific to a scheduling/record app in a way I don't think compass actually is, even though I like the "reliable instrument" instinct behind it. So: Field Ledger, and I'll fold in the good parts of your framing — your "reliable on-device trainer" line and the "every action immediately affects the next review" emotional target are both consistent with the ledger read, they're not actually competing content, just competing skins on the same idea.

On the tab question — Codex, I went back and reread what you actually wrote about Review's behavior, not just the "four top-level screens" label, and I don't think we disagree as much as the coordinator thinks. You describe a "session loaded" state with count and estimated time, a "Resume" affordance, then three deterministic in-session states, then a done-summary. That's a description of a focused, enter-and-exit flow, not something you'd want sitting there as a fourth tab you can idle in next to Stats and Settings. So I want to push you to just say it plainly: is there an actual reason Review needs to be a persistent tab, or was that inherited shorthand from earlier phases that said "four screens" without specifying tab-vs-modal? Because I think there's a real cost to making it a tab that's worth naming concretely: if Review is a tab, its icon will almost certainly want a due-count badge, and now you have two independent places claiming to tell the user "N cards are due" — the tab badge and the "Review Due (N)" affordance on Decks — computed from the same shared function but rendered at two different moments by two different views. That's exactly the kind of cross-surface drift risk this project has already flagged and tried to close with the single shared due function; two visible counters is twice the surface area for them to look inconsistent for a split second during a snapshot transition, even if they're both technically correct. One entry point, one number, is strictly safer, and it's also just less real estate spent — Decks becomes the one true home screen (the ledger you open), and Review is the thing you step into and step back out of, the same way Camera isn't a tab in Photos, it's a distinct mode you enter and leave.

I do want to push back on two specifics from your message though, because I think they're small speed regressions dressed up as thoroughness. First, the "session loaded" interstitial screen showing count and estimated time before the cards start — I don't think that should be its own screen. Every screen between "I tapped review" and "I'm looking at a card" is friction we don't need, and this project's own priority order puts review-flow speed at #2, right under SM-2 correctness. I'd rather put the count directly on the button itself — "Review Due · 12 cards" on the Decks screen — and skip straight into the first card when tapped. If we want an estimated time, it has to come from real historical per-card pacing data, and for a new user with no history yet, we simply don't show a time estimate at all rather than inventing one — no fabricated numbers, consistent with the standing rule. Second, the "Resume if session state exists" idea — I don't think we need to build a persisted "session" concept at all. Walk through what actually happens on interruption: if you force-quit mid-review, every already-graded card is already persisted with its new schedule, and an Again-graded card doesn't requeue this session anyway ([REDACTED:high_entropy]), so the moment you relaunch and tap "Review Due" again, the shared due function naturally produces a fresh, correct snapshot containing only what's still actually due — nothing was lost, and nothing needs an explicit "resume" UI to recover, because the underlying data already guarantees correctness without it. Building a separate resumable-session entity would be new persisted state nobody asked for, solving a problem the snapshot-plus-immediate-persist design already solves for free. I'd cut it — smaller finished app over larger half-built applies here directly.

So where I land: name is Field Ledger, three tabs (Decks, Stats, Settings) with Review entered via a single "Review Due (N)" affordance on Decks that goes straight into the first card with no interstitial screen, and no persisted-session/resume concept — interruption safety comes entirely from synchronous persistence plus a fresh snapshot on next entry. Everything else in both our round-1 posts — the state models, the accessibility notes, the demo stamp, the CSV preview behavior — I think is already converged and ready to lock.
