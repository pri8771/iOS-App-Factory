**Codex (Product Strategist · Visionary) — Round 2**

I’m glad both of you pushed this this far — the hard part now is not features, it’s locking behavior so it can’t drift.

On the session question, I want to hard-line this as a requirement: due-ness is always derived from the shared `due` function, but once a review session starts, the queue is a snapshot. We can still obey DEC-initial_discussion-004 because deck badges, scope selectors, and review pre-entry all query live from the same shared function at the moment of display; we just don’t keep requerying mid-session while the user is in flow. If timezone or clock shifts while they’re reviewing, it won’t pop cards out from under them or inject new cards unpredictably. That is exactly the behavior that makes interruption-safe sessions feel trustworthy.

I’ll lock the SM-2 formula now instead of letting anyone infer it later. This is non-negotiable and will be documented in code comments plus tests:

- Again: `interval = 1`, `repetitions = 0`, `ease = max(1.3, ease - 0.20)`
- Hard: `repetitions += 1`, `ease = max(1.3, ease - 0.15)`, interval progression: if `repetitions` is 1 => 1, if 2 => 6, else `round(prevInterval * ease * 0.8)`
- Good: `repetitions += 1`, `ease = ease`, interval progression: if 1 => 1, if 2 => 6, else `round(prevInterval * ease)`
- Easy: `repetitions += 1`, `ease = ease + 0.15`, interval progression: if 1 => 1, if 2 => 6, else `round(prevInterval * ease * 1.3)`

That gives an explicit, deterministic, auditable schedule and gives us the ease-floor test in a way you can prove (`max(1.3, ...)`). It’s an adaptation of the canonical SM-2/4-choice mapping where interval growth is driven by EF and grade-specific multipliers, and the “Again means back to learning” behavior is explicit.

Then the in-session behavior must be explicit too: Again does not requeue in the current session. It is a card-lift to tomorrow (or earliest next local calendar day based on shared due logic), and removed from the active queue. This is scope-safe for this build and avoids inventing a second algorithmic branch for “learn/relearn steps” that the prompt didn’t authorize. The session summary still shows it as Again and we keep the integrity guarantee.

For CSV, we should not cheat with “works for most files.” Import is strictly two columns: front, back. We parse RFC4180-compliant CSV (quoted commas/newlines/quotes), and every row gets an outcome in preview: `INSERT`, `DUPLICATE`, or malformed reason. Rows with exactly two populated columns and no parse error can be inserted; malformed rows (missing field, malformed quoting, extra columns when not parseable, malformed UTF-8) are surfaced individually with line numbers; duplicates are deterministic by normalized front+back equality within target deck and are rejected in strict mode with explicit row errors. No “quietly skip.”

On that note, CSV export in this phase stays two-column only: front/back only. No note export, no hidden third column, because that keeps contract and round-trip honest. If notes exist, they are intentionally out-of-scope for CSV transport and must be clearly called out as such in the CSV feature copy/help.

Reminder text: I want a safe, honest implementation over a brittle “live count” promise. Local notifications cannot safely guarantee a live N at fire time without background execution guarantees we don’t have. So notification body should avoid pretending precision it can’t maintain. “You have cards due for review.” is explicit and truthful. If we still want a number in-app, we can show it there from current shared due count; for notification scheduling we do not claim precision we cannot guarantee. This preserves the no-lie contract.

Demo data should never poison aggregate user metrics. When demo mode is on, demo decks/cards stay visible with explicit badging and remain excluded from real-user aggregate retention and “overall” due summaries unless the user explicitly opts into a “show demo metrics” path. That means retention and retention trend are trustworthy by default.

Archive/delete: archive means hidden from default active review scope only; archived decks remain editable, exportable, and recoverable. Deletion is a separate destructive action with explicit confirmation and irreversibility warning. No “no delete ever” trap for power users.

I’d call these the final hard decisions for this phase so we can move with zero ambiguity and no “we decided in build.”

### Round 3


**Codex (Product Strategist · Visionary) — Round 3**

Codex, I’m aligned with your direction on session snapshotting and the 2-column CSV contract; those are the right trust moves. On the two unresolved items, I want to close them hard now.

For Hard: let’s choose the fixed `prevInterval * 1.2` multiplier. I’m not doing this because I think it’s arbitrary; I think it’s the cleanest, least-surprising interpretation of the 4-grade “Hard” step in a pure SM-2 family implementation. You get one simple rule for retention slowdown, you keep EF as the long-term memory-quality knob (with the already-locked floor), and you avoid a hidden coupling where Hard becomes “good * almost* EF,” which is much less transparent to users and harder to reason about in tests. If EF is already low, using `*1.2` gives stable, bounded behavior under repeated misses. If EF is high, cards can still recover through Good/Easy. This is far easier to document in-app (“Hard reduces growth a little; Easy boosts it”) and to verify in unit tests. I’d reject the `*ease*0.8` variant to avoid ambiguity and to keep the algorithm behavior easy to explain and trust.

On duplicates: I think we should explicitly reject duplicates as import errors, not merge or silently skip. The rule should be “DUPLICATE row is not imported,” and the preview must show that exact outcome per row with line numbers so the user knows precisely why. That preserves the “never silently drop” promise and prevents accidental bloat of review queues from noisy imports. Matching should be scoped to the target deck and deterministic: normalize by trimming surrounding whitespace/newlines and Unicode normalization (so copy/paste noise doesn’t defeat detection), then compare front+back case-sensitively. If someone wants case-insensitive semantics, that’s a separate explicit preference surface we should not introduce in this phase. Allow partial import (non-duplicate + valid rows still commit) if the user confirms; just never treat a duplicate as implicitly added. This gives us trust, auditability, and a clean first-pass guarantee: every duplicate action is user-visible and intentional.

**Claude (QA & Risk · Skeptic) — Round 3**

Let me take the Hard-grade fight first because I think it's actually resolvable on the merits, not just a coin flip. Codex's formula — `prevInterval × ease × 0.8` — has a real pathology I want to walk through with actual numbers: take a mature card with ease 2.8 (which is completely normal after a run of Easy grades) and a 20-day interval. Under Codex's formula, Hard produces `20 × 2.8 × 0.8 = 44.8` days — Hard would push the card out further than Good would on a lower-ease card, and in fact as ease climbs, Hard's multiplier (`ease × 0.8`) approaches and can exceed 2.0, meaning "I found this hard" results in the interval nearly doubling. That's backwards. The entire point of a Hard grade is "I got it, but barely" — it should always produce meaningfully less growth than Good, for every ease value, not just typically. A fixed `× 1.2` multiplier, independent of ease, guarantees that invariant unconditionally: Hard always grows slower than Good (since Good is `× ease`, and ease is floored at 1.3, so even at the floor, Good's 1.3× already exceeds Hard's fixed 1.2×, and the gap only widens as ease rises). I'd also point out this isn't me inventing a competing formula — a fixed hard-multiplier around 1.2, decoupled from ease, is literally how Anki's actual shipped algorithm handles Hard, which is the one real-world four-button SM-2 derivative anyone can point to and say "this has been tested at scale." Codex, your version is a genuine invention with an unbounded-growth edge case in it; mine is boring and copies the one existing implementation that's been checked by millions of reviews. I'll go further: this is exactly the kind of thing our own unit-test mandate should catch, so I want a specific test case added to the record — grade a card Hard at ease 2.8 with interval 20, assert the result is meaningfully less than what Good would have produced from the same state — precisely so this pathology can never sneak back in during implementation.

On CSV duplicates, though, I want to actually update my position instead of just restating it, because rereading DEC-prompt_contract-005's own constraint — "post-import count must reconcile exactly with preview minus flagged errors" — that phrasing only makes sense if flagged rows (including duplicates) are excluded from the insert count. If duplicates get flagged in preview but still inserted, as I argued last round, then the math "preview minus flagged errors" doesn't reconcile with what actually landed in the deck — you'd have imported more rows than "preview minus flagged" predicts. So Codex is right and I was wrong: duplicates need to be skipped, not imported alongside a flag. But I want to sharpen the framing on "reject" — it shouldn't read as "the whole import fails," it should be a per-row skip with an explicit, visible reason ("DUPLICATE — already exists in this deck, not imported"), while every other clean row in the same file still commits. That keeps faith with "never silently drop a row" — the row isn't dropped silently, it's dropped loudly and individually — while also solving a real practical problem neither of us named yet: if we imported duplicates anyway, then accidentally tapping import twice on the same file, or re-importing a CSV you'd already brought in last month, would silently double every card in the deck. Skipping duplicates makes CSV import idempotent by construction, which is a property worth having for free.

Where I'll push back on Codex's proposed matching rule is "normalized" — that word is doing a lot of unstated work. Normalized how? If it means case-insensitive, then a German-vocab deck with "der Tisch" and "Der Tisch" (legitimately different capitalization contexts in real usage) would get silently treated as duplicates and one would vanish from the import — which is itself a silent, unwanted drop, just laundered through the word "duplicate" instead of "error." I'd rather trim leading/trailing whitespace only (catching the extremely common CSV noise case of trailing spaces or a stray tab) and keep the actual front/back comparison case-sensitive and otherwise exact. That's a narrower, safer definition of "duplicate" that only catches things a reasonable person would agree are actually the same card, and doesn't risk quietly discarding content a user typed on purpose. If Codex wants broader fuzzy matching later, that's a real feature with its own edge cases (accents, punctuation, Unicode normalization forms) that deserves its own scoped discussion, not smuggled in as "normalized" in a duplicate-detection one-liner.

So here's where I think this closes out: Hard uses a fixed `prevInterval × 1.2` multiplier, independent of ease, for the concrete unbounded-growth reason above; duplicates are skipped per-row with an explicit visible reason (not imported), keeping the whole-file import behavior idempotent and consistent with the existing "preview minus flagged" reconciliation rule; and duplicate matching is whitespace-trimmed but otherwise case-sensitive exact match, not a broader normalization that risks discarding legitimately distinct cards. I don't see a live disagreement left after this — if Codex agrees on the fixed multiplier given the ease-scaling pathology, and I've conceded the reject-not-import point on duplicates, both open items are actually settled on substance rather than by a coordinator picking a side.

Again resets repetitions to 0, interval to 1 day, ease -= 0.20 (floor 1.3). Hard: ease -= 0.15 (floor 1.3), interval = `round(prevInterval × 1.2)` — a fixed multiplier, decoupled from ease, guaranteeing Hard always grows slower than Good. Good: ease unchanged, interval = `round(prevInterval × ease)`. Easy: ease += 0.15, interval = `round(prevInterval × ease × 1.3)`.
- Due-ness is always live via one shared function outside of an active session (deck badges, scope selectors, any in-app count); an active review session snapshots its due-card queue once at scope-selection time and never re-queries mid-session.
- Again never requeues within the same session — the card just leaves the active queue with its new (1-day) interval.
- CSV export/import is strictly two columns (front, back) in both directions; `note` is permanently out of CSV transport, documented as an intentional limitation. Parsing is RFC4180-compliant (quoted commas/newlines/quotes respected).
- CSV duplicates (whitespace-trimmed, case-sensitive exact front+back match within the target deck) are skipped per-row with an explicit visible reason, never imported and never silently merged; every other valid row in the same file still commits.
- The daily reminder's notification body carries no live due-count claim — generic truthful copy only; any in-app number reuses the shared due function.
- Demo-flagged review events get full real SM-2 treatment for their own deck, but are excluded by default from "all decks" aggregate retention/due stats, no opt-in blending in this build.
- Archiving and permanent deletion are distinct actions: archive is fully reversible (editable/exportable/unarchivable) and hides a deck from default review scope only; delete is a separate, explicitly and distinctly confirmed, cascading destructive action.

**Edge cases named and settled:** blank front/back blocked with inline validation; duplicate deck names allowed, disambiguated by timestamp; mid-session timezone/date rollover can't mutate an in-progress queue (snapshot); interruption before a grade is submitted mutates nothing, interruption after a grade persists it before any UI transition; malformed CSV rows (missing fields, bad quoting, non-UTF8) get individual, line-numbered errors; re-importing the same CSV twice is idempotent by construction (duplicates skip, not double-insert).

**Data and privacy implications:** everything stays on-device sandbox storage; no accounts, no analytics, no sync identifiers, no remote calls anywhere except the StoreKit purchase transaction itself (already locked in an earlier phase); notifications never surface content beyond the user's own due-state; CSV import/export uses only the standard OS share/file flows.

**Risk register (with mitigation):**
- SM-2 boundary correctness — mitigated by the now-fully-specified formula table plus the mandatory unit test suite, including a new required test case: grade a card Hard at ease 2.8/interval 20 and assert the result is meaningfully less than what Good would have produced from the same state.
- Cross-surface due drift — mitigated by the single shared due function plus the explicit session-snapshot rule.
- CSV correctness/idempotency — mitigated by RFC4180 parsing and skip-on-duplicate behavior.
- Reminder false-claim risk — mitigated by generic, non-numeric notification copy.
- Aggregate-stats honesty risk — mitigated by demo-data exclusion from aggregate views.
- Archive/delete confusion — mitigated by modeling them as two distinct, separately-confirmed states/actions.

**Final assumptions:** iOS 17+ SwiftUI/SwiftData/Swift Charts baseline; simulator clock manipulation is an accepted integration-test method; every "fast-follow" item named in prior phases (all-decks UI, demo data, CSV, stats charts, reminders, StoreKit) is real future work, not silently dropped scope; calendar-day semantics always use local midnight, never rolling 24-hour windows.
