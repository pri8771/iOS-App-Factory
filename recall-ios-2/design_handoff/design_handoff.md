Now the part I actually want to push hard on, because it's an engineering trap hiding inside a design decision everyone already agreed on. The signature interaction — the 3D Y-axis card flip — has a real SwiftUI gotcha: `rotation3DEffect` rotates the same view, it doesn't swap content, so if you naively rotate one view from 0° to 180° the back face renders mirrored (readable only in a mirror) unless you swap in the back-face content exactly at the 90° midpoint and apply a compensating 180° rotation to it so it reads correctly once past the midpoint. This has to be built as two overlaid views (front/back) each with their own rotation and a `.opacity`/visibility toggle keyed to rotation angle, not one view with animated text swap. The second trap is hit-testing: whichever face is rotated past 90° and visually hidden still receives touches unless you explicitly `.disabled()` or `.allowsHitTesting(false)` it, so a fast double-tap during the flip can register on the wrong face. Both of these need to be named explicitly in the handoff or a builder will ship a flip that mirrors the back text or double-fires on quick taps.

Second engineering trap, arguably more important: the locked "session snapshot, never re-queried mid-session" rule ([REDACTED:high_entropy]) is incompatible with using SwiftData's `@Query` property wrapper inside the Review view. `@Query` is inherently live — it auto-refreshes the moment any matching model object's `nextReviewDate`/`updatedAt` changes, which is exactly what happens the instant you grade a card. If Review's queue is built with `@Query`, the "snapshot" is fiction; grading card 3 will cause SwiftData to silently re-evaluate the fetch and can reorder or drop cards from the array the view is iterating. The queue must be captured once at scope-selection time as a plain `[PersistentIdentifier]` or `[Card]` array assigned to local `@State`, built from one `FetchDescriptor` call through the shared due function, and the Review view must never re-run that fetch until scope-selection happens again. This is the single highest-risk implementation detail in the whole app relative to what's already been decided, because it's the kind of thing that compiles, looks correct in a quick demo, and then breaks under exactly the force-quit/relaunch or clock-jump test that's supposed to prove it.

Third: due-count computation for deck rows on the Decks screen must not be N separate fetches (one due-count query per deck row) — that's an N+1 pattern that'll show up as jank once someone has more than a handful of decks. The shared `dueCards(scope:)` function should back a single grouped fetch (one `FetchDescriptor` with a predicate on `nextReviewDate <= endOfLocalDay`, then bucketed by deck in memory) that Decks calls once per screen appearance, not once per row. Same discipline applies to the Stats aggregate queries — demo-exclusion needs to be a predicate condition in the fetch itself (`isDemo == false`) for aggregate views, not a post-fetch `.filter` that still pulls demo rows into memory and risks a future screen forgetting to filter them back out.

Fourth, smaller but worth locking now: the daily reminder must be scheduled as a repeating `UNCalendarNotificationTrigger` built from `DateComponents(hour:minute:)` with `repeats: true`, not a one-shot notification re-scheduled by app logic — a one-shot silently stops firing the day the user doesn't open the app, which would quietly violate "reminds you daily" the first time it matters.

### Binding engineering constraints (locked, not optional notes)
1. 3. Demo-data exclusion from aggregate Stats views is a predicate condition in the fetch itself (`isDemo == false`), never a post-fetch `.filter`.
