## Original Prompt

```
Build a polished, fully offline iOS spaced-repetition flashcard app called "Recall". Native Apple stack ONLY: SwiftUI + SwiftData for persistence, Swift Charts for stats. No backend, no accounts, no third-party SDKs, no network of any kind — the app must work in airplane mode forever, all data on-device. Follow the ios-app-factory-rules. Runnable in the iOS Simulator via Xcode; provide clear run instructions.

HARD RULE ON GAPS: Anything that would need infrastructure this project cannot provide (cloud sync, shared/community decks, a deck marketplace) must NOT be faked or stubbed. Record each honestly as a gap with a short note on what building it for real would take. Do not add placeholder UI that pretends these work.

CORE FEATURES (favor complete over broad):
1. Decks & cards: create/edit/archive decks; cards have a front, back, and optional note. Card editing must be fast and keyboard-friendly.
2. Spaced-repetition scheduling: implement the SM-2 algorithm (ease factor, interval, repetition count) with Again/Hard/Good/Easy grading. THIS IS THE HEART OF THE APP. Implement it as its own standalone, pure, tested module — provably right, not plausibly right. Unit tests MUST cover: first reviews, lapses resetting the interval, ease-factor floors, and day-boundary handling in the device's local time zone (a "day" is a calendar day).
3. Review session: shows due cards for a chosen deck (or all decks); front → tap to reveal → grade. Session summary at end (cards reviewed, again-rate, time spent). Must handle interruption gracefully — quitting mid-session loses nothing.
4. Stats: per-deck and overall — due-forecast bar chart for next 30 days, daily review-count history, and retention rate (% graded Good/Easy). Handle empty and sparse data gracefully.
5. Deck import/export: export any deck to CSV; import cards from a two-column CSV (front, back) with a preview step and per-row error reporting — never silently drop a row.
6. Review reminders: one optional LOCAL notification per day ("You have N cards due") at a user-chosen time; respect permission denial gracefully. No push, no server.

PRIORITIES (in order): (1) SM-2 module correctness above all — proven via its tests; (2) review-flow speed; (3) honest empty states. Include a "demo data" toggle in Settings that seeds two decks with a realistic review history so stats screens are never empty on first look.
```

### Round 1


**Codex (Product Strategist · User Advocate) — Round 1**

Recall is a polished, fully offline iOS flashcard app that helps self-directed learners protect long-term retention by turning short daily review sessions into trustable outcomes through immediately persisted, SM-2-powered scheduling with no accounts, no network, and no fake data.

The primary user is someone like a language learner or certification candidate on a plane/train with unstable connectivity who has a small window of 60–180 seconds to clear due cards and come back tomorrow with a known-correct schedule they can trust.

The core loop is: choose a deck or all decks, load only truly due cards for the current local day, tap to reveal answer, grade with Again/Hard/Good/Easy, persist that card’s new interval/ease/repetition immediately, and continue until finished for an accurate summary (reviewed count, again-rate, elapsed time), with interruption-safe behavior that preserves all prior grades even after app relaunch.

Hard scope boundaries are: one native app only (recall-ios-2), no cloud sync, no shared/community deck marketplace, no accounts, no push or backend, no cross-device collaboration, only two-column CSV import/export, and only the four core screens (Decks, Review, Stats, Settings) with fast keyboard-friendly card editing and real empty/loading/success/error states, plus local notification reminders that reflect true system permission status.

Measurable success criteria are: all features run entirely offline; deck/card CRUD, archive, and immediate grade persistence work against restart-safe force-quit interruptions; SM-2 engine is pure and test-covered for first-review, lapse reset, ease-factor floor, and local calendar-day/DST boundary behavior; due review/session flow never shows non-due cards and summary metrics match graded cards; stats render forecast/history/retention for real and sparse data without fabricated values; CSV import always shows a preview and per-row errors with no silent drops; one-per-day local reminder obeys actual notification authorization state and gives a re-enable path on denial; demo data is clearly labeled as non-user data and fully removable when disabled.

The biggest risk is clock-boundary trust debt from SM-2 day calculations (especially DST/local-calendar transitions), and the final output must preserve this as a hard acceptance invariant, not an implementation detail.

**Claude (Design Lead · Systems Thinker) — Round 1**

Here's my independent take, coming at this purely from how the thing will actually get used and where it'll break.

The product promise I'd lock in: Recall is a single-purpose, fully offline flashcard app that schedules your reviews for you using a correctly-implemented SM-2 algorithm, so you always know exactly what to study today and never have to think about scheduling yourself. The promise isn't "flashcards" — Quizlet and a hundred index-card apps already do flashcards. The promise is trustworthy scheduling with zero infrastructure risk. If the SM-2 engine is even slightly wrong, the whole product promise collapses, because the entire value proposition is "trust the algorithm, not your own judgment about what to restudy."

Primary user and scenario: someone with an existing pile of material to memorize — vocab, board-exam facts, terminology — who opens the app in short, frequent bursts (waiting in line, on a commute, before bed) and expects the due list to already be correct with zero setup ceremony each time. The core loop is: open app → see what's due (by deck or across everything) → tap through reveal/grade for each card → get a short honest summary → close. That loop needs to be interruptible at literally any point — mid-card, mid-session, mid-deck-switch — with zero state loss, because the real usage pattern for a "waiting in line" app is getting interrupted by the thing you were waiting for.

Where I'd push back on scope before it drifts: this app has an unusually large number of "silent correctness" surfaces for something that sounds simple — the SM-2 math itself, but also calendar-day boundaries, timezone changes (someone flies during a review streak), DST transitions, and what "due" means when the device clock changes (a user could travel and gain/lose review days; the spec should say due-ness is computed from the device's current local calendar day at the moment of viewing, not cached, so travel can't produce a broken or duplicated queue). None of this is visible in a screenshot, so it's exactly the kind of thing that gets glossed over once UI work starts feeling more urgent than test-writing.

The second thing I'd flag as an information-architecture risk rather than a feature gap: "due cards for a chosen deck or all decks" sounds like one screen, but it's actually two different empty-state stories and two different session-summary stories (a per-deck streak versus a mixed-deck session where the user might want to know which decks contributed to the again-rate). If the review screen doesn't carry a lightweight sense of "which deck is this card from" when reviewing all decks, the session summary can't honestly attribute anything, and users studying multiple decks lose the ability to tell where they're actually struggling.

Hard scope boundaries I'd keep non-negotiable: no cloud sync, no accounts, no shared/marketplace decks, no card types beyond front/back/note, no tags, no rich text/markdown/LaTeX — all already decided, and I'd resist any pressure later to sneak these in as "small" additions, because each one touches the SwiftData schema and therefore touches every guarantee about persistence and demo-data badging.

Measurable success criteria I'd hold the build to, stated so they're actually checkable against a running app rather than a vibe: (1) the SM-2 test suite passes against known reference sequences including a lapse-then-recover and a DST-crossing multi-day gap; (2) a card graded and then a force-quit/relaunch shows the exact same next-due-date as if the app had stayed open; (3) a cold-start review session with zero due cards shows a designed empty state, not a blank screen or a spinner; (4) CSV import of a file with at least one bad row completes with every row individually accounted for (imported or flagged), and the post-import deck count matches the reconciled preview exactly; (5) turning off the demo-data toggle leaves zero demo-flagged rows in the store, verifiable by count.

The detail I most want preserved into architecture: "due" must be computed live from local calendar day at read-time everywhere it's displayed (deck list badge, review scope selector, notification content, stats forecast axis) — one shared function, not reimplemented per screen — because that's the single spot most likely to silently drift from the SM-2 module's own day-boundary logic and produce a mismatch between "you have 3 cards due" and what actually loads in the review session.
