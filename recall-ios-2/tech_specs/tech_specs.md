**Claude (Frontend Engineer · Visionary) — Round 1**

I'm going to lay out the client architecture for Recall as I think it should be built, since this phase is where "tech_specs" either becomes a real contract parallel build lanes can code against, or a vague paragraph that gets reinterpreted five different ways during build.

Start with the shape of the app. `RecallCore` is a real local Swift Package with a single job: given a schedule and a grade, produce the next schedule, and given a schedule and "now," say whether it's due. Nothing in it touches SwiftData, SwiftUI, or `Date()` directly — every function takes a `Clock`. The app target is SwiftUI + SwiftData, MV-not-MVVM: views own `@Environment(\.modelContext)` for CRUD, and the two places where "one shared function" actually matters — due-querying and review-session state — are owned by dedicated `@Observable @MainActor` service types (`DueQueryService`, `SessionEngine`) so there's exactly one code path, not a convention someone can forget. Root navigation is a three-tab `TabView` (Decks, Stats, Settings); Review is a `fullScreenCover` with its own `SessionEngine` instance created fresh at scope-selection time from one `FetchDescriptor` call — never `@Query` inside that view, because `@Query`'s live refresh would mutate the queue the instant a card gets graded, which is exactly the bug the whole force-quit guarantee depends on not happening.

On the data model, I want to name something explicitly that hasn't been spelled out yet: Recall needs a `ReviewLogEntry` model, separate from `Card`'s current schedule state. `Card` only knows its *current* ease/interval/next-due-date — it has no memory of history. But the daily-history chart, the retention-rate calculation, and the per-deck attribution in a mixed "all decks" session summary all need a durable record of *every grading event*, not just the card's present state. So: `Deck` (id, name, createdAt, isArchived, isDemo), `Card` (id, front, back, note, deck relationship, easeFactor, intervalDays, repetitions, nextReviewDate, isDemo — denormalized off the deck rather than traversed through the relationship, because SwiftData's `#Predicate` support for relationship-property filtering is exactly the kind of thing that quietly falls back to in-memory filtering, which is already banned here), and `ReviewLogEntry` (id, timestamp, gradeRaw: Int, cardID, deckID, isDemo — both IDs and the demo flag denormalized so stats queries never need a join to build a predicate). Every `#Predicate`-filtered field across all three models stays a flat `Int`/`Bool`/`Date`/`UUID` — no enums, no computed properties, consistent with the architecture review's ruling. For CloudKit-shape (still unbuilt, still just a documented future path), every non-optional attribute needs either a default value or must be Optional, and every relationship must be Optional — that's a more specific rule than "no `.unique`" and worth locking now so nobody adds a required non-defaulted property later and quietly breaks the migration path.

Persistence: one `ModelContainer` for `[Deck.self, Card.self, ReviewLogEntry.self]`, one `SchemaMigrationPlan` established from day one even though there's only one version today — the discipline is cheap now and expensive to retrofit. Every grade-write path calls `context.save()` synchronously right after the mutation; I'd wire this through a single `GradeRecorder` function so there's one call site that both updates the `Card` and appends the `ReviewLogEntry`, atomically, rather than trusting two separate writers to stay in sync.

Here's the one place I want to push past "adequate" into something a bit bolder, because I think it's cheap and pays for itself immediately: the clock-jump acceptance test that's been referenced across five phases as "advance the simulator's system clock and relaunch" is a manual, flaky, slow way to prove day-boundary correctness at the app level. I want a `DebugClockOverride` — the app checks `ProcessInfo.processInfo.arguments` for a launch argument like `-RecallClockOffsetDays N`, compiled only into Debug/Test configurations (stripped entirely from Release via `#if DEBUG`, so it can never leak into a shipped build), and if present, the app's injected `Clock` becomes a real offset clock instead of `SystemClock`. That turns "quit the app, manually change the simulator date in Settings, relaunch, eyeball it" into a real `XCUITest` that launches with an argument, grades a card, terminates, relaunches with a +1-day offset, and asserts the card now shows due — deterministic, fast, runs in CI, and actually exercises the same `DueQueryService` path the user hits, rather than only proving the pure module is correct (which the `TestClock` unit tests already do). This is the kind of investment that makes the "provably right" claim actually provable end-to-end instead of provable-in-the-algorithm-but-hoped-for-in-the-UI.

The edge case I don't think any prior phase named and I want on the record: a device clock that moves *backward* — a user manually resetting their system time, or a bad NTP sync — shouldn't be able to produce a card that's "extra due" or double-counted in daily-history stats. Since due-ness is a pure `calendar.startOfDay(due) <= calendar.startOfDay(now)` comparison and `ReviewLogEntry` timestamps are write-once at grade time, a backward clock jump can't retroactively duplicate history, but it can make an already-graded-today card look due again if "today" rewinds past the grading day — worth one explicit unit test (`TestClock` moving backward across a review) so this isn't discovered by an actual user's misconfigured device.

Testing strategy: `RecallCoreTests` (pure XCTest, `TestClock`-driven) covers first-review, lapse-reset, ease floor under repeated Again, the Hard-must-always-underperform-Good invariant at ease 2.8/interval 20, calendar-day boundaries including a spring-forward and a fall-back transition, backward-clock safety, RFC4180 edge cases (quoted commas, embedded newlines, escaped quotes), and duplicate detection. `RecallAppTests` uses an in-memory `ModelContainer` to test `DueQueryService`, `SessionEngine`, `GradeRecorder`, and CSV commit against real SwiftData without touching disk. `RecallAppUITests` owns the force-quit/relaunch persistence test and the new clock-offset due-computation test described above, both fully automated.

## Final Output

**Architecture overview:** `RecallCore` is a real local Swift Package — pure SM-2 engine, shared due-computation, RFC4180 CSV parser/writer — with zero SwiftData/SwiftUI imports and every "now"-dependent call taking an injected `Clock`. The app layer is MV, not MVVM: views hold `@Environment(\.modelContext)` for direct CRUD; review-queue construction and stats aggregation go through two dedicated `@Observable @MainActor` services, `DueQueryService` and `SessionEngine`, so "one shared function" is enforced by there being exactly one type. Three tabs (Decks, Stats, Settings); Review is a `fullScreenCover`, never a tab.

**Data models (SwiftData `@Model` classes, not `Codable` structs):**
- `Deck` — id, name, createdAt, isArchived, isDemo, cascade-deleting `cards` relationship.
- `Card` — id, front, back, note, `deck` relationship, easeFactor, intervalDays, repetitions, nextReviewDate, isDemo (denormalized from deck), lastGradeRaw. Cards belong permanently to their creation deck — no `moveCard` function exists anywhere in this contract, and that absence is intentional.
