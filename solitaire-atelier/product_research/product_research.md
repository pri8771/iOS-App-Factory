## Original Prompt

```
Build a native iOS Solitaire (Klondike) game — SwiftUI, 100% local, zero
network calls, zero sign-in/accounts/analytics/telemetry of any kind. No
backend. All state (stats, settings, saved game) persists on-device only.

THE CENTRAL CONSTRAINT — READ THIS FIRST: this must be a real, fully
playable, correctly-rules-implemented Klondike solitaire game. Drag-and-drop
(or tap-to-move) card interaction, legal-move validation, win detection,
undo, new-game/deal, and a stock/waste/foundation/tableau layout that
actually works. Do not let the visual ambition come at the cost of the game
being playable and correct — a beautiful app that can't be played is a
failure.

VISUAL DESIGN — THIS IS THE PART THAT MUST WIN AWARDS:
Cards must look like real, tactile playing cards — not the generic flat
rounded-rectangles-with-tiny-corner-pips that every solitaire clone uses.
Invent a genuinely original custom card face system: bespoke rank/suit
typography or iconography (not SF Symbols reused as suit glyphs), a
consistent illustrated or generative pattern language across all 52 cards
and the card back, real card-stock texture/shadow/lighting, and satisfying
physical motion (cards should feel like they have weight — spring-based
drag, believable flip/deal animation, subtle parallax or depth).

The bar: this should look and feel like something from an Apple Design
Award reel, not a tutorial app. Judge yourself against that bar throughout
— if a screen looks like a stock SwiftUI solitaire tutorial, it has failed
the brief. One clear, original visual "hook" (an art direction, a material
language, a signature interaction) should be identifiable in one glance
that no other solitaire app has.

Also include: light/dark mode (both fully art-directed, not just inverted
colors), haptics on card moves/wins, a stats screen (games played/won,
best time, streak — all local), and a settings screen (draw-1 vs draw-3,
card back selection, timer on/off).

Ship something that could realistically be submitted to the App Store today
and be visually distinctive in a screenshot alone.
```

**Claude (QA & Risk · Pragmatist) — Round 1**

Here's my independent read on this, coming at it from what could break and what's actually achievable in a first build.

Audience-wise, I'd treat this as two overlapping groups rather than one: the mass-market "kill five minutes in a waiting room" solitaire player who wants zero friction and a game that just works, and a smaller design-literate audience the prompt is explicitly courting with the "Apple Design Award reel" language — people who'll screenshot it and compare it to MobilityWare's Solitaire, Apple's own card-game visual conventions, and polished indie card apps. This is my own inference from the prompt's tone, not a researched claim — I don't have fetched competitor data in this context, so I'm marking every comparison below as ASSUMPTION rather than pretending I looked it up. The dominant incumbents (MobilityWare Solitaire, Solitaire.com-style clones) win on ubiquity and lose badly on visual identity — flat rounded rectangles, tiny corner pips, ad interstitials breaking the tactile fantasy. The gap this app is aimed at is real: nobody in that category has invested in a bespoke card-face grammar or genuine physicality. But I want to flag the trap in chasing that gap: readability at actual card size is a correctness requirement wearing an art costume. Seven tableau columns on a 6.1" iPhone in portrait means each card is roughly 45-50pt wide. A "bespoke, non-SF-Symbols" suit/rank glyph system that reads great in a design mockup at 400% zoom can become illegible or ambiguous at that size — and an illegible rank is a gameplay bug (player can't tell if it's a 6 or an 8), not just an aesthetic miss. I'd treat legibility-at-native-size as a hard gate on the card system before any further art investment, and I want that written down now so a later phase doesn't have to rediscover it after the glyphs are already built.

Second concrete risk: touch ergonomics. Narrow tableau columns plus multi-card run dragging plus needing precise drop-target detection is exactly the kind of interaction that looks fine in a demo GIF and falls apart under a real thumb — mis-taps triggering snap-back animations repeatedly will read as "janky" rather than "tactile," which directly undercuts the one thing the prompt cares most about. I'd want generous hit-testing padding beyond the visual card bounds baked into the interaction model from the start, not bolted on after QA complains.

Third: accessibility isn't a nice-to-have here, it's a real conflict with the brief's own ambition. Spring-based physical drag and flip animation must honor `accessibilityReduceMotion`, and this is a card game where color-only suit differentiation (red/black) plus small custom glyphs is a real risk for contrast/VoiceOver users. The HIG cheat sheet already in context is clear that native accessibility comes free with system components and has to be deliberately re-earned with custom ones — a fully custom card renderer means someone has to explicitly wire VoiceOver labels ("Seven of Hearts, tableau column 3, face up") since a generative glyph won't be inherently readable by assistive tech.

Fourth, and this is a gap I don't think the prior phase actually closed despite flagging it: "stock cycling behavior is fixed by explicit settings semantics and documented" was decided as a principle but never pinned to an actual value. Standard Klondike has real variants here — unlimited redeals vs. capped passes through the stock — and different well-known implementations disagree. I'd lock this now rather than let it drift into implementation-time improvisation: default to unlimited stock recycling (waste flips back into stock, redraws indefinitely) since that's the more common casual-app default and the simplest to implement correctly, and treat a pass-limit as out of scope unless a later phase explicitly argues for it.

Fifth, a boring but real one: state restoration under app termination. iOS can kill this app mid-drag or mid-flip-animation. The persisted save has to represent a coherent logical game state (which pile each card is logically in, face-up/face-down) independent of wherever the animation happened to be visually — otherwise relaunch shows a state that doesn't match what the player saw right before backgrounding, which will read as data corruption even though it's really an animation/state-sync bug.

For platform opportunities I'd actually call out restraint as the opportunity: CoreHaptics/UIFeedbackGenerator for real haptic texture is free and cheap to get right, `matchedGeometryEffect` and spring animations are native and don't need any hand-rolled physics engine, and Dynamic Type / dark mode semantic colors come for free if the theme file is disciplined about it. The temptation I'd guard against is scope creep toward things that sound native and cool but aren't in the contract — widgets, Live Activities for an in-progress game, Game Center — all of which either violate the no-network/no-accounts constraint or just aren't asked for.

For the first build, my implication is: ship fewer card backs (two well-executed, not a gallery), pick one real signature interaction (my guess: the deal/flip animation, since it's the first thing anyone sees and doesn't require solving the harder multi-card-drag physics problem to feel premium) rather than spreading effort across several competing motion ideas, and validate the custom glyph system's legibility at true on-device card size before treating the art system as settled — because if that fails, it fails the brief's own explicit test ("looks like a stock tutorial") no matter how generative and consistent the underlying design system is.
