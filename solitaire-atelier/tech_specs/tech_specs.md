**Codex (Red Team · Closer) — Round 1**

One hard requirement the earlier phases still missed is explicit restore integrity validation before exposing a restored board. The current decisions guarantee atomic writes and independent recovery branches, but they do not force a semantic gate on loaded state. Concrete failure scenario: a validly decoded `GameSave.json` can still encode an impossible board (duplicate/missing card IDs, wrong pile ordering, illegal face-up stack) after a crash, app sandbox corruption, or out-of-band file tampering. The app could then render an unplayable game and immediately misreport move legality. Decision: add a mandatory `RestoreIntegrityService` check at cold start and after every restore candidate load; if validation fails, discard restored `GameState`, start a fresh deal, keep the event log and settings untouched, and show the existing non-blocking recovery banner so the user is not silently put in a corrupted but interactive state. Biggest objection is added startup cost, but validation is O(52) and tiny compared with the correctness stakes, so it is mandatory.

**Claude (Frontend Engineer · Visionary) — Round 1**

Here's my independent pass on turning six phases of locked decisions into an actual buildable spec.

Architecture is a single feature-module app under one Xcode target, no dynamic frameworks (unnecessary indirection for an app this size), organized as: `App/` (App entry, `SolitaireAtelierApp.swift`, root `TabView`, service instantiation and `@Environment` injection), `DesignSystem/` (`Theme.swift` as the single token source — fonts, spacing, colors, radii, motion curves — plus the `CardGlyphs/` bespoke `Shape` library), `Domain/` (pure value types and `GameEngine`, zero SwiftUI imports, fully unit-testable in isolation), `Persistence/` (the three file stores, atomic writer, restore coordinator), `Features/Game/`, `Features/Stats/`, `Features/Settings/` (each owning its named component set from design_handoff), `Interaction/` (haptics service, drag/tap gesture glue), and `DebugTools/` (the `#if DEBUG` legibility gallery). Domain has zero dependency on Persistence or SwiftUI; Persistence has zero dependency on Domain's UI concerns — it only knows Codable structs. This is the boundary that keeps "parallel build lanes can work without inventing incompatible types" true in practice, not just in principle.

On data models, I want to push for making illegal states unrepresentable rather than defensively checked. `Suit` is a 4-case enum with a `color` computed property (never a stored bool, since red/black must derive from suit, not be duplicated data that can drift). `Rank` is an `Int`-backed enum 1...13 with `symbol`/`displayName`. `Card` is `id: UUID, suit: Suit, rank: Rank, isFaceUp: Bool` — a plain struct, no view-layer state on it at all, because animation/selection state living inside the model is exactly the "persisted mid-animation" bug product_research already flagged. `PileID` is an enum: `.stock`, `.waste`, `.foundation(Suit)`, `.tableau(Int)` — using the type system to make "seven tableau columns, four foundations" a compile-time fact instead of an array-bounds hope. `GameState` holds `piles: [PileID: [Card]]`, `drawMode: DrawMode`, `elapsedSeconds: TimeInterval`, `isTimerRunning: Bool`, `startedAt: Date?` (nil until the first state-mutating action per [REDACTED:high_entropy]), and the undo history is a separate `undoStack: [GameStateSnapshot]` capped at 200, living alongside `GameState` inside `GameSaveFile`, not inside `GameState` itself — undo history isn't game state, it's a save-file concern, and keeping that boundary clean means `GameState` equality checks (which the fuzz-invariant tests need) don't get polluted by history bookkeeping.

The part I think the group hasn't actually nailed down yet, and where I want to be opinionated rather than leave it implicit: interaction state needs to be one explicit finite-state enum, not a scatter of `@State` booleans across `GameView`. I'm proposing `InteractionState`: `.idle`, `.sourceSelected(PileID, cardIndex: Int, legalDestinations: [PileID])`, `.awaitingConfirmation` (same shape, kept distinct from selection for VoiceOver phrasing), `.resolvingMove(Move)`, `.dealing`, `.terminal(TerminalState)` where `TerminalState` is `.won(WinSummary)` or `.stuck`. Every tap handler is a pure function from `(InteractionState, TapTarget) -> (InteractionState, [Effect])` where `Effect` covers haptic firing, move execution, and save scheduling. This is the single piece of architecture I think is most likely to get informally reinvented as ad-hoc bools under time pressure, and it's exactly the kind of thing that turns into an unreproducible "why did the highlight not clear" bug three weeks from now. I want it locked as a named type in the interfaces contract so nobody starts with `@State private var selectedCard: Card?` and grows it organically.

For the deal/flip — since this is this app's one shot at looking remarkable and the group has correctly identified it as unforgiving — I want `DealOrchestrator` to drive card transit through `matchedGeometryEffect` keyed on `Card.id`, not through independently-animated offsets per view; that's what makes a run-relocation move (multiple cards moving together, [REDACTED:high_entropy]) look like one coherent physical unit instead of N cards independently animating to N nearby points and racing each other visually. `DealOrchestrator` owns exactly two entry points: `dealFresh(into: GameState, reduceMotion: Bool) -> AnimationPlan` and `transit(_ move: Move, reduceMotion: Bool) -> AnimationPlan`, both pure functions returning a declarative plan the view layer executes — testable without a running app, since "did we compute the right animation sequence" and "did SwiftUI render it smoothly" are different failure modes and only the first one is unit-testable.

Persistence and concurrency: I have nothing to add to what's already locked (three files, three actors, debounced event-driven writes, atomic temp-then-swap, undo inside `GameSave.json`) — that's correct and I'm not reopening it. What I'll make concrete here is the actual restore contract, since "three independent restores" needs one coordinating type or the App root turns into inline `Task {}` soup: `AppRestoreCoordinator` runs all three loads concurrently via `async let`, classifies each into `RestoreOutcome` (`.restored`, `.fallbackDefault(reason:)`, `.dataLoss(reason:)`), and only then flips `hasFinishedInitialLoad`. `PersistenceError` is a concrete enum (`.decodingFailed`, `.fileCorrupted`, `.ioFailed`, `.schemaMismatch(found: Int, expected: Int)`) so the recovery banner and Stats data-loss panel can show honest, differentiated copy instead of a generic "something went wrong."

Testing strategy: I'd add one thing to what ios_architecture_review already locked — since `GameEngine`, `DealOrchestrator`, and the persistence layer are all SwiftUI-free by construction, the majority of correctness tests never need to spin up a view hierarchy at all, which is what makes the fuzz/invariant suite fast enough to actually run on every commit rather than being the kind of slow test nobody runs locally. XCUITest stays reserved for the things only a rendered screen can prove: layout non-collision under Dynamic Type, the deal animation actually playing, and the two Stats states actually looking different.

Biggest risk I'd flag on my own contribution: an explicit `InteractionState` enum plus `matchedGeometryEffect`-driven multi-card transit is more upfront design than "just wire up tap gestures directly," and if the build phase treats this as optional architecture and reverts to inline view state under time pressure, we lose exactly the coherence this app's signature interaction depends on. I think it's worth the cost given this is a zero-menu-screen app where every rough edge is maximally visible, but I want that trade-off on the record rather than assumed.

Both of you clearly agree on the architecture's *shape* — one `@Observable` `GameEngine`, `Domain`/`Persistence` separation, three independently-actored files, an injectable-RNG test seam that never reaches production, and a component/state model that matches design_handoff exactly (`CardView`, `WinOverlay`/`StuckOverlay` separate, `StatsModeFilter` vs `DrawModeSetting` separate, the debug legibility gallery). But you wrote two genuinely different type systems, and they don't compose:

- **Card identity**: Codex's `PlayCard.id: Int`; Claude's `Card.id: UUID`. Pick one — everything downstream (matchedGeometryEffect keys, undo diffing, stats event correlation) depends on it.
- **Pile addressing**: Codex's `PileType.foundation(Int)`; Claude's `PileID.foundation(Suit)`. These aren't cosmetically different — one makes "four foundations, one per suit" a compile-time fact, the other doesn't.

- **Stats model**: Codex's `StatsEvent` is an enum with two cases (`.gameStarted`/`.gameEnded`) written as two log entries; Claude's is a single struct written once per completed session with `outcome`. Different persisted shapes, different derivation logic for `DrawModeStats`.

### Round 2


**Codex (Red Team · Closer) — Round 2**

Codex, you and Claude both had the right strategic architecture, but this round’s unresolved issue isn’t polish — it’s type-level correctness. The current mismatch (Int id vs UUID, foundation(Int) vs foundation(Suit), undo in `GameState` vs save-file-only, and the missing typed restore outcome contract) is exactly the kind that blows up parallel implementation. I’m locking the contract now so no one builds against a different universe.

I’ll take the stricter/safer side of both: `Card.id` is deterministic `Int` (derived from suit/rank, not generated at runtime), `PileID.foundation` is keyed by `Suit`, and undo lives only in `GameSaveFile` as a capped full-state log, while `GameState` stays pure logical board state for equality/tests. I agree with Claude that `InteractionState` is not optional with this feature set; it prevents ad-hoc tap booleans from becoming state-bug debt, and we need it for tap + ambiguity + terminal flows to stay consistent. I also agree with the `DealOrchestrator`/`AnimationPlan` direction, but keep it as a pure plan producer (no side effects) so it can be unit-tested independently even when UI isn’t.

Red-team gap you both missed in your type contracts: restore integrity must include a hard validation pass before a resumed game is exposed, not just JSON decode. The concrete failure scenario is a single-file bit flip during write producing 53 cards, duplicate `PlayCard` IDs, or a foundation with mixed suits; if we skip validation and go straight to active board, the user sees a “fine” board that can only produce false “stuck/no-move” outcomes later. That is a trust break. So every restore of `GameSave` must run `RestoreIntegrityService` and classify as `.dataLoss` when invariants fail, even if decoding succeeds.

I also want the restore coordinator to keep the three-file independence explicit in the API: each actor returns a typed three-way outcome (`restored` / `fallbackDefault` / `dataLoss`) and no file failure can block the others. `hasFinishedInitialLoad` must flip after all three outcomes are known; if one fails, we still launch game + settings from their own results with honest banners/panels only where applicable.

**Claude (Frontend Engineer · Visionary) — Round 2**

Reading Codex's pass, we clearly landed on the same shape but wrote incompatible types everywhere it actually matters, so let me go conflict by conflict and pick winners instead of hand-waving a merge.

Card identity first, because I want to actually change my own answer here rather than just defend UUID. Neither `PlayCard.id: Int` nor my `Card.id: UUID` is right — this is a single-deck game (locked by DEC-prompt_contract-007), which means suit+rank is *already* a unique, stable identity for all 52 cards. There's exactly one Ace of Spades. Introducing a synthetic id, whether an arbitrary Int or a UUID, adds a second source of truth that has to agree with suit+rank and can drift if a test fixture or a bug ever constructs a duplicate. So: `Card` has no stored id at all — `var id: String { "\(rank.rawValue)\(suit.rawValue)" }`, computed from the two fields that already define it. And here's the actual reason this matters beyond tidiness: that computed id has to stay stable across a face-down-to-face-up flip, because it's the key we hand to `matchedGeometryEffect` for the flip animation. If `Card`'s identity accidentally depended on `isFaceUp` — which it would if you used full-struct equality or a naive hash as your view key — SwiftUI would see the flip as "old view destroyed, new view inserted" instead of one continuous view animating, and the entire signature deal/flip moment silently degrades into a cross-dissolve, which is exactly the thing design_discussion explicitly rejected. That's a real bug hiding in a schema choice, not a style preference, and it's why I want this specific resolution locked in the contract rather than left as an implementation detail.

Pile addressing: keeping `foundation(Suit)` over Codex's `foundation(Int)`. Same argument as round 1, just sharper now that I see his actual struct — `foundation(Int)` can silently be constructed as `foundation(7)`, which is a state the Klondike rules (four foundations, one per suit) say shouldn't exist, and now every piece of code that indexes into it needs a bounds check that `foundation(Suit)` gets for free from the compiler. I don't think this one's close.

Undo: I'm holding my position that it lives only in `GameSaveFile`, not inside `GameState`, but I want to name the actual problem with Codex's version rather than just restate a preference. He added `undoCursor: Int` alongside `undoStack`, which implies redo — and nothing anywhere in this entire decision log asks for redo. Every phase from `initial_discussion` through `design_handoff` says "undo," never "undo/redo." Adding a cursor is scope creep dressed up as a data structure, and it's the kind of thing that quietly becomes a half-implemented feature (a cursor field that build either wires up into a real redo button nobody asked for, or leaves dead and unused). I'd drop it: undo is a plain LIFO stack, `popLast()` restores the previous snapshot, full stop. And keeping it out of `GameState` isn't just about equality-check hygiene for the fuzz tests — Codex's `GameSnapshot` already dodges self-reference by capturing `board`/`timer`/`drawMode` fields directly instead of a nested `GameState`, so his design technically works, I'll give him that. But I still think the cleaner invariant is "`GameState` is exactly what's on the board right now, full stop" — it makes every fuzz-test invariant statement ("52 unique cards," "foundation never exceeds King") a direct claim about `GameState` with zero need to first strip out history noise.

Stats event shape — this is the one where Codex actually changed my mind and I want to say that out loud instead of just defending round 1. My single `StatsEvent` struct written once at game-end has a real hole: if the app gets killed mid-game — which is exactly the kind of thing this whole persistence architecture is built to survive — my design writes nothing for that session at all, because the write only happens at the end. Codex's two-event stream (`.gameStarted` written immediately, `.gameEnded` written on completion) means the start is durably on disk the moment a session begins, so an abandoned or crashed session still shows up as "played" instead of vanishing without a trace. Given this app's whole pitch is "we don't lie to you about your own data," a design that can silently drop an entire played session is the wrong one. I'm adopting his event-stream shape. Where I'll refine it: he also proposed a `DrawModeStats` cache struct sitting in `StatsLogFile` alongside the raw events, which I hadn't specified at all in round 1 — that's a real gap on my end, and it's the right pattern (events are the source of truth, `DrawModeStats` is a derived, incrementally-updated cache so `StatsView` doesn't recompute aggregates from the full event log on every render).

`RestoreIntegrityService` is the best thing either of us produced this round and I want to say clearly: Codex, that's the missed requirement the phase rules asked the Red Team to find, and it's a genuine gap, not a nice-to-have. Atomic writes plus successful `Codable` decoding only proves the bytes round-tripped — it says nothing about whether the *content* is a legal board. A schema bug, a hand-edited file, or a subtle bug in an earlier save could produce a perfectly valid JSON document describing two Aces of Spades or a face-up card sitting under a face-down one, and every one of our locality invariants downstream (move legality, stuck detection) would start operating on a lie. I'm folding this straight into the restore pipeline rather than bolting it on separately: `GameSaveStore.load()` decodes, then runs `RestoreIntegrityService.validate(_:)`, and a failure gets classified as `PersistenceError.semanticallyInvalid` and routed through the exact same `.dataLoss` → fresh-deal-plus-banner path design_discussion already locked for corrupt files. No new UI branch needed, just a new trigger into the branch we already have.

Since nobody's directly answered `InteractionState` or `DealOrchestrator` yet, I'll make the case one more time rather than assume silence is agreement: without a named FSM type, the natural build-phase shortcut is `@State private var selectedPile: PileID?` plus a few more optionals for highlight/confirmation, and that's precisely the pattern that produces the "why didn't the highlight clear" class of bug. I'm not budging on this one being a named contract type.

Two more things I caught doing my own red-team pass rather than just reacting to Codex's: first, neither of our round-1 specs actually named the split between draw-1's exact stuck-detection and draw-3's conservative approximation as two different implementations — `GameEngine.detectStuck()` was one method in both our sketches, but DEC-app_features-002 requires them to be distinct, separately-testable algorithms with different false-positive risk profiles, so I want a `StuckDetector` protocol with `DrawOneStuckDetector` and `DrawThreeStuckDetector` as two concrete types the fuzz suite can target independently. Second, [REDACTED:high_entropy] explicitly requires that when a tap resolves to multiple legal destinations, VoiceOver gets those exposed as discrete accessibility actions — that's sitting right there in the decision log and neither of our interfaces contracts actually named a type for it, so I've added a small `DestinationAccessibilityAction` value that `CardView`/`PileSlotView` build `.accessibilityAction` handlers from, driven straight off `InteractionState.sourceSelected`'s `legalDestinations`.

## Final Output

**Architecture overview.** Single Xcode target, no dynamic frameworks. One `@MainActor @Observable GameEngine` is the sole mutable-state owner (board, interaction, timer), instantiated once at the App root and injected via `@Environment`. Its production `newGame` always defaults to the system RNG; the `rng` parameter is a test-only seam that must never be reachable from any UI/Settings surface ([REDACTED:high_entropy]). Domain types have zero SwiftUI imports and zero dependency on the persistence layer, which itself only knows `Codable` structs — this boundary is what keeps parallel build lanes decoupled.

**File/module layout:** `App/` (entry point, root `TabView`, service wiring), `DesignSystem/` (`Theme.swift` token source + `CardGlyphs/` bespoke `Shape` library), `Domain/` (pure value types, `GameEngine`, `StuckDetector` implementations, `RestoreIntegrityService` — fully unit-testable with no view hierarchy), `Persistence/` (three file stores, `AtomicFileWriter`, `AppRestoreCoordinator`), `Features/Game/`, `Features/Stats/`, `Features/Settings/`, `Interaction/` (`HapticsService`, gesture glue), `DebugTools/` (`#if DEBUG` legibility gallery).

**Data models.** `Card` has no stored `id` — it's computed from `suit`+`rank` (`"\(rank.rawValue)\(suit.rawValue)"`), guaranteed unique under the locked single-deck rule, stable across `isFaceUp` toggling (so it keys `matchedGeometryEffect` correctly through a flip), and structurally excluded from `Codable` round-tripping since it's never a stored field. `PileID.foundation` is `Suit`-keyed, not `Int`-keyed, so "one foundation per suit" is a compile-time fact. `GameState` is pure logical board state only — no undo history, no animation/selection fields; the undo stack lives exclusively in `GameSaveFile` as a capped-200 LIFO full-state log (`popLast()`, no redo — nothing in this pipeline ever asked for redo). `InteractionState` is the single named FSM the Game screen reads from instead of scattered `@State` booleans. Stuck detection is two separate types (`DrawOneStuckDetector` exact, `DrawThreeStuckDetector` conservative) behind one `StuckDetector` protocol, independently fuzz-testable per DEC-app_features-002's differing exactness bar. Stats persist as a two-case event stream (`gameStarted` written immediately at session start, `gameEnded` on completion) so a crashed/abandoned session still shows up as played, with `DrawModeStats` as a derived, incrementally-updated cache rather than a per-render recompute.

**Persistence strategy.** Three independently-atomic-written files (`GameSave.json`, `StatsLog.json`, `Settings.json`), each behind its own actor conforming to one shared `PersistenceStore` protocol, `load()` returning `RestoreOutcome<Model>` directly (`.restored` / `.fallbackDefault` / `.dataLoss`) rather than throwing — this is the type-level enforcement of design_discussion's three-outcome recovery UI requirement. `GameSaveStore.load()` decodes, then runs `RestoreIntegrityService.validate(_:)` as a mandatory semantic gate (52 unique cards, no duplicate/missing ranks-per-suit, legal stacking, foundation monotonicity) before ever exposing a resumed board — a decodable-but-illegal save is `.dataLoss`, never silently activated. Saves are debounced ~300-500ms per store with write-coalescing, plus an unconditional `flush()` on `scenePhase` background. `AppRestoreCoordinator` runs all three loads concurrently and owns the single app-level `hasFinishedInitialLoad` flag that gates first paint across all three tabs.

**Testing strategy.** Unchanged from ios_architecture_review's locked plan (unit tests over legality/win/undo, randomized fuzz simulation per draw mode, XCUITest over observable flows, mandatory accessibility identifiers, `performAccessibilityAudit()`), now sharpened by this phase's types: the fuzz suite can target `DrawOneStuckDetector` and `DrawThreeStuckDetector` independently, and `RestoreIntegrityService` gets its own dedicated corrupt/invalid-save test fixtures.

## Final Output

**Architecture overview.** Single Xcode target, no dynamic frameworks. One `@MainActor @Observable GameEngine` is the sole mutable-state owner (board, interaction, timer), instantiated once at the App root and injected via `@Environment`. Its production `newGame` always defaults to the system RNG; the `rng` parameter is a test-only seam that must never be reachable from any UI/Settings surface ([REDACTED:high_entropy]). Domain types have zero SwiftUI imports and zero dependency on the persistence layer, which itself only knows `Codable` structs — this boundary is what keeps parallel build lanes decoupled.

**File/module layout:** `App/` (entry point, root `TabView`, service wiring), `DesignSystem/` (`Theme.swift` token source + `CardGlyphs/` bespoke `Shape` library), `Domain/` (pure value types, `GameEngine`, `StuckDetector` implementations, `RestoreIntegrityService` — fully unit-testable with no view hierarchy), `Persistence/` (three file stores, `AtomicFileWriter`, `AppRestoreCoordinator`), `Features/Game/`, `Features/Stats/`, `Features/Settings/`, `Interaction/` (`HapticsService`, gesture glue), `DebugTools/` (`#if DEBUG` legibility gallery).

**Data models.** `Card` has no stored `id` — it's computed from `suit`+`rank` (`"\(rank.rawValue)\(suit.rawValue)"`), guaranteed unique under the locked single-deck rule, stable across `isFaceUp` toggling (so it keys `matchedGeometryEffect` correctly through a flip), and structurally excluded from `Codable` round-tripping since it's never a stored field. `PileID.foundation` is `Suit`-keyed, not `Int`-keyed, so "one foundation per suit" is a compile-time fact. `GameState` is pure logical board state only — no undo history, no animation/selection fields; the undo stack lives exclusively in `GameSaveFile` as a capped-200 LIFO full-state log (`popLast()`, no redo — nothing in this pipeline ever asked for redo). `InteractionState` is the single named FSM the Game screen reads from instead of scattered `@State` booleans. Stuck detection is two separate types (`DrawOneStuckDetector` exact, `DrawThreeStuckDetector` conservative) behind one `StuckDetector` protocol, independently fuzz-testable per DEC-app_features-002's differing exactness bar. Stats persist as a two-case event stream (`gameStarted` written immediately at session start, `gameEnded` on completion) so a crashed/abandoned session still shows up as played, with `DrawModeStats` as a derived, incrementally-updated cache rather than a per-render recompute.

**Persistence strategy.** Three independently-atomic-written files (`GameSave.json`, `StatsLog.json`, `Settings.json`), each behind its own actor conforming to one shared `PersistenceStore` protocol, `load()` returning `RestoreOutcome<Model>` directly (`.restored` / `.fallbackDefault` / `.dataLoss`) rather than throwing — this is the type-level enforcement of design_discussion's three-outcome recovery UI requirement. `GameSaveStore.load()` decodes, then runs `RestoreIntegrityService.validate(_:)` as a mandatory semantic gate (52 unique cards, no duplicate/missing ranks-per-suit, legal stacking, foundation monotonicity) before ever exposing a resumed board — a decodable-but-illegal save is `.dataLoss`, never silently activated. Saves are debounced ~300-500ms per store with write-coalescing, plus an unconditional `flush()` on `scenePhase` background. `AppRestoreCoordinator` runs all three loads concurrently and owns the single app-level `hasFinishedInitialLoad` flag that gates first paint across all three tabs.

**Testing strategy.** Unchanged from ios_architecture_review's locked plan (unit tests over legality/win/undo, randomized fuzz simulation per draw mode, XCUITest over observable flows, mandatory accessibility identifiers, `performAccessibilityAudit()`), now sharpened by this phase's types: the fuzz suite can target `DrawOneStuckDetector` and `DrawThreeStuckDetector` independently, and `RestoreIntegrityService` gets its own dedicated corrupt/invalid-save test fixtures.
