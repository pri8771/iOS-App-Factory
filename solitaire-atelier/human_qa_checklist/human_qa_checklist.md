## 0. Pre-flight: known crash risk (test this first)

**QA-000 — Corrupt-save / restore-path crash probe**
The build's own test suite crashed here (`AppRestoreCoordinatorTests.swift:54`, force-unwrap on an empty/nil `[Card]`) before it could finish running — meaning this exact code path has never been exercised end-to-end by anything, human or automated.
- Steps: (a) Start a game, make a few moves. (b) Force-quit the app. (c) Locate `GameSave.json` in the app's Application Support container (via Xcode's device file browser or simulator container path) and either delete it or corrupt it (truncate the file, or edit one card's suit field to garbage). (d) Relaunch.
- Expected: App launches into a **fresh deal** (the full deal/flip animation plays), followed by a small dismissible banner ("Couldn't restore your last game — dealt a new one") appearing only after the deal settles. **No crash, no blank screen, no infinite spinner.**
- Regression check: Repeat with an empty tableau array specifically (since that's the shape the crashing test was exercising) — deal a game, quit immediately after the very first move so as little state as possible is saved, then corrupt/truncate and relaunch.
- **This is a release blocker if it crashes.** Do not treat "VERIFIED" build status as evidence this path works — it is specifically the one path proven not to have run.

## 1. Cold launch & first three seconds

**QA-001 — Fresh install, first launch**
- Steps: Fresh install, launch.
- Expected: App opens directly into the game board — no menu/title screen, no loading spinner. Cards deal with individual per-card spring arcs (not a uniform cascade), each lands with a slight overshoot-and-settle, then face-up cards perform a genuine two-sided flip (never a cross-dissolve).
- Regression: This animation must look and feel premium — this is the one unhideable, unskippable moment in the whole app (no menu screen to hide behind). Watch specifically for dropped frames, cards popping into place instead of animating, or a flip that looks like an opacity fade.

**QA-002 — Resume on relaunch (no replay)**
- Steps: Play a few moves, force-quit the app cleanly (not mid-drag), relaunch.
- Expected: The board resumes exactly where it left off — tableau, undo count, elapsed timer all match pre-kill state. **The deal/flip animation does NOT replay.**
- Regression: This is a named flow (`resume-in-progress-without-replay`) — a replay here is a hard fail.

**QA-003 — New Game / draw-mode change deal**
- Steps: Tap New Game (or change draw mode) mid-session.
- Expected: Confirmation dialog appears if a game is in progress; confirming triggers a fresh deal/flip animation identical in quality to first launch.

## 3. Core interaction: tap-to-move

**QA-010 — Single-card legal move (one destination)**
- Steps: Tap a card with exactly one legal destination (e.g., an Ace to an empty foundation).
- Expected: Move executes immediately with a spring-physics transit animation (lift, travel, settle) — not a flat teleport or linear slide. Haptic feedback fires.

**QA-011 — Single-card move (multiple legal destinations)**
- Steps: Tap a card that could legally go to more than one tableau column.
- Expected: All legal destinations highlight; a second tap on a destination confirms the move there. No auto-pick of one destination without the highlight step.

**QA-012 — Blocked move**
- Steps: Tap a card, then tap an illegal destination (wrong color/rank sequence, non-King into empty column).
- Expected: Card does not move; a lateral shake (~8–12pt, one cycle) plus a rigid impact haptic fires. **Must not** be the heavier notification-style haptic (that's reserved for win/stuck only).

**QA-013 — Multi-card run relocation**
- Steps: Build a tableau run of 3+ alternating-color descending cards (e.g., black 7, red 6, black 5 stacked face-up). Tap the top (highest) card of that run.
- Expected: The entire run moves together as one coherent unit to a legal destination — no card-by-card animation, no flicker, no momentary wrong z-order.
- Regression: This was called out repeatedly as a real implementation risk distinct from single-card moves — test it deliberately, don't assume it "just works" because single-card taps do.

**QA-014 — Stock draw and cycling**
- Steps: Draw through the entire stock in both Draw-1 and Draw-3 (separately), let it exhaust, and tap to recycle waste back into stock.
- Expected: Unlimited redeal — stock cycles indefinitely, no artificial cap.

## 4. Terminal states (test both draw modes separately)

**QA-020 — True win**
- Steps: Play (or engineer) a game to completion — all four foundations built up through King.
- Expected: `WinOverlay` appears immediately with a success-tier haptic (notification-style `.success`) and any recorded time. This must not be silently absent — foundations quietly filling up with no acknowledgment is a fail.

**QA-021 — Stuck board, Draw-1**
- Steps: Play (or construct) a Draw-1 board with genuinely zero legal moves anywhere (stock, waste, tableau, foundations).
- Expected: `StuckOverlay` appears with a warning-tier haptic. Draw-1's detector is supposed to be an **exact** static pass — a false stuck-report here (declaring stuck while a legal move actually exists) is a hard fail.

**QA-022 — Stuck board, Draw-3 (never-false-positive check)**
- Steps: This is the adversarial case: try to construct or grind toward a Draw-3 board where a legal move is buried deep in the stock (only reachable after cycling through several draws), and confirm the app does **not** show `StuckOverlay` while that move is still technically reachable.
- Expected: Draw-3's stuck detector is a documented conservative approximation, deliberately biased to under-report stuck rather than over-report it. A false "you're stuck" here is the single most trust-damaging bug this app could ship (per the product brief's own framing) — treat any Draw-3 false-stuck sighting as a release blocker, not a nice-to-have fix.

## 5. Undo

**QA-030 — Multi-step undo**
- Steps: Make 5+ moves (mix of single-card and run moves and at least one stock draw), then undo repeatedly back to the start.
- Expected: Each undo restores the exact prior state (board, waste, undo count) — no drift, no skipped steps, no crash at the bottom of the stack (attempting to undo past the start should simply do nothing, not crash).

**QA-031 — Undo survives backgrounding**
- Steps: Make several moves, background the app for 30+ seconds (long enough to risk a jetsam kill on a real device), foreground it.
- Expected: Undo history is still intact, not reset to empty.

## 6. Persistence & lifecycle

**QA-040 — Timer freeze-before-flush ordering**
- Steps: Start a game with the timer on, let it run for a measured ~10 seconds, background the app, wait a further measured 30 seconds, foreground it.
- Expected: Elapsed time reflects only the ~10 seconds of active play, **not** the 30 seconds spent backgrounded. If the recorded time includes backgrounded time, that's a data-integrity bug (locked ordering: timer must freeze before the persistence flush fires).

**QA-041 — Mid-drag/mid-flip kill safety**
- Steps: Force-quit the app at the exact moment a card is mid-transit (tap a move and immediately background/kill the app).
- Expected: On relaunch, the board reflects a clean, settled logical state (card either fully at its new destination or the move never happened) — never a card frozen mid-air or duplicated.

## 8. Stats

**QA-060 — Fresh-install empty state, per mode**
- Steps: On a brand-new install, before playing any game, open Stats. Check both Draw-1 and Draw-3 tabs/filters.
- Expected: A genuine, on-brand "no games played yet" empty state per mode — never a blank screen, never "0" that could be mistaken for data loss, never the other mode's numbers bleeding through.

**QA-062 — Per-mode isolation**
- Steps: Play and win a few games in Draw-1 only, then check Draw-3's stats.
- Expected: Draw-3 still shows its own honest empty/low state — Draw-1 activity must not leak into Draw-3's numbers.

**QA-063 — gameStarted fires only on fresh deals**
- Steps: Note "games played" count, relaunch the app several times without ever tapping New Game (just resuming the same in-progress game each time).
- Expected: Games-played count does **not** increment on mere relaunch/resume — only on an actual fresh deal (first install or explicit New Game/draw-mode-confirm).

## 9. Accessibility

# Solitaire Atelier — Manual QA Checklist

**Prerequisites:** Run this on a real device or simulator with iOS 17+. Test the full pass in both Light and Dark mode, and repeat the gameplay core (QA-010 through QA-040) in both Draw-1 and Draw-3 modes. A clean install (delete app, reinstall) is required before QA-001.

---

## 0. Pre-flight: known crash risk (test this first)

**QA-000 — Corrupt-save / restore-path crash probe**
The build's own test suite crashed here (`AppRestoreCoordinatorTests.swift:54`, force-unwrap on an empty/nil `[Card]`) before it could finish running — meaning this exact code path has never been exercised end-to-end by anything, human or automated.
- Steps: (a) Start a game, make a few moves. (b) Force-quit the app. (c) Locate `GameSave.json` in the app's Application Support container (via Xcode's device file browser or simulator container path) and either delete it or corrupt it (truncate the file, or edit one card's suit field to garbage). (d) Relaunch.
- Expected: App launches into a **fresh deal** (the full deal/flip animation plays), followed by a small dismissible banner ("Couldn't restore your last game — dealt a new one") appearing only after the deal settles. **No crash, no blank screen, no infinite spinner.**
- Regression check: Repeat with an empty tableau array specifically (since that's the shape the crashing test was exercising) — deal a game, quit immediately after the very first move so as little state as possible is saved, then corrupt/truncate and relaunch.
- **This is a release blocker if it crashes.** Do not treat "VERIFIED" build status as evidence this path works — it is specifically the one path proven not to have run.

## 1. Cold launch & first three seconds

**QA-001 — Fresh install, first launch**
- Steps: Fresh install, launch.
- Expected: App opens directly into the game board — no menu/title screen, no loading spinner. Cards deal with individual per-card spring arcs (not a uniform cascade), each lands with a slight overshoot-and-settle, then face-up cards perform a genuine two-sided flip (never a cross-dissolve).
- Regression: This animation must look and feel premium — this is the one unhideable, unskippable moment in the whole app (no menu screen to hide behind). Watch specifically for dropped frames, cards popping into place instead of animating, or a flip that looks like an opacity fade.

**QA-002 — Resume on relaunch (no replay)**
- Steps: Play a few moves, force-quit the app cleanly (not mid-drag), relaunch.
- Expected: The board resumes exactly where it left off — tableau, undo count, elapsed timer all match pre-kill state. **The deal/flip animation does NOT replay.**
- Regression: This is a named flow (`resume-in-progress-without-replay`) — a replay here is a hard fail.

**QA-003 — New Game / draw-mode change deal**
- Steps: Tap New Game (or change draw mode) mid-session.
- Expected: Confirmation dialog appears if a game is in progress; confirming triggers a fresh deal/flip animation identical in quality to first launch.

## 2. Card visual system / legibility gate (never verified before this phase)

**QA-004 — Rank/suit glyph legibility at true size**
- Steps: At default Dynamic Type size, look at every rank (A, 2–10, J, Q, K) across all 4 suits on the actual tableau (not zoomed). If `CardGalleryDebugView` is reachable via a debug menu/scheme, open it instead for a full 52-card grid at the real computed `cardWidth()`.
- Expected: Every rank/suit is unambiguous at a glance — no rank could be confused for another, no suit could be confused for another, even briefly.
- Regression: Repeat with Dynamic Type set to **Accessibility1** (Settings > Accessibility > Display & Text Size > Larger Text > drag to max, or the largest accessibility size). This is the actual locked release gate — a FAIL here is expected to trigger a pre-approved bounded fallback (flatten the corner-index/pip zone to solid ink with a larger, bolder index), not a full redesign. Record PASS/FAIL explicitly; do not let this slide as "looks fine to me."

**QA-005 — Card stock / lighting art direction**
- Steps: Compare Light mode (should read as daylight through a window — cooler, brighter felt, grey pewter) against Dark mode (should read as a desk lamp at night — warmer, saturated green pooling toward near-black at the edges, warm dim pewter).
- Expected: These read as two genuinely different lighting scenes, not an inverted color palette. Card face/ink color should look identical in both modes (by design — only the table/shadow/hardware differ).
- Regression: If dark mode looks like light mode with colors flipped, that's a fail against a named, locked decision.

**QA-006 — Card back selection**
- Steps: In Settings, switch between the two card backs.
- Expected: Exactly two visually distinct backs exist, both selectable, change applies live with no confirmation and no need to start a new game.

## 3. Core interaction: tap-to-move

**QA-010 — Single-card legal move (one destination)**
- Steps: Tap a card with exactly one legal destination (e.g., an Ace to an empty foundation).
- Expected: Move executes immediately with a spring-physics transit animation (lift, travel, settle) — not a flat teleport or linear slide. Haptic feedback fires.

**QA-011 — Single-card move (multiple legal destinations)**
- Steps: Tap a card that could legally go to more than one tableau column.
- Expected: All legal destinations highlight; a second tap on a destination confirms the move there. No auto-pick of one destination without the highlight step.

**QA-012 — Blocked move**
- Steps: Tap a card, then tap an illegal destination (wrong color/rank sequence, non-King into empty column).
- Expected: Card does not move; a lateral shake (~8–12pt, one cycle) plus a rigid impact haptic fires. **Must not** be the heavier notification-style haptic (that's reserved for win/stuck only).

**QA-013 — Multi-card run relocation**
- Steps: Build a tableau run of 3+ alternating-color descending cards (e.g., black 7, red 6, black 5 stacked face-up). Tap the top (highest) card of that run.
- Expected: The entire run moves together as one coherent unit to a legal destination — no card-by-card animation, no flicker, no momentary wrong z-order.
- Regression: This was called out repeatedly as a real implementation risk distinct from single-card moves — test it deliberately, don't assume it "just works" because single-card taps do.

**QA-014 — Stock draw and cycling**
- Steps: Draw through the entire stock in both Draw-1 and Draw-3 (separately), let it exhaust, and tap to recycle waste back into stock.
- Expected: Unlimited redeal — stock cycles indefinitely, no artificial cap.

---

## 4. Terminal states (test both draw modes separately)

**QA-020 — True win**
- Steps: Play (or engineer) a game to completion — all four foundations built up through King.
- Expected: `WinOverlay` appears immediately with a success-tier haptic (notification-style `.success`) and any recorded time. This must not be silently absent — foundations quietly filling up with no acknowledgment is a fail.

**QA-021 — Stuck board, Draw-1**
- Steps: Play (or construct) a Draw-1 board with genuinely zero legal moves anywhere (stock, waste, tableau, foundations).
- Expected: `StuckOverlay` appears with a warning-tier haptic. Draw-1's detector is supposed to be an **exact** static pass — a false stuck-report here (declaring stuck while a legal move actually exists) is a hard fail.

**QA-022 — Stuck board, Draw-3 (never-false-positive check)**
- Steps: This is the adversarial case: try to construct or grind toward a Draw-3 board where a legal move is buried deep in the stock (only reachable after cycling through several draws), and confirm the app does **not** show `StuckOverlay` while that move is still technically reachable.
- Expected: Draw-3's stuck detector is a documented conservative approximation, deliberately biased to under-report stuck rather than over-report it. A false "you're stuck" here is the single most trust-damaging bug this app could ship (per the product brief's own framing) — treat any Draw-3 false-stuck sighting as a release blocker, not a nice-to-have fix.

## 5. Undo

**QA-030 — Multi-step undo**
- Steps: Make 5+ moves (mix of single-card and run moves and at least one stock draw), then undo repeatedly back to the start.
- Expected: Each undo restores the exact prior state (board, waste, undo count) — no drift, no skipped steps, no crash at the bottom of the stack (attempting to undo past the start should simply do nothing, not crash).

**QA-031 — Undo survives backgrounding**
- Steps: Make several moves, background the app for 30+ seconds (long enough to risk a jetsam kill on a real device), foreground it.
- Expected: Undo history is still intact, not reset to empty.

## 6. Persistence & lifecycle

**QA-040 — Timer freeze-before-flush ordering**
- Steps: Start a game with the timer on, let it run for a measured ~10 seconds, background the app, wait a further measured 30 seconds, foreground it.
- Expected: Elapsed time reflects only the ~10 seconds of active play, **not** the 30 seconds spent backgrounded. If the recorded time includes backgrounded time, that's a data-integrity bug (locked ordering: timer must freeze before the persistence flush fires).

**QA-041 — Mid-drag/mid-flip kill safety**
- Steps: Force-quit the app at the exact moment a card is mid-transit (tap a move and immediately background/kill the app).
- Expected: On relaunch, the board reflects a clean, settled logical state (card either fully at its new destination or the move never happened) — never a card frozen mid-air or duplicated.

## 7. Settings

**QA-050 — Draw-mode change: confirm path**
- Steps: Mid-game, switch draw mode in Settings, confirm the dialog.
- Expected: Current game is discarded, a fresh deal starts in the new mode (with the real deal/flip animation).

**QA-051 — Draw-mode change: cancel path**
- Steps: Mid-game, switch draw mode in Settings, then cancel the dialog.
- Expected: **Both** the in-progress game and the draw-mode setting remain completely unchanged — deliberately try to catch a "cancel silently applied it anyway" bug here.

**QA-052 — Timer toggle**
- Steps: Turn timer off mid-session, then check Stats for that game.
- Expected: Stats shows "N/A" for best time when timer is off — never a fabricated or stale numeric value.

**QA-053 — Card back live switch**
- Steps: Change card back while a game is in progress.
- Expected: Applies instantly, no confirmation prompt, no new-game requirement (unlike draw mode).

## 8. Stats

**QA-060 — Fresh-install empty state, per mode**
- Steps: On a brand-new install, before playing any game, open Stats. Check both Draw-1 and Draw-3 tabs/filters.
- Expected: A genuine, on-brand "no games played yet" empty state per mode — never a blank screen, never "0" that could be mistaken for data loss, never the other mode's numbers bleeding through.

**QA-061 — Data-loss state is visually distinct from empty state**
- Steps: Corrupt `StatsLog.json` directly (truncate or garbage-edit it), relaunch, open Stats.
- Expected: A **structurally different** state from QA-060 — different icon, explicit "data was lost" copy (not just "no games"), and a working "Reset local stats and continue" action. These two states must never be confusable at a glance.

**QA-062 — Per-mode isolation**
- Steps: Play and win a few games in Draw-1 only, then check Draw-3's stats.
- Expected: Draw-3 still shows its own honest empty/low state — Draw-1 activity must not leak into Draw-3's numbers.

**QA-063 — gameStarted fires only on fresh deals**
- Steps: Note "games played" count, relaunch the app several times without ever tapping New Game (just resuming the same in-progress game each time).
- Expected: Games-played count does **not** increment on mere relaunch/resume — only on an actual fresh deal (first install or explicit New Game/draw-mode-confirm).

## 9. Accessibility

**QA-070 — VoiceOver card labels**
- Steps: Enable VoiceOver, swipe through the board.
- Expected: Each card announces something concrete like "Seven of Hearts, tableau column 3, face up" — not "image," not silence, not a generic label.

**QA-071 — VoiceOver ambiguous-destination actions**
- Steps: With VoiceOver on, select a card that has multiple legal destinations.
- Expected: Each legal destination is exposed as a **separate VoiceOver action** (not just a visual highlight sighted users get) — a VoiceOver-only user must be able to choose among them non-visually.

**QA-072 — Reduce Motion**
- Steps: Enable Reduce Motion in system settings, then trigger a deal, a flip, and a move-transit.
- Expected: All three become an identical, simple ~150ms linear opacity fade to final position — no positional translate, no per-card stagger, no spring/overshoot.

**QA-073 — Suit distinguishability without color**
- Steps: Use a grayscale/colorblind filter (Settings > Accessibility > Display & Text Size > Color Filters, or Smart Invert) and check suit identification.
- Expected: Suits remain distinguishable by shape/glyph alone, not just color.

**QA-074 — Dynamic Type / accessibility text sizes**
- Steps: Max out Dynamic Type (Accessibility1+) across Settings and Stats screens.
- Expected: No text clipping, no overlapping labels/values, no truncation that loses meaning.

## 10. Known gaps (explicitly not silently omitted)

- **Test suite has never successfully executed.** The build compiles cleanly, but the actual `xcodebuild test` run crashed partway through (`AppRestoreCoordinatorTests.swift:54`, force-unwrap on `[Card]`). This means the fuzz/invariant suite (52-unique-cards, foundation monotonicity, no-false-stuck) and the hand-built Draw-3 adversarial fixture have **compiled but never run** — QA-000 and QA-022 above are the human backstop for exactly this gap.
- **Card-glyph legibility (QA-004) has never been judged by anyone with simulator/eyes access before this phase** — this is the first real opportunity to close out a risk flagged in nearly every phase since `product_research`.
- **Live interactive drag and win-screen sharing are intentionally absent from this build** (explicitly cut in `app_features`/`per_app_product_brief`) — do not test for these as missing features; tap-to-move (including run relocation) is the only interaction model in scope.
- **No accounts, network, or cloud sync exist by design** — do not test for iCloud/cross-device behavior; a reinstall is expected to wipe local stats/settings, and Settings should disclose this.
