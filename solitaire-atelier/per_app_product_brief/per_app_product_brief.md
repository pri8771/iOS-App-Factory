`solitaire-atelier` exists to be the offline Klondike app people can trust for 5–15 minute sessions: deterministic rules, fast recovery, and visual quality that feels hand-built instead of generic template Solitaire.

The paid value is not features that can be faked with cosmetic overlays; it is utility and confidence. Users pay (whether through a direct purchase decision or retention preference) for three things: guaranteed correctness of move logic and state, zero-friction local continuity, and a card system that stays legible and tactile at actual tablet-width gameplay size. The core loop is: on launch, go straight to active game state (or a fresh deal if no active game exists); show current tableau/foundation/waste/stock; allow tap-to-move or drag with immediate valid/invalid feedback and haptics on accepted/rejected actions; draw/recycle from stock according to current draw mode; place, continue, undo inline whenever needed; persist every meaningful action; detect and present two terminal states clearly (true win and no legal moves); and transition to New Game with stats/streak updates and state reset by design. There is no separate “playbook” screen and no onboarding gate before this loop.

Its competitive wedge is not just “another Solitaire,” because almost all competitors optimize for either one extreme (classic utilitarian) or the other (flashy but shallow). Here the wedge is the combination: strict Klondike rules locked to the canonical model, full state integrity on relaunch, and an intentionally authored physical card language with a distinctive reveal animation signature that is visible on first frame and still keeps gameplay fast. The growth mechanism is niche and viral by composition, not by social feed dependence: people share solved-streak screenshots and seed-based challenge codes locally (Messages, Notes, QR, or copy/paste) because deck behavior is deterministic, so friends can replay the exact board and compare results. Local-first behavior is the backbone: all gameplay state, settings, and stats live on-device in local persistence, with save state written only from settled logical state so a background kill mid-animation never corrupts the resumed board. Draw mode is session-consistent; changing it requires new game flow by design. Timer handling is session-local and pause-aware, and stats are split per draw mode so metrics stay honest. Light and dark are fully themed via one theme system, no hardcoded style literals, no placeholders, and both appearances are complete from launch.

Cloud-ready extension path is a clear interface layer, not a new source of truth for v1: define a transport-agnostic persistence protocol now (local store for v1), then add optional adapters later for encrypted device backup and cross-device restore, keeping the on-device model as the source-of-truth schema so nothing in gameplay depends on connectivity. What this should make users keep is the certainty that every session remains coherent and beautiful from first card dealt to game end, even after interruptions, with no account friction, no privacy cost, and no “looks right but plays wrong” traps.

The biggest objection to this direction is that forbidding all monetization and network features removes easy growth levers and recurring revenue narratives, which can make product messaging feel less obvious. The non-negotiable detail to preserve in final output is that that constraint is itself part of the value proposition: trust and permanence first, no external dependency. The success of this app must be measured on correct gameplay, interruption-safe persistence, and premium tactile clarity, not on social features or monetization shortcuts.

**Claude (QA & Risk · Closer) — Round 2**

Let me push back on my own round-1 position because Codex's challenge-seed idea deserves a real hearing, not a dismissal — but I still land somewhere different from where Codex put it.

Codex's instinct is right that "someone screenshots it unprompted" is a passive bet, and passive bets are how growth mechanisms quietly become "we hoped." I was too conservative saying zero feature surface — if the entire growth story rests on screenshots, the app should at least make screenshotting/sharing frictionless at the exact moment someone's most likely to want to, which is the win screen. So I'm updating: some kind of native share affordance on win belongs in this brief. But the specific mechanism Codex proposed — a challenge seed that reproduces the identical deal for a friend to replay — I think is the wrong shape for what this app can actually afford to build safely, and I want to walk through why concretely rather than just asserting it.

A shareable seed only works if the shuffle is genuinely reproducible from that seed, on a different device, possibly a different iOS version, possibly a different Swift runtime. `SystemRandomNumberGenerator` is explicitly not a documented, versioned algorithm — Apple doesn't guarantee it produces the same output from the same seed across OS versions, because it's backed by the system CSPRNG, not a deterministic PRNG. So "seeded replay" as a feature actually requires standing up a second, hand-rolled deterministic RNG (something like a splitmix64 or PCG implementation) that lives entirely separately from the real-shuffle path used for every actual game. That's not a small add — it's a second RNG implementation, a second Fisher-Yates path, and now two things that both claim to produce "a valid shuffled Klondike deal" that have to be kept in sync forever, tested separately, and verified to never leak into each other. DEC-prompt_contract-011 already locks "fresh real-RNG shuffle every new game" as a correctness requirement with automated-reject teeth — the moment there are two shuffle code paths in the codebase, any verification pass has to prove the real-play path never accidentally takes the deterministic one, which is exactly the kind of subtle state-machine bug this fleet has shipped before. And per the ordering rule we all just agreed on in round 1 — correctness work is never the thing that gets cut, visual polish is — building a second RNG system to support a growth feature is spending correctness-tier engineering budget on a feature that is, honestly, unproven.
