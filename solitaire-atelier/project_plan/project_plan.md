**Claude (Backend / Systems Engineer · Skeptic) — Round 1**

Coming at this from the systems/persistence side, and I want to push back on a few things that have been treated as settled in the interfaces-json but aren't actually de-risked yet.

The biggest one: nobody has actually pinned down how `GameState.piles: [PileID: [Card]]` round-trips through Codable, and I think that's a landmine. `PileID` is an enum with associated values (`.foundation(Suit)`, `.tableau(Int)`), not `String` or `Int`. Swift's synthesized `Codable` for `Dictionary` only uses a keyed container when the key type is `String`/`Int`-backed — otherwise it falls back to encoding as a flat alternating array of keys and values in an unkeyed container. That's not wrong, exactly, but it means: the JSON isn't human-inspectable for QA/debugging (which we're going to want when a corrupt-save fixture doesn't decode the way we expect), dictionary iteration order isn't guaranteed stable, and every place that has to iterate "all piles" for `RestoreIntegrityService`'s semantic checks needs to not accidentally depend on ordering. I'd rather we settle this in the very first domain milestone with an actual round-trip unit test than discover it three phases into the persistence work. Honestly I'd push for replacing the dictionary with a struct that has named fields (`stock`, `waste`, `foundations: [Suit: [Card]]`, `tableau: [[Card]]`) — foundations still benefits from Suit-keying, but stock/waste/tableau don't need to be inside a PileID-keyed dictionary at all, and the semantic validator gets simpler, enumerable fields instead of having to defensively iterate a dictionary and hope nothing's missing.

Second: the timer-pause-then-flush ordering on backgrounding. We've locked "timer pauses on background" and separately locked "unconditional flush on scenePhase background," but nobody has sequenced which happens first. If flush fires before the timer freezes `elapsedSeconds`, or if they race, we persist a slightly-wrong elapsed time — small, but it's exactly the kind of "app lied about the player's own data" bug this whole pipeline has been paranoid about avoiding. This needs to be an explicit ordering requirement in the build plan, not just two independently-true decisions that happen to touch the same lifecycle event.

Third, on sequencing: I think the plan needs to treat the card-glyph legibility gate as blocking, not just "existing." If `CardGalleryDebugView` gets built in week 5 after `GameView`, `DealOrchestrator`, and half the interaction layer are already wired against specific glyph shapes and a specific `cardWidth` formula, and legibility fails at accessibility1 Dynamic Type, we're not tweaking a `Shape` — we're re-touching every view that assumes those proportions. The design-system milestone (Theme tokens + CardGlyphs + CardView + the gallery) has to close with a real accessibility1-scale legibility pass before gameplay UI construction starts consuming it.

Fourth, I want to flag the undo-stack-inside-GameSaveFile choice honestly rather than assume it's free: every debounced save now serializes up to 200 full-state snapshots, not just current state. At single-deck-52-card scale that's maybe 100-200KB of JSON per write, which is fine for flash I/O but not exactly "free" if someone later tries to lower the debounce window for responsiveness — worth a note so nobody "optimizes" the debounce down and reintroduces I/O jank during the exact spring animations we built `DealOrchestrator` to protect.

Fifth on verification: draw-3's "never falsely reports stuck" claim is a released product promise, not a nice-to-have test. That needs actual hand-constructed adversarial fixtures — boards designed to have exactly one legal move buried in a specific stock-cycle position — not just randomized fuzzing, because random fuzzing is much more likely to hit "obviously many legal moves" or "obviously zero cards left" than "exactly one move, buried." Randomized fuzz is necessary but not sufficient for that specific guarantee.

Sequencing-wise, my instinct is: guardrails/scaffolding first (CI dependency-lint gate, module layout, themed LaunchScreen) before any feature code, then domain+persistence fully unit/fuzz-tested with zero UI, then design-system-with-legibility-gate, then gameplay UI, then Stats/Settings/TabView shell, then a dedicated cross-cutting hardening pass for backgrounding/timer/save-ordering and accessibility audit, then a real verification-and-repair milestone that isn't just "run the tests once" but budgets time to actually fix what they find.
