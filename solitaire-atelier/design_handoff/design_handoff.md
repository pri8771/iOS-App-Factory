**Claude (Frontend Engineer · Systems Thinker) — Round 1**

Let me put down the concrete numbers and the systems-level shape before anyone else anchors the room.

Screens are exactly the three tabs already locked — Game, Stats, Settings — in a plain `TabView` with no `NavigationStack` wrapping any of them, because none of the three ever need drill-down (Stats' draw-1/draw-3 toggle is a segmented control, not a push). That matters for state ownership: I want a single `GameEngine` (an `@Observable` class, iOS 17+, holding board state, undo stack, timer, terminal-state flags) instantiated once at the App root and handed down via environment, not recreated per tab — Game reads/writes it directly, Stats reads from a separate append-only event log the engine writes to on game start/end (already decided to exist from day one), Settings reads/writes its own small struct. Three separate persisted files, not one combined blob: `GameSave.json`, `StatsLog.json`, `Settings.json` in Application Support / UserDefaults respectively. This is a deliberate reliability choice, not just tidiness — design_discussion locked that Game, Stats, and Settings each fail and recover independently (a corrupt game save shouldn't ever take Stats down with it), and that only actually holds if they're physically separate files with independent atomic-write-temp-then-swap operations. If we let one engineer "simplify" this into a single AppState.json down the line, we silently reintroduce a single point of failure that contradicts an already-locked decision — the spec needs to say this explicitly so it isn't rediscovered as a bug.

One thing I don't think either the design_discussion or earlier phases said out loud, and I want it locked here: the card face itself — ink color for rank/suit glyphs, vellum stock tone — should be constant across light and dark mode. Only the table felt, ambient shadow, and pewter hardware shift between the daylight and lamp-only scenes. A physical card doesn't change ink color when the room light changes; if we let the semantic color system apply a `cardInk` light/dark swap the way it does for `textPrimary`, we'll get an uncanny "the card itself re-tinted" effect that breaks the one metaphor this whole design language is built on, and it also protects us against a real risk: if dark mode's glyph ink gets remapped for "proper" dark-mode contrast, it could interact badly with the legibility gate that's already the single riskiest unresolved item in this pipeline. So in the theme, `cardGlyphInkBlack` / `cardGlyphInkRed` / `cardStockVellum` are NOT semantic light/dark pairs — they're fixed constants, and only `tableFelt`, `tableShadow`, `chromeBackground`, `pewter`, `textPrimary/Secondary` get light/dark pairs. I'd rather this be a named rule in the spec than an implicit assumption a builder has to reverse-engineer.

Concrete tokens: spacing base unit 4pt, steps xs 4 / sm 8 / md 16 / lg 24 / xl 32 / xxl 48. Corner radii: cardRadius 6pt (cards should look cut, not app-icon-rounded — this is a real tell that separates "real card" from "SwiftUI rounded rectangle"), sheetRadius 20pt, controlRadius 10pt. Type scale mapped to Dynamic Type so nothing is a bare fixed number in the view layer: screenTitle 28/Semibold→`.title`, sectionHeader 20/Semibold→`.headline`, body 17/Regular→`.body`, caption 13/Regular→`.caption`, statNumber 34/Bold rendered as a fixed-width tabular numeral style so stat digits don't jump the layout as they update. Colors, semantic roles, light/dark hex: `tableFeltTop` #3A6E52 / #123321, `tableFeltShadowed` #245039 / #081C12, `chromeBackground` #EDE7D8 / #1B1712, `textPrimary` #201D18 / #F0E9D8, `textSecondary` #6B6656 / #A79D87, `pewter` #9296998C-ish flat #8D9093 / #5E5C58, `accentSuccess` #2E7D4E / #4FB27B, `accentWarning` (recovery banners, data-loss state) #A6472C / #D97C55. Card constants regardless of scheme: `cardStockVellum` #F5EFDF, `cardGlyphInkBlack` #221E17, `cardGlyphInkRed` #8A2A22, `cardBackPewterSeam` #8D9093.

Components, named so the builder isn't inventing structure mid-build: `FeltBackgroundView` (renders the active lighting scene as a pre-baked gradient + directional shadow, computed once per `colorScheme` change and cached — not recomputed per frame, because this sits behind every drag/deal animation and recalculating a radial gradient at 120Hz during a spring animation is a real perf trap), `CardView` (face-up/face-down/selected/legalDestination/blocked visual states, glyph rendered as a `Shape`-based path system so it scales crisply instead of being a rasterized image, embossing done via a fixed two-layer highlight/shadow offset baked into the shape, not a live-computed 3D light), `PileSlotView` (the empty-pile outline that must always render so an empty foundation or emptied tableau column never collapses the layout — this is an easy miss: a tableau column with zero cards still needs a visible drop target), `DealOrchestrator` (a non-visual sequencer object driving the per-card spring timing, the only place that owns "is this a fresh deal or a resume" logic, and the only place that branches for Reduce Motion — I want Reduce Motion defined precisely as "cards appear in final position via a single 150ms opacity fade, no spring, no per-card stagger," not just "shorter," because "shorter but still spring" is what the last few Reduce Motion implementations in this fleet have quietly shipped and it doesn't satisfy the setting's intent), `ConfirmationSheet` (shared by New Game and draw-mode switch, deliberately NOT a system `.confirmationDialog` — I'm breaking from "prefer system controls" here on purpose, because a system action sheet can't carry the felt/vellum material language and design_discussion explicitly rejected system chrome; it still has to behave like one accessibility-wise: default focus on Cancel, VoiceOver announces the destructive framing, dismiss via swipe or explicit Cancel), `RecoveryBanner`, `WinOverlay`, `StuckOverlay`, `StatsSegmentedHeader`, `StatCard`, `EmptyStateView`, `DataLossStateView` (visually distinct per DEC-design_discussion-005 — different icon family, warm-warning tint, not felt-green), `SettingsRow`, `CardBackPicker` (live preview, applies instantly), `ToastView`.

Motion and haptics, concretely: card lift-on-select uses `UIImpactFeedbackGenerator(.light)`, a legal move settling uses `.medium`, a blocked-move rejection uses `UINotificationFeedbackGenerator.error` paired with a short lateral shake (8pt, 2 cycles, 120ms) on the card, win fires `UINotificationFeedbackGenerator.success` once foundations complete. Generators should be instantiated once and kept warm (`.prepare()` called on card selection, before the actual move resolves) rather than created fresh per call — recreating them per tap adds a perceptible ~30-50ms latency spike on first use, which is exactly the kind of thing that reads as "janky" in a tactile app. Deal/flip spring: response 0.45, damping 0.72 per card, staggered start offset ~18ms between cards so the cascade reads as sequential release rather than simultaneous; flip itself is a 3D rotation on Y axis, 0.32s, easeInOut, with the face swapped at the 50% rotation point (not a cross-dissolve).

Accessibility: every `CardView` gets an explicit accessibility label built from a template ("Seven of Hearts, tableau column 3, face up"), suit shown via a distinct pip silhouette family per suit (not just color) so VoiceOver-off colorblind users get the same non-color cue sighted users do, multi-destination taps expose each legal destination as a discrete accessibility action rather than relying on a sighted-only highlight-then-tap, and Reduce Motion is checked once per session (not per animation call site) via an environment value threaded through `DealOrchestrator` and the per-move transit animation.

On external design: given the spec above already pins every numeric value a SwiftUI builder needs, I don't think we need a full external design pass — but I'd make one narrow exception. The rank/suit glyph legibility gate at true ~46pt card width has been flagged as unresolved since product_research and nobody has actually looked at it yet. I'd rather we generate a handful of static reference images of one full tableau column at true device point size (not zoomed mockups) — either through Claude Design or just a throwaway SwiftUI preview rendered to actual scale — and eyeball it before locking the glyph shapes in code, because if it fails at true size we want to know before 52 cards' worth of `Shape` paths get built around a losing design, not after.

**DESIGN SPEC — Component Inventory**

Persistence architecture: three independently-persisted files — `GameSave.json`, `StatsLog.json`, `Settings.json` — each with its own atomic temp-then-swap write, so a corrupt game save can never take Stats or Settings down with it. A single `GameEngine` (`@Observable`) owns Game state; Stats reads from an append-only local event log the engine writes on game start/end; Settings owns its own small struct.

**DESIGN SPEC — Navigation**

Root is one `TabView`, three peer tabs — Game (default/launch), Stats, Settings — no `NavigationStack`, no menu/onboarding screen. Cold launch: attempt restore once at boot; if it succeeds with an active board, show it immediately; if it fails/is corrupt, run a fresh deal exactly as on first install, then layer a small dismissible `RecoveryBanner` after the deal settles ("Couldn't restore your last game — dealt a new one") — never a blocking modal before the first board frame. `DrawModeConfirmSheet` is the one shared component for both New Game and mid-game draw-mode switches. A single app-level `hasFinishedInitialLoad` flag (set once after Game/Stats/Settings all restore together at cold start) gates first paint on all three tabs — no independent per-tab loading state, since there's no real async gap once that one restore completes.

**DESIGN SPEC — Screen States**

*Game:* `restoring` (brief, boot-only) → `active` (source-selected / ambiguous-destination-with-VoiceOver-actions / blocked-feedback sub-states, run-relocation via head-card tap) → `moveExecuting`/`undoing` (spring transit) → `win` / `stuck` terminal overlays, each with distinct iconography and CTAs (`New Game`+`Return to board` for win; `New Game`+`Continue` for stuck) → `pendingConfirmation`. Recovery is the fresh-deal-plus-banner pattern above, never a modal.
*Stats (per draw mode):* `neverPlayed` (inviting icon, "No games played in Draw One yet, deal one to start your streak"), `populated` (games played/won, best time or "N/A" when timer off, streak), `dataLossError` (structurally distinct icon/tone, "Stats data unavailable after a local restore error," action "Reset local stats and continue") — never visually confusable with `neverPlayed`.
*Settings:* `ready` (draw mode, card-back, timer, local-data disclosure line), draw-mode change opens `DrawModeConfirmSheet` only if a game is active, card-back applies instantly, persistence-fallback shows a lightweight `ErrorToast` with controls staying usable — never a silent fake default.

**DESIGN SPEC — Motion & Haptics**

Fresh deal only (never on resumed cold launch): per-card delay `0.045s + index*0.025s`, spring response ≈0.55, damping ≈0.78, slight arc with overshoot-and-settle, directional highlight catch on landing; face-up cards get a true Y-axis flip, ~0.32s easeInOut, content swapped at the midpoint — never a cross-dissolve. Tapped move (single card or full valid run): quarter-card lift + 0.28s spring settle, never a teleport. Undo reverses the same transit.

Haptics: accepted move `.medium` impact; stock draw `.light` impact; undo `.soft` impact; **blocked/rejected move `UIImpactFeedbackGenerator(.rigid)` + 8–12pt one-cycle lateral shake** (not a notification generator — Apple's own guidance is that notification feedback should stay rare because frequent use dilutes its meaning, and blocked taps happen constantly in normal play); win `UINotificationFeedbackGenerator(.success)`; stuck-board detected `UINotificationFeedbackGenerator(.warning)`; fresh-deal start, one understated notification cue only, never per-card. Generators are kept warm (`.prepare()` on selection) rather than instantiated per call, and all haptic call sites live in one shared interaction layer, not scattered through view code.

Reduce Motion (strict, no exceptions, applies identically to deal/flip/move-transit): single 150ms linear **opacity-only** fade to final position — zero translate, zero 3D, zero per-card stagger. This is stricter than "shorter spring" on purpose, since even subtle positional motion is what the setting exists to remove.

**DESIGN SPEC — Accessibility**

Every `CardView` exposes an explicit VoiceOver label ("Seven of Hearts, tableau column 3, face up"). Suit differentiation is shape-level in the glyph family itself, never color-only. When a tap resolves to multiple legal destinations, each is exposed as a discrete VoiceOver action, not just a visual highlight. Semantic reading order: top controls → stock/waste/foundations → tableau columns left-to-right. Icon-only controls carry both label and hint. Hit-testing uses padded targets beyond visual card bounds. Text/controls must never collide under Dynamic Type up through `accessibility1` — if they would, decoration is reduced first, logic and state are never hidden or shrunk to fit.

**Must / Should / Could / Won't** (restated per Codex's earlier quality-gate request)
- **Must:** Game/Stats/Settings triad, resume-first launch, draw-1/draw-3 parity, full legal-move + run-relocation + undo path, both terminal states, Theme-only styling with zero hardcoded literals, full accessibility labeling/actions, honest non-blocking persistence-failure states everywhere.
- **Should:** run one real on-device legibility pass at true card width before the glyph shapes are considered locked in code; enforce the `cardWidth` formula in every layout path, never a fixed constant.
- **Could:** further micro-tuning of felt/shadow/pewter lighting fidelity once gameplay correctness and the legibility gate are both confirmed.
- **Won't:** win-screen share sheet, live interactive drag, third-party frameworks/packages, any encrypted local persistence layer, any card-face recoloring or ambient wash tied to appearance.
