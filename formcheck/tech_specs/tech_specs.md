On the geometric rules — this is the thing the whole project is graded on, and so far every phase has described it structurally ("hip-knee-ankle angle for squat," "elbow angle for push-up") without ever writing the actual numbers. I want to lock these now: squat uses the knee angle (hip–knee–ankle, averaged across both legs when both are visible, single-leg with a confidence-weighted fallback when one side is occluded) with a standing threshold of 160° and a depth threshold of 100°; a rep completes when the angle descends below 100° and returns above 160° in the following window; if the local minimum for a rep never crosses below 100°, that rep still counts (motion was completed) but emits a formFlag naming the exact measured angle — "Squat depth: hips only reached ~128° knee bend (target: below 100°)" — not a generic warning. Push-up mirrors this on elbow angle (shoulder–elbow–wrist), standing/top at >160°, bottom depth target <90°, same flag-on-shortfall pattern naming the measured degree value. Plank is structurally different, per the already-locked hold-based metric shape: instead of a rep counter it tracks a hip alignment angle (shoulder–hip–ankle) that should sit near 180° in a straight line; the moment `abs(180° − hipAngle)` exceeds a 15° tolerance band for more than a 1-second sustained window, that duration accrues into `outOfFormSeconds` and fires exactly one flag transition (entering vs. exiting out-of-form), naming which direction it broke ("hips sagging" below the band vs. "hips piking" above it). Every one of these thresholds needs a debounce/hysteresis wrapper — I'm proposing a generic `RepStateMachine` with separate enter/exit thresholds and a minimum-consecutive-frame dwell count (3 frames) so a single noisy frame can't flip state, which is exactly the noise-robustness product_research already mandated but never made concrete.

On classification: I don't think a bundled Core ML model is honestly in scope here — there's no labeled multi-person pose-sequence training set available in this project, and fabricating one or bundling an unvalidated model would be worse than the heuristic the prompt pre-authorizes. I want to lock the heuristic explicitly now rather than leave it ambiguous into build: classify off torso orientation (shoulder-to-hip vector angle relative to vertical — near-vertical suggests squat, near-horizontal suggests push-up or plank) combined with joint-cyclicity variance over a rolling ~2-second window (squat/push-up show periodic knee/elbow angle oscillation; plank shows low variance across all joints while horizontal). This is genuinely explainable in exactly the way the product's whole pitch depends on, which is actually a strength of choosing heuristic over black-box ML, not just a fallback — and the in-app disclosure copy should say exactly this, not a vague "we use on-device analysis" line.

The single biggest risk I'd flag against my own proposal, playing red team on myself: none of the prior phases have addressed what happens when Vision returns multiple body observations in frame (a second person walking behind, a mirror reflection, a poster). `VNDetectHumanBodyPoseRequest` can return an array, and nothing in the spec so far says how we pick which one is "the user." I want to lock that now too: select the observation with the largest bounding-box area, tie-broken by average joint confidence, and treat every other observation as ignored noise — this needs to be a named, tested rule, not an implicit "we'll just take `.first`." A second gap in the same family: the finalizing state has a 400ms floor before it resolves, but if the app is force-quit during that exact window (after End is tapped, before the write completes), the reconciliation scan needs to know this is a "user already asked to end, don't just resume in-progress" case — I want the SessionStatus transition to move to `.finalizing` (not stay `.inProgress`) the instant End is tapped, so the launch-time reconciliation scan treats a `.finalizing` orphan identically to an `.inProgress` orphan (both become `.completedEndedEarly`), rather than accidentally treating a mid-finalize crash as a clean completion or a totally lost session.
