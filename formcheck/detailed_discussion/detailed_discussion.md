**Claude (QA & Risk · Skeptic) — Round 1**

Starting from what's already locked, the part I'd stress hardest is the "auto-finalize on interruption" decision (DEC-initial_discussion-004), because the decision as written assumes the app gets a chance to run finalize code. Backgrounding is one thing — `scenePhase` or a background task can catch that. But a force-quit, a crash inside the Vision pipeline, a thermal shutdown mid-plank, or the OS killing the app for memory pressure during a long recording session all skip that code path entirely. If we don't also design a recovery reconciliation on next launch — scan for any session row left in an "in-progress" state and finalize it retroactively as ended-early using whatever timestamp/rep data was already persisted incrementally — then the "History/Watch/Catalyst can never disagree about whether a session exists" guarantee is actually false for the crash case, which is exactly the failure mode priority (c) was written to rule out. This means rep counts and elapsed time need to be persisted incrementally (e.g., after each counted rep, not just at session end), not held in memory until a clean finalize — that's a concrete architectural constraint, not a nice-to-have.

Second, plank doesn't fit the rep-counting model at all, and I don't think that's been said out loud yet. Squat and push-up produce a rep count from a repeating state machine; plank is a single continuous hold where the "form issue" (e.g., hip sag/pike relative to a shoulder-hip-ankle line) can occur and resolve repeatedly over one uninterrupted duration. If the session model's primary metric is `repCount`, plank sessions either get a meaningless value (always 1, or always 0) or we need a distinct session shape for hold-based exercises (duration + cumulative out-of-form seconds/instances) from the start. Retrofitting this after squat/push-up are built around "reps" as the primary unit is exactly the kind of quiet scope compression that turns "three exercises, one rule each" into "two real exercises and one squeezed into the wrong data shape."

Third, I want to flag a real entitlement risk that hasn't been named specifically: if the three targets (iOS, watchOS, Catalyst) are meant to share one SwiftData store via an App Group container, App Groups are a paid-developer-account capability on some account tiers and need to be checked, not assumed, exactly like [REDACTED:high_entropy] already flags for HealthKit/Catalyst generally — but I'd call out App Groups by name as the specific likely wall, since WatchConnectivity itself doesn't require shared storage (it can work purely over message-passing with the Watch keeping its own transient state), and if App Groups turn out to be blocked, the fallback is Watch has no persistent local store of its own and only mirrors transient in-session data pushed from the phone — that's a materially different architecture and needs to be decided now, not discovered mid-build.

Fourth, on capability detection specifically for Simulator: `AVCaptureDevice.default(for: .video)` returns `nil` in Simulator because there's no hardware at all — that's a different code path than a real device where the user denied permission (`.authorizationStatus == .denied`) or an enterprise-restricted device (`.restricted`). All three need distinct, honest copy ("no camera hardware detected" vs "camera access denied — open Settings to allow" vs "camera access restricted on this device"), because collapsing them into one generic "camera unavailable" message would itself be a small dishonesty against the project's own priority (a).

Fifth, on HealthKit energy estimate: the contract already forbids inventing biometric numbers, but I don't think we've pinned down what "honestly computed" actually means in practice. A defensible approach is a MET-based estimate (fixed MET values for squat/push-up/plank from published exercise-physiology tables) times duration times body mass — but body mass requires an additional HealthKit *read* permission scope beyond the write-only workout permission already scoped, which is a second permission prompt we haven't accounted for. If we don't want that extra permission surface, the honest fallback is to write the HKWorkout with duration and type only, and explicitly omit energy rather than guess a generic multiplier with no basis — I'd rather we decide "no energy field in v1, duration/type only, documented as a limitation" than quietly ship a MET-times-70kg-assumed-average estimate that's fabricated in everything but appearance.

Sixth, demo-fixture fencing: "must never appear in an HKWorkout write, must be excludable" is stated as a requirement but not as an enforcement mechanism. The only way I'd trust this holds under future edits is if every query that feeds Charts aggregates, HealthKit write eligibility, and export all filter on an `isDemo` flag at the persistence/query layer (a single computed property or predicate reused everywhere), not a per-screen UI check — because a UI check gets missed the first time someone adds a new chart or export path.

Last, storage and privacy: recorded clips are the most sensitive asset in this app (video of someone in their home), and nothing so far specifies where they live on disk, whether they're excluded from iCloud/device backup, or what happens on erase — erase must delete the actual clip files, not just the SwiftData rows referencing them, or "full local erase" is a lie. I'd also flag low-disk-space mid-recording as a real failure mode: if the clip write fails partway through, the session must still save with its rep/duration data and simply have no clip reference, never lose the whole session over a full disk.
