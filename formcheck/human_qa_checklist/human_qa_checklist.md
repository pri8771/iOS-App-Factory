# Formcheck — Manual QA Checklist

**Setup:** Fresh install, no prior app data. Run primarily on iOS Simulator (a real device is needed only for the items explicitly marked *Device required*). Use a clean Simulator (Settings → General → Reset, or delete and reinstall the app) before starting so first-run states are genuine.

**How to read results:** Every item below is marked with how it can be verified in this environment:
- **[SIM]** — fully testable in iOS Simulator right now.
- **[DEVICE]** — requires real hardware; Simulator cannot exercise this path.
- **[CODE-ONLY]** — currently unbuildable/untestable in *any* environment because the underlying feature was never implemented; test the *honesty of the gap reporting* instead, not the feature.

## 1. First launch & discoverability

4. **[SIM]** Before any session exists, open History and the per-exercise Charts screen. **Expected:** each shows a real designed empty state — icon, one line of explanation, and an action (e.g., "Start a demo session") — never a blank screen or bare "No data" text.

## 2. Capability detection (Home/Capture)

5. **[SIM]** Open Home / tap into capture. **Expected:** Simulator deterministically reports a **no-camera-hardware** state (Simulator has no camera), shown as its own honestly-worded state with a distinct icon and remedy text — not a generic "camera unavailable" banner.
6. **[SIM]** Confirm this no-hardware state is visually and textually distinct from what an access-denied or access-restricted state would look like (check via code/screenshots if the other two states can't be triggered). **Expected:** three genuinely different messages exist in the app, not one collapsed message reused three ways.
7. **[DEVICE]** On a real device: deny camera permission, relaunch, and open capture. **Expected:** the access-denied state fires (distinct from no-hardware), with a working Settings deep-link. *Cannot be verified in Simulator — log as device-required if untested.*
8. **[CODE-ONLY]** Access-restricted (MDM-style) state — cannot be triggered honestly on a personal device or Simulator. Verify via code review only that the state exists and has its own icon/text, and log verification method as code-only.

## 3. Demo session — the core, fully-real pipeline

This is the one workflow that must work perfectly — it's the only proof the pose→rule→persist→display chain is real.

9. **[SIM]** Tap the demo-session entry point, start a set. **Expected:** a dominant tabular-numeral rep counter appears and increments with a felt pulse per rep.
10. **[SIM]** Watch for at least one amber form-flag annotation to fire during the set. **Expected:** the annotation names the specific rule/joint/angle that fired (e.g., "knee angle only reached X°, depth target is 100°") — never generic text like "form issue detected." Fail this item if the copy is generic.
11. **[SIM]** Let the set finish naturally. **Expected:** it finalizes into a Post-Set Summary sheet showing final rep count/hold-duration and the one flag if it fired, with a single Done action.
12. **[SIM]** Tap Done. **Expected:** lands in History, and the just-completed session is visible **immediately**, with no app relaunch required. (This is the specific SwiftData cross-context-propagation risk called out in project_plan — if the session doesn't appear until you force a refresh or relaunch, that's a real bug, not a cosmetic issue.)
13. **[SIM]** Confirm the demo session is visually fenced in both places it appears: a dashed border and a badge in the History row, and the same fencing in Session Detail when tapped into. **Expected:** unmistakably distinguishable from what a "real" session would look like.
14. **[SIM]** Open the per-exercise Swift Charts trend for the exercise used. **Expected:** the demo data point appears and is visually distinguishable (per the shared `isDemo` fencing) rather than blending in as if it were real user data.
15. **[SIM]** Run the demo session 2–3 times in a row. **Expected:** History accumulates multiple distinct rows (not overwriting one row), and the chart shows multiple trend points.
16. **[CODE-ONLY / honest gap]** Note explicitly in the report: because live camera capture was never built, there is currently no way to produce a genuinely non-demo session in this app. The "demo data must never blend into real aggregates" requirement is therefore only verifiable in the abstract (the `isDemo` predicate exists and is applied in code) — it has never been exercised against an actual mixed real+demo dataset. Do not report this requirement as "verified" beyond that.
