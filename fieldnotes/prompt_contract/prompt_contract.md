Now my actual read on this, wearing the "what quietly breaks" hat.

The single biggest risk to this whole build is that priority (a) — audio-session interruption correctness — is exactly the kind of requirement that's easy to claim is done and hard to actually prove is done. AVAudioSession interruption handling (begin/end interruption notifications, `.shouldResume` option, route changes from AirPods disconnect, Siri duck-and-resume, a phone call arriving, the app going to background then getting killed by the system for memory pressure) has a huge number of edge cases, and the iOS Simulator cannot simulate a real phone call or a real Bluetooth route change. Any later phase that says "tested interruption handling" needs to specify exactly what was tested (which notifications, which transition simulated how) because "handled interruptions" without a concrete test method is an unverifiable claim, not a fact. I want a decision rule that no phase gets to mark this requirement done without naming the specific interruption scenarios exercised and how (real device required for phone-call and Bluetooth-route scenarios; background-kill can be approximated via Xcode's "Simulate Memory Warning" / debugger detach but that's an approximation, not proof).

Second risk: several of these features have hidden cross-cutting dependencies the prompt doesn't spell out but that will break integrity if skipped. The widget and Live Activity need to read the same SwiftData store as the main app, which means an App Group container and a shared model container — if that's not set up, the widget will either crash, show stale/no data, or the build will silently fall back to fake placeholder data (which the global rules explicitly forbid: "No sample or placeholder data shown as if it were the user's real data"). Same for the Share Extension — it needs an App Group to write into the same store the main app reads, or shared entries silently vanish. This should be a hard requirement even though the user didn't say the words "App Group."

Third: "ending cleanly when the app is killed mid-recording (no orphaned Live Activity)" is a very strong guarantee. iOS does not reliably run app code at the moment of a force-kill — there's no guaranteed clean-shutdown hook. The realistic mechanism is: request the Live Activity with a sensible stale/timeout date up front, and reconcile/end any stale activity on next launch — not "detect the kill and clean up live." If the team quietly implements only the happy-path stop-button flow and calls the kill-scenario "handled," that's a false claim. I want the contract to state the actual mechanism (staleDate + relaunch reconciliation) as the definition of "clean" here, so nobody promises something iOS can't do.

Fourth, on honesty about gaps: the prompt pre-empts one gap (CarPlay entitlement) but there are at least two more real candidates that deserve the same treatment rather than being discovered late: (1) HealthKit — reading HealthKit data for real requires the HealthKit capability/entitlement in the provisioning profile, which is available on a free personal-team account for local device testing but not for TestFlight/App Store distribution without a paid account; that distinction should be recorded explicitly, not asserted as either "fully works" or "fully blocked." (2) On-device Speech recognition support is locale- and device-dependent (`SFSpeechRecognizer.supportsOnDeviceRecognition`, and it can be `false` even when the framework itself is available) — the contract needs a decision rule for what "reject/flag" actually means in the running app: does the record button get disabled, does the user see an explicit banner, does the entry still get created with transcription marked as unavailable? That has to be decided now, not improvised later, because "flag" is not a UI behavior.

Fifth, the "real relevance score you define and document" requirement is a trap for hand-waving — it's trivial to ship a search that's actually just weighted substring matching while calling it a relevance score. The contract should require the scoring formula (whatever it is — recency-weighted BM25-lite, field-weighted term frequency, whatever's chosen) to be written down as a concrete, checkable spec, and the testable requirement should be "given two entries where one has more matching terms in transcript vs one has a matching tag, verify the ranking matches the documented formula's prediction," not just "search returns results."

Sixth, backlink integrity: the prompt's bar ("no dangling or duplicate backlink" on link/unlink/delete) needs a precise definition of what "delete" does to inbound links — does deleting entry A remove the backlink pointer from B, or does B's link to A become a dead/broken-link chip that's shown as such? Both are legitimate designs but they have to be picked explicitly, because "no dangling backlink" and "show broken link honestly" can conflict if not specified.

This is the actual mechanism that keeps tap-to-seek accurate after a transcript edit.

State this caveat explicitly wherever this requirement is claimed as done; don't imply a zero-window guarantee.
