   each transcript to suggest tags and a mood score. Suggestions are

4. Sketch annotations: attach PencilKit sketches to any entry (finger
   or Pencil), stored alongside the audio/transcript.
5. Bi-directional linking: entries can @-mention/link other entries;
   each entry shows a "linked from" backlinks section computed live
   from the local store (no manual backlink maintenance) — same
   integrity discipline as a graph/notes app: linking, unlinking, and
   deleting an entry must never leave a dangling or duplicate backlink.
6. Search: full-text search across transcripts AND tags/mood, with
   results ranked by a real relevance score you define and document

7. HealthKit correlation (read-only, explicit permission): show each

   never block core journaling on this permission.
8. Home-screen widget + Live Activity: widget shows the latest entry's
   mood/snippet; a Live Activity shows elapsed time and live waveform

   or the app is killed mid-recording (no orphaned Live Activity).
9. Share Extension (separate target): accept shared text or a photo
   from other apps and create a new Fieldnotes entry from it.
10. App Intents: "Start a voice entry" and "Search my journal" exposed
    to Shortcuts/Siri.
11. CarPlay: a minimal CarPlay scene for hands-free start/stop
    recording while driving. This requires Apple's CarPlay audio-app
    entitlement, which a personal free developer account cannot

currency). Seed a "demo entries" toggle in Settings with realistic

### Round 1 (Codex — Design Lead · Skeptic)

Here's my take on refining the information architecture and UX flows based on our existing design priorities and constraints.

**Information Architecture:**
- **Home Screen:** The home screen should be the Timeline where entries are displayed. Each entry shows a brief preview with the date, mood chip, and a snippet of the transcript or title. Users can tap on an entry to view details.
- **Record Screen:** This is where users initiate new voice recordings. It should display a live waveform while recording, show interruption states (e.g., "Interrupted," "Finalizing"), and provide options for tags and sketches.
- **Entry Detail Screen:** After tapping on an entry in the Timeline, users can view the full transcript with tap-to-seek functionality. They should also see suggested tags and mood scores, as well as any backlinks from other entries that mention this one.
- **Search Screen:** A dedicated screen for searching through transcripts and tags/mood. The search results should be ranked by a documented relevance formula.

**UX Flows:**
1. **Home Screen (Timeline)**
   - **Action:** Tap on "Record" button
   - **Result:** Navigate to Record Screen

2. **Record Screen**
   - **Action:** Start recording
   - **Result:** Live waveform appears; UI shows "Recording"
   - **Interrupted:** UI changes to "Interrupted"; finalize or resume options appear
   - **Finalized:** Entry returns to Timeline with basic info (date, mood chip)
   - **Post-Record Actions:**
     - Tap transcript for more details
     - Edit tags and add sketches

3. **Entry Detail Screen**
   - **Action:** Tap on a transcript sentence
   - **Result:** Audio player plays the audio from that point
   - **Action:** Add tag or sketch
   - **Result:** Tag/sketch appears in entry; can be edited or dismissed
   - **Backlinks Section:**
     - Shows entries that mention this one
     - Clicking on a backlink navigates to that entry

4. **Search Screen**
   - **Action:** Type search query
   - **Result:** List of results ranked by relevance
   - **Action:** Tap on result
   - **Result:** Navigate to Entry Detail Screen for that entry

**Design Considerations:**
- **Consistency in UI States:** Ensure every screen consistently shows loading, success, and error states. For example, the Timeline should show a loading indicator while entries are being fetched.
- **Clear Navigation:** Make sure there's clear visual hierarchy and easy navigation between screens. The home button should always return to the Timeline.
- **Accessibility:** All text and controls should be accessible; use semantic color roles for readability in both light and dark modes.
- **Data Protection:** Ensure all sensitive data like audio files, transcripts, and sketches are protected with `NSFileProtectionCompleteUntilFirstUserAuthentication`.

**Risks:**
- **Complexity in Interruption Handling:** Ensuring the app correctly handles multiple simultaneous interruptions is crucial. A misstep here can lead to corrupted recordings or loss of data.
- **Inconsistent UI States:** If any screen fails to show the correct state, users may become confused or frustrated.
- **Security Risks:** Improper handling of permissions and data protection can lead to security vulnerabilities.

**Preservation Details:**
- **Interruption Handling:** The build must implement a robust state machine that correctly handles multiple interruptions. This should be thoroughly tested in various scenarios.
- **UI States:** Every screen must have comprehensive testing for all possible states, ensuring a smooth user experience.
- **Data Protection:** Explicitly document and enforce the use of `NSFileProtectionCompleteUntilFirstUserAuthentication` across all sensitive data.

This initial design aims to provide a clear, consistent, and secure user experience while minimizing potential risks.

**Must-have (fully functional this build):**
- Interruption-safe voice recording: state machine (idle/recording/interrupted/finalizing) handling `.interruption` and `.routeChange` as distinct events, live waveform, clean finalize/resume.
- On-device transcription: three-state status (ready/downloading/unavailable), editable transcript, anchor-ID tap-to-seek surviving edits with nearest-surviving-anchor fallback.
- Auto-tag & mood suggestions: dismissible/editable, never silently applied.
- Bi-directional linking: UUID-based @-mentions, live-computed backlinks, dedup, no self-mention, visible broken-link indicator on stale mentions.
- Search: documented deterministic relevance formula, verified against a fixed two-entry test case; untranscribed entries remain findable via tags/mood/sketch metadata.
- Demo entries toggle: reversible, fully seeded, visually/data-model distinct from real entries — elevated to Must despite reading as cosmetic, because a broken demo toggle damages the first impression of every other feature.
- App Group + shared SwiftData container (infra) and file-protection minimums on all App Group data.

**Should-have (built and working, allowed to be thinner):**
- PencilKit sketches (finger/Pencil, one free / unlimited Pro).
- HealthKit read-only correlation — the denied/no-data hedge state gets full visual treatment since it's what most reviewers will actually see; core journaling is never blocked by this permission.
- Home-screen widget + Live Activity (reload-budget-respecting, staleDate + relaunch reconciliation for cleanup).
- Share Extension (one-way text/photo import).

**Could-have (built this cycle, first to cut under time pressure — in this order: Pro subscription, then App Intents):**
- App Intents ("Start a voice entry," "Search my journal").
- Fieldnotes Pro subscription (Insights, advanced search, unlimited sketches, icons/themes) — StoreKit correctness (offline-after-purchase, no feature/data gating) makes a half-built version worse than none, so it's named explicitly as the first casualty if time runs short.
- Share-as-card export, CloudKit-ready off-by-default toggle.

**Won't (this cycle — code path still built, only the runtime is out of reach):**
- CarPlay's actual on-vehicle execution, blocked on the CarPlay audio-app entitlement unavailable to a free developer account.
