   AVAudioSession category/interruption handling genuinely right, this

   server-based recognition is available for a locale). Transcript is

   each transcript to suggest tags and a mood score. Suggestions are

4. Sketch annotations: attach PencilKit sketches to any entry (finger

5. Bi-directional linking: entries can @-mention/link other entries;
   each entry shows a "linked from" backlinks section computed live
   from the local store (no manual backlink maintenance) — same

6. Search: full-text search across transcripts AND tags/mood, with
   results ranked by a real relevance score you define and document

7. HealthKit correlation (read-only, explicit permission): show each

   never block core journaling on this permission.
8. Home-screen widget + Live Activity: widget shows the latest entry's
   mood/snippet; a Live Activity shows elapsed time and live waveform

   or the app is killed mid-recording (no orphaned Live Activity).
9. Share Extension (separate target): accept shared text or a photo
   from other apps and create a new Fieldnotes entry from it.
10. App Intents: "Start a voice entry" and "Search my journal" exposed

11. CarPlay: a minimal CarPlay scene for hands-free start/stop
    recording while driving. This requires Apple's CarPlay audio-app

Navigation is a single `TabView` (Timeline / Search / Settings) with a `NavigationStack` per tab so push history is independent across tabs — switching tabs and back must preserve each stack's scroll/detail position, that's a real user-visible bug class if built naively with one shared stack. Entry Detail is pushed from Timeline or Search. @-mention autocomplete inside the transcript editor is an inline popover-style overlay anchored to the caret, not a full sheet — it needs to stay light enough that keyboard + autocomplete list + transcript text never collide, which is its own overlap risk the global no-overlap rule should catch but a builder could miss because it's dynamic, not static layout.

The part I want to flag hardest: transcription state, tag/mood suggestions, and backlinks must never live in a separate `@Published` view-model field that's derived once and cached — they have to be read live off the SwiftData model on every render. The reason is structural, not stylistic: DEC-prompt_contract-008 requires backlinks to be a live query with zero stored bookkeeping, and DEC-initial_discussion-003 requires the Timeline card's transcribing/ready badge to update in place without blocking a new recording. If a view model snapshots either of those into local state, you get exactly the failure mode this whole app was designed to avoid — a badge that lies about the entry's real state until the user pulls to refresh. Concretely: Timeline's `@Query` should read `Entry` directly from the shared App Group `ModelContainer`, and the transcription pipeline (a background `Task` per entry, not a shared queue actor that could serialize entries behind each other — DEC-initial_discussion-003 explicitly says a second recording must never be blocked) writes status updates straight onto the `Entry` model on the main actor, so SwiftData's own change notification is what drives the UI, not a bespoke pub-sub layer. Backlinks resolve via a `#Predicate` filtering `Entry.mentions.contains(targetID)` computed at Entry Detail render time — I'd deliberately keep this a per-screen query, not a global backlink index rebuilt on every entry save, because a naive "recompute all backlinks for all entries on any change" job is an easy way to introduce jank once someone seeds 50+ demo entries.

One edge case I don't see named anywhere upstream: what happens if the user is actively editing a transcript (the `editing` state on Entry Detail) at the exact moment a phone-call interruption fires on a *different* in-progress recording elsewhere in the app? That shouldn't be possible if Record is truly modal (you can't be on Entry Detail while Record's fullScreenCover is up), but it's worth stating explicitly in the handoff that Record being presented modally is itself part of the interruption-safety design, not just a navigation choice — a builder who later "improves" Record into a non-modal push nav would silently reopen a race between transcript editing and the interruption state machine.

Waveform rendering deserves a performance note. AVAudioEngine's tap gives you raw sample buffers at the hardware rate; drawing every sample as an ink stroke will pin the main thread. The `WaveformInkView` should consume a throttled, downsampled amplitude stream (bucket to roughly 12-15 updates/sec, RMS per bucket) published from the recording controller, not raw taps — that keeps the "ink accreting" animation smooth without competing with the audio render thread for CPU, which matters more here than in a typical app because a dropped audio buffer during a demanding animation frame is literally the worst-case failure this app exists to prevent.

**Navigation Pattern:** Single `TabView` (Timeline/Search/Settings), each tab with its own `NavigationStack` so per-tab push history/scroll position survives tab switches. Entry Detail is pushed from Timeline or Search. @-mention autocomplete is an inline popover anchored to the caret inside the transcript editor, not a sheet.

**Screen States (copy + recovery, not placeholder text):**
- Timeline empty: "No entries yet" / "Tap the record button to capture your first note" + open-notebook glyph.
- Timeline error (SwiftData container failed to load): "Couldn't open your journal" + Retry — visually distinct from the empty state so data loss is never mistaken for a fresh install.
- Entry Detail transcript states: "Transcribing…" (ink-draw idle pulse, no spinner) / "Downloading on-device speech model…" (note it can take a minute first use) / "Transcription unavailable in this language on this device" (links to Settings permission matrix).
- Search empty states, two distinct copies: "No entries indexed yet" (nothing to search) vs. "No matches for '<query>'" (searched, found nothing).

**Motion & Haptics:** Waveform ink draws as a continuously appended path (no discrete animation) fed by a throttled/downsampled amplitude stream (~12–15 updates/sec, RMS per bucket) — never raw AVAudioEngine taps, which would pin the main thread against the audio render path. Interruption color shift: 300ms crossfade. Card badge transition (transcribing→ready): 200ms crossfade + subtle checkmark scale-in, never a layout-shifting pop. Record's fullScreenCover uses a custom vertical-slide-up, not the default modal bounce. Haptics: light impact on arm, medium on record start, distinct warning-style haptic at the moment interruption is detected (covers phone-in-pocket cases the VoiceOver announcement doesn't reach), success haptic on finalize.

**Accessibility:** Every mood chip/state badge pairs color with a text/VoiceOver label (never color alone). Interruption ink-color change fires a simultaneous VoiceOver announcement. Sparkline is `.accessibilityHidden(true)` (decorative); EntryCard's VoiceOver reading order is date → mood label → state badge → transcript snippet, not raw z-order. At largest Dynamic Type, sparkline drops before colliding with badges/chips.

**Architecture rules the spec depends on (build phase must honor, not just the visuals):** Timeline's `@Query` reads `Entry` directly off the shared App Group `ModelContainer`; transcription status/tags/mood/backlinks are never cached in view-model state — they're read live so SwiftData's own change notification drives the UI. Transcription runs as one background `Task` per entry (not a shared serializing queue actor), so a second recording is never blocked. Backlinks resolve via a per-screen `#Predicate` query at Entry Detail render time, not a globally rebuilt index.
