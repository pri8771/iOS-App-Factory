Coming at this as the person who has to make the client code actually hold together across four targets and a dozen concurrent state sources — my read is that the biggest risk this phase faces isn't picking the right framework, it's letting "SwiftData is the source of truth" become a slogan instead of an enforced boundary. So I'm going to spec the data layer and concurrency boundaries tight enough that a builder literally cannot reintroduce a cached snapshot by accident, and then push one genuinely bold idea on top: this app's per-entry waveform shouldn't just be a recording artifact, it should be a *visual fingerprint* — I'll get to that.

**Architecture overview.** MVVM-lite, but "VM" is doing almost no work here on purpose. Views bind directly to `@Query`/`@Model` via SwiftData's own observation — Entry lists, transcript state, tags, mood, backlinks all read live off the store, per design_handoff's mandate. The only real "services" layer sits below the model layer: a `RecordingController` (owns the AVAudioEngine graph + interruption state machine, isolated off the main actor), a `TranscriptionCoordinator` (one Task per entry), an `AutoTagger` (NaturalLanguage wrapper, synchronous but dispatched off-main for longer transcripts), a `SearchRelevanceScorer` (pure function, no state at all — this is deliberate, see below), a `BacklinkQuery` (pure query function), and a `HealthContextProvider` (live HKQuery wrapper, zero persistence). Everything that isn't genuinely stateful machinery is a pure function over the SwiftData store. That's the whole architecture in one sentence: state lives in one place, and everything else is either a state machine that owns exactly one hard problem (audio) or a pure function that reads the store.

**File/module layout.** One local Swift package, `FieldnotesCore`, holds everything that must be schema-identical across targets: `Models/` (Entry, Anchor, Tag, Mention, Sketch, the shared enums), `Persistence/` (AppGroupConfig, ModelContainerFactory, FileProtectionHelper), `Search/` (SearchRelevanceScorer), `Backlinks/` (BacklinkQuery, MentionAutocompleteQuery), `RecordingEngine/` (RecordingController, AudioSessionManager, WaveformAmplitudePublisher, RecordingReconciler), `Transcription/` (TranscriptionCoordinator, SpeechAvailability), `Tagging/` (AutoTagger), `HealthKitBridge/` (HealthContextProvider, HealthDaySummary), `DemoData/` (DemoDataSeeder), `Subscription/` (SubscriptionManager). The app target then holds only UI and target-specific glue: `App/`, `Theme/Theme.swift`, `Timeline/`, `Record/`, `EntryDetail/`, `Search/`, `Settings/`, `CarPlay/` (scene delegate + template, gapped but compiling), `StoreKitPro/`. `FieldnotesWidget` holds the home-screen widget and the Live Activity (its `ActivityAttributes` struct lives in Core since both the app that starts the activity and the widget extension that renders it need the identical type). `FieldnotesShare` is the Share Extension target, thin — it composes an `Entry` via Core's factory and writes straight into the shared container. Nothing touches the model schema except through Core.

**Data models**, concretely, because this is where "parallel lanes don't invent incompatible types" actually gets decided:

`Entry`: id (UUID), title (String — yes, entries get a short editable label; this is what makes DEC-prompt_contract-014's rename-safety concrete, since @-mention autocomplete/display needs *something* human-readable that isn't the immutable UUID), createdAt/updatedAt (Date), audioRelativePath (String), durationSeconds (TimeInterval), recordingStatus (persisted enum: .finalized / .interrupted / .recoveredAfterUnexpectedExit — coarse, disk-truth state, distinct from the richer in-memory `RecordingState` the controller uses live), transcriptionStatus (enum: .notStarted / .modelDownloading / .transcribing / .ready / .unavailable), cachedTranscriptText (String — a denormalized concatenation of non-deleted Anchor text, recomputed synchronously on every anchor mutation, purely so search doesn't have to fault in every entry's anchor relationship on every keystroke; it is a cache with exactly one writer, never an independent source of truth), moodScore (Double?, -1…1), moodLabel (String?), moodStatus (SuggestionStatus: .suggested/.accepted/.dismissed), waveformSummary ([Float], ~48 RMS buckets computed once at finalize — this is what feeds EntryCard's ghost sparkline; nobody upstream named this field but the component inventory needs persisted waveform data, not live-only), isDemo (Bool). Relationships: anchors (to Anchor, cascade delete), tags (to Tag, cascade delete), sketches (to Sketch, cascade delete), outgoingMentions (to Mention, cascade delete) — all optional-with-inverse per the CloudKit constraint.

`Anchor`: id (UUID, immutable identity), entry (inverse relationship), startTime/endTime (TimeInterval, immutable), sequenceIndex (Int, immutable), text (String, the one mutable field — this *is* the overlay delta DEC-prompt_contract-015 describes), isDeleted (Bool). Anchors are never actually removed from the store on edit — a "delete" sets `isDeleted` and empties `text`. That's what makes the nearest-surviving-anchor fallback possible: the ID and position survive, only the content and visibility do not.

`Tag`: id, entry (inverse), name (String), source (.aiSuggested/.userAdded), status (SuggestionStatus, shared enum with mood).

`Mention`: id, sourceEntry (relationship, inverse — cascade-deletes when source is deleted), targetEntryID (raw UUID, *not* a relationship — this is the load-bearing choice, since a relationship would either force a non-optional inverse SwiftData can't express or auto-null on delete, and we specifically need to detect "target no longer exists" rather than have it silently vanish), anchorID (UUID?, which anchor position it's attached to for inline rendering), createdAt.

`Sketch`: id, entry (inverse), drawingData (Data, `.externalStorage`), createdAt.

Backlinks are computed, never stored: `BacklinkQuery.backlinks(for: entryID, in: context)` fetches `Mention` where `targetEntryID == entryID`, dedupes by `sourceEntry.id` ([REDACTED:high_entropy]), and returns the source Entries. A forward mention is "broken" when `context.model(for: mention.targetEntryID)` resolves to nothing — rendered as the dashed BacklinkRow variant, never silently dropped to plain text.

**Persistence strategy.** One `ModelContainer`, one App Group container, built by `ModelContainerFactory.make(cloudKitEnabled: Bool)` in Core and injected via environment into all four targets — no target gets its own `@Model` copies, full stop. Audio files and PencilKit drawings live as real files under the App Group container via FileManager (Entry stores only the relative path; Sketch's `.externalStorage` attribute handles its own file), with `NSFileProtectionCompleteUntilFirstUserAuthentication` applied explicitly after write, not assumed as default. Every model satisfies CloudKit's constraints (no `.unique`, optional+inverse relationships, defaults on non-optionals) from the first commit even though the sync `ModelConfiguration` stays local-only and the Settings toggle stays off.

**Search — the part I want to be stubborn about, since two prior phases promised a real formula and neither wrote one down.** `SearchRelevanceScorer.score(entry:queryTokens:now:) -> SearchScoreResult` is a pure, testable function: transcriptScore = 3 points per query token found as a whole word in `cachedTranscriptText` (case-insensitive), +5 if the full query phrase appears as a contiguous substring; tagScore = 5 points per query token that exactly matches a tag name; moodScore = 4 points if a query token matches the entry's mood label; recencyBonus = up to 2 points on a 15-day step decay (2 if <15 days old, 1 if 15–29, 0 after) — but recencyBonus only applies *on top of* a nonzero content match, never as a standalone reason an entry appears, so an old entry with zero real match never surfaces just because it's recent. Results are sorted by total descending, ties broken by createdAt descending, entries with total == 0 excluded entirely (that's the honest "no matches" vs "nothing indexed" split). Fixed two-entry proof case: Entry A ("Walked along the beach this morning, felt calm and clear-headed", tags nature/morning, mood positive, created today) vs Entry B ("Long stressful meeting about the beach house renovation budget", tag work, mood negative, created 20 days ago), query "beach calm" → A scores 3+3+0+0+2(recency)=8, B scores 3+0+0+0+1(recency)=4, so A outranks B despite both containing "beach" — because the formula rewards actual relevance, not insertion or alphabetical order. `matchReasons` on the result (ordered by contribution) is what feeds the "why this matched" UI hint. Untranscribed entries score purely on tag/mood, which is exactly DEC-prompt_contract-017's documented behavior, not a special case in the code.

**Concurrency boundaries and error handling.** Main actor owns the `ModelContext` and all UI. `RecordingController` is its own actor, reachable via `handleInterruption(type:options:)` / `handleRouteChange(reason:)` as directly callable methods (NotificationCenter is a thin forwarding shim, per the architecture review) — it publishes a downsampled amplitude stream (~12–15Hz) via `AsyncStream<Float>` for `WaveformInkView`, never raw taps. `TranscriptionCoordinator` spawns one `Task` per entry, writes status back onto the model on the main actor when done — no shared queue actor, so a second recording is never gated behind a first entry's transcription. Errors are typed per domain (`RecordingError`, `TranscriptionError`, `HealthKitError`) and always resolve to a visible UI state, never a silent catch — there is no `try?` anywhere in the recording or finalize path.

The one honestly risky call in my own design: `cachedTranscriptText` is a denormalized field, which means there are technically two places transcript content could theoretically get out of sync if a builder edits Anchor.text directly instead of going through a single `TranscriptEditor.applyEdit(anchorID:newText:)` entry point. I think the tradeoff is worth it — without the cache, search over a few hundred entries means faulting in every entry's anchor relationship on every keystroke, which is the kind of thing that feels fine in a two-entry test case and then jank on a seeded 60-entry demo set — but it only stays safe if there's exactly one write path, and that needs to be a rule the build phase actually enforces, not just a comment.

Now the visionary push, because "correct" and "remarkable" aren't the same bar: the `waveformSummary` I added to Entry shouldn't just be a generic sparkline — I'd render it with a per-entry deterministic ink-color seed derived from the entry's mood + a hash of its id, so that scrolling the Timeline actually looks like flipping through a hand-annotated field notebook where every entry has its own slightly different ink character, not forty identical gray sparklines with a color dot next to them. It's cheap (we already compute the RMS buckets at finalize for free), it's fully within the existing design language, and it's the difference between "waveform visualization exists" and the Timeline actually looking like nobody else's app. I'd rather spend fifteen minutes of polish budget there than on anything CarPlay-adjacent.

One local Swift package (`FieldnotesCore`) holds the shared schema (`Entry`, `Anchor`, `Tag`, `Mention`, `Sketch`), persistence helpers, search scoring, backlink queries, the recording engine, transcription coordination, tagging, the HealthKit bridge, demo-data seeding, and subscription logic — imported identically by the main app, widget, Share Extension, and CarPlay code path. Concrete additions this phase: an `Entry.title` field for human-readable mention display, a documented denormalized `cachedTranscriptText` cache with a single enforced write path, a `waveformSummary` field powering both the Timeline sparkline and a per-entry deterministic ink-color visual signature, `Mention.targetEntryID` stored as a raw UUID (not a relationship) to make broken-link detection possible, and `Anchor` soft-deletion to support the nearest-surviving-anchor tap fallback. The search relevance formula is fully specified with exact weights and a worked two-entry proof case. Testing strategy splits into CI-runnable pure-logic coverage versus a separate physical-device manual tier. Full interfaces-json contract is emitted below for parallel build lanes to code against.
