First, backgrounded recording. Nobody in this chain has named it yet, so I will: without the `audio` UIBackgroundMode declared in the main app target's Info.plist, iOS suspends the process within seconds of backgrounding and AVAudioEngine's render thread stops — meaning "survive being backgrounded" (requirement #1, the app's single hardest promise) is structurally impossible without this capability. This isn't optional polish, it's the precondition for the entire interruption-safety story, and it needs to be decided now: the app target ships with Background Modes → Audio enabled, and the AVAudioSession category is `.playAndRecord` (not `.record`) with `.allowBluetooth` and `.defaultToSpeaker`, activated only while Record is presented or audio is playing in Entry Detail, deactivated otherwise — not left permanently active, which would fight other apps for the audio session and drain battery for no reason.

Second, the recording pipeline must never buffer the take in memory and write it out on stop. If the app is force-quit mid-recording (one of the five named scenarios), an in-memory buffer dies with the process and the entry is gone — the single worst failure this whole project exists to prevent. The architecture has to write each `AVAudioEngine` tap buffer straight to an `AVAudioFile` on disk incrementally, and on next launch the app must scan for any entry left in "recording" or "interrupted" status with no clean finalize and reconcile it from whatever was actually flushed to disk — worst case a truncated-but-valid file marked "recovered after unexpected exit," never silent data loss and never a corrupted file that just fails to open. That reconciliation path is a concrete, testable requirement, not a nice-to-have, and it belongs in requirements-json before build starts.

Third, and this is the one I'll be most stubborn about: the whole "flip a config, not a migration" claim about CloudKit-readiness ([REDACTED:high_entropy]) is currently aspirational, not architected. CloudKit-backed SwiftData has real constraints — no `@Attribute(.unique)`, every relationship optional with an inverse, every non-optional attribute needs a default value — and if the schema isn't written to satisfy those constraints from day one, "off-by-default toggle" becomes exactly the migration project the decision promised to avoid. I want this stated as a hard build rule now: every SwiftData model in this app is written CloudKit-compatible from the first commit, even though the toggle stays off, specifically so that decision doesn't quietly become false six months from now.

One package, one schema, compiled once, imported everywhere.
