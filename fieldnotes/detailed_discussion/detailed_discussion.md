**Claude (QA & Risk · Skeptic) — Round 1**

Let me poke at the places I think will actually break in build and verification, since this phase is where ambiguity has to die or become an explicit assumption.

Start with the interruption state machine, because "5 named scenarios" understates the real problem: interruptions compose. What happens when a Siri invocation interrupts the recording and, before we finish resuming, a phone call comes in? What about a route change (headphones unplugged/AirPods disconnect) — that's a *separate* AVAudioSession notification (`.routeChange`, not `.interruption`) and it's the one people forget, because unplugging wired headphones mid-recording doesn't pause anything by default, it just silently switches to the speaker/mic in a way that can clip or distort the take. I want it stated explicitly that the session manager is a proper state machine (idle/recording/interrupted/finalizing) that's reentrant to overlapping interruption signals, not a boolean `isInterrupted` flag — a flag breaks the instant two interruption sources overlap, which is exactly the kind of thing that only shows up on manual test rep 14 of 20, not rep 1.

Second, on-device Speech has two gotchas nobody's named yet: the on-device language model isn't necessarily already downloaded even when `supportsOnDeviceRecognition` returns true for a locale — first use on a fresh device can trigger a background asset download, so there's a real third state beyond "unavailable" and "ready": "downloading, try again shortly." If we collapse that into "unavailable" we're technically lying about *why* transcription isn't happening yet, which is exactly the kind of dishonesty this whole app is supposed to avoid. Second: Speech authorization (`SFSpeechRecognizer.requestAuthorization`) is a distinct permission from microphone access — two separate system prompts, denyable independently — so there's a real combination matrix (mic granted + speech denied = record-only entries forever; mic denied = no recording at all) that the health-card writeup needs to cover, not just "Speech unavailable."

Third, the transcript-anchor overlay model needs one more rule spelled out: what happens when a user's edit spans or deletes an entire anchor's text, or merges two sentences into one? The seek-by-anchor-ID rule survives character-level edits fine, but if the anchor itself is deleted, tapping near that gone sentence needs to resolve to the nearest surviving anchor rather than doing nothing or throwing — that's a concrete fallback rule, not an implementation detail to leave implicit.

Fourth, backlinks: I want it on record that a duplicate @-mention of the same entry within one transcript dedupes to a single backlink entry (not once per occurrence), and that a self-mention (entry mentions itself) is either disallowed at autocomplete time or explicitly rendered without infinite recursion risk in the "linked from" UI — nobody's said which, and it's cheap to decide now and expensive to discover as a crash later.

Fifth, HealthKit is more annoying than a binary authorized/denied. Apple deliberately does not tell you whether the user denied read access — `requestAuthorization` completing just means the sheet was shown, not what they chose, and querying denied data returns an empty result indistinguishable from "no data exists that day." So "connected" vs "not connected" in this app is actually going to be inferred from empty results over some window, and the UI copy needs to hedge accordingly ("no data available" reads very differently from a confident "not connected" claim if what we actually know is "either denied or genuinely no data logged that day").

On privacy/storage: audio files, transcripts, and PencilKit drawings sitting in the shared App Group container should get real Data Protection (`.completeUntilFirstUserAuthentication` at minimum, ideally `.complete`) since this is a journal — arguably the most sensitive personal data category this factory has touched. And HealthKit data specifically should never be persisted into SwiftData at rest; it should be queried live per-view and displayed, not cached to disk, both because Apple's review guidelines are touchy about this and because it's the kind of decision that's much cheaper to bake in now than retrofit.

Two smaller risk-register items worth naming explicitly rather than discovering in build: widget reload budget is finite (roughly 40-70 background reloads/day system-wide) so the widget must only call `WidgetCenter.reloadTimelines` on actual entry save, not speculatively; and Live Activities auto-expire at 8 hours, which is irrelevant for a 30s-3min journal entry but matters for the "orphaned Live Activity" edge case if the OS itself force-ends the activity independent of our staleDate mechanism — worth folding into the residual-window caveat already on record rather than treating as a new gap.

Last thing I want locked as an explicit assumption rather than left implicit: demo entries and real entries must be mutually unlinkable — a demo entry's seeded @-mention should only ever resolve to other demo entries, and a real entry should never be able to @-mention a demo entry (autocomplete should filter demo entries out entirely once the toggle state is real-data-only, or filter both ways). Otherwise turning the demo toggle off mid-use could either strand a live backlink pointing at a poof'd demo entry or, worse, blur the toggle's whole "never mistaken for real data" guarantee from DEC-prompt_contract-009.
