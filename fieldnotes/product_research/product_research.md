## Original Prompt

```
Build a polished, fully offline-first iOS voice-journaling app called
"Fieldnotes". Native Apple stack only: SwiftUI + SwiftData, AVFoundation
for recording, Speech framework for on-device transcription, Natural­
Language framework for on-device tagging/sentiment, PencilKit for sketch
annotations. No backend, no accounts, no network dependency for any core
feature — everything must work in airplane mode. Follow the
ios-app-factory-rules. If a requested capability needs something this
project genuinely cannot provide (a special Apple entitlement, a paid
developer account feature, server-side ML), do NOT fake or stub it —
record it as an explicit gap with what it would actually take.

Core features (complete over broad — ship fewer things fully working):

1. Voice entries: record audio journal entries with a live waveform
   view while recording. Recording must survive being interrupted by a
   phone call, Siri, or the app being backgrounded, and must resume
   or cleanly finalize the entry rather than corrupt/lose it — get
   AVAudioSession category/interruption handling genuinely right, this
   is the hardest technical part of the app.
2. On-device transcription: transcribe each recording using Speech
   framework (on-device recognition only — reject/flag if only
   server-based recognition is available for a locale). Transcript is
   editable after the fact; edits must not desync from the audio
   timeline (tapping a transcript sentence seeks the audio to that
   point).
3. Auto-tagging & mood: run NaturalLanguage tokenization/sentiment on
   each transcript to suggest tags and a mood score. Suggestions are
   editable/dismissible — never silently apply an AI guess as fact.
4. Sketch annotations: attach PencilKit sketches to any entry (finger
   or Pencil), stored alongside the audio/transcript.
5. Bi-directional linking: entries can @-mention/link other entries;
   each entry shows a "linked from" backlinks section computed live
   from the local store (no manual backlink maintenance) — same
   integrity discipline as a graph/notes app: linking, unlinking, and
   deleting an entry must never leave a dangling or duplicate backlink.
6. Search: full-text search across transcripts AND tags/mood, with
   results ranked by a real relevance score you define and document
   (not just substring match order).
7. HealthKit correlation (read-only, explicit permission): show each
   entry's mood alongside that day's HealthKit sleep/activity summary
   if authorized, and degrade to "not connected" honestly if denied —
   never block core journaling on this permission.
8. Home-screen widget + Live Activity: widget shows the latest entry's
   mood/snippet; a Live Activity shows elapsed time and live waveform
   while actively recording, ending cleanly when the recording stops
   or the app is killed mid-recording (no orphaned Live Activity).
9. Share Extension (separate target): accept shared text or a photo
   from other apps and create a new Fieldnotes entry from it.
10. App Intents: "Start a voice entry" and "Search my journal" exposed
    to Shortcuts/Siri.
11. CarPlay: a minimal CarPlay scene for hands-free start/stop
    recording while driving. This requires Apple's CarPlay audio-app
    entitlement, which a personal free developer account cannot
    obtain — if that's confirmed true in this environment, build the
    CarPlay scene code path correctly but record in Gaps that it
    cannot actually run/ship without that entitlement, rather than
    silently omitting the feature or pretending it works.

Priorities, in order: (a) audio-session interruption correctness — a
lost or corrupted recording is the worst possible failure, (b) backlink
graph integrity, (c) honest degradation of every permission-gated
feature (Speech, HealthKit, CarPlay). Use Decimal/Int for anything
numeric that isn't inherently floating (durations in seconds as
TimeInterval is fine; don't invent unnecessary Decimal use here — this
app's money-precision lesson from prior apps doesn't apply, there's no
currency). Seed a "demo entries" toggle in Settings with realistic
sample entries, transcripts, tags, and backlinks so no screen is empty
on first review. Provide a clear way to run it in the iOS Simulator via
Xcode, and call out anywhere CarPlay/HealthKit/Speech behave differently
in Simulator vs. a real device.
```

Reading this as a QA/pragmatist, not a visionary: I want to know what actually breaks first, and what's the smallest thing we can ship that's genuinely trustworthy rather than merely feature-complete.

Likely overlap with two groups: people already using Day One or Daylio for reflective/mood journaling, and people who like the Obsidian/Roam bidirectional-linking mental model and want that applied to voice rather than typed notes (ASSUMPTION — no market data was fetched for this project, this is inference from the feature list, not research). On comparables: Day One is the incumbent to beat on polish and has audio/photo entries, but it's fundamentally cloud-sync-centric and doesn't do transcript-to-audio-timeline seeking or a computed backlink graph (ASSUMPTION, based on general familiarity with the product, not a fetched source). Apple's own Voice Memos app already does on-device transcription in recent iOS versions (ASSUMPTION/general knowledge) — which matters a lot for how this app should be pitched, because "we transcribe on-device" alone is no longer a differentiator, Apple ships that natively now. The actual differentiator in this feature list is the combination: transcript+audio+tags+mood+backlinks+HealthKit context in one graph-aware local store. Obsidian/Roam prove the backlink UX pattern works and that users tolerate "computed live" backlinks over manual link management, which validates DEC-prompt_contract-008's approach. None of these comparables combine voice-first capture with a linking graph, so that's the real gap — but it's also why this is the hardest possible v1 to build well, since it's assembling patterns from three different app categories (journaling, transcription, graph notes) that don't normally coexist.

Here's my actual worry, wearing the pragmatist hat: eleven features plus a widget plus a Live Activity plus a Share Extension plus App Intents plus a CarPlay scene is not "a first build," it's a portfolio of five apps stitched together. The prompt contract already got the priority order right (interruption correctness > backlinks > honest degradation), but product research should say the quiet part out loud: a genuinely shippable v1 is the core loop — record, interruption-safe, transcribe, tag/mood suggest, backlink, search — done to the "20+ scenario-tested" bar the contract demands. Widget and Live Activity are next because they're actually testable in Simulator and reuse the same App Group work. Share Extension and App Intents are real but secondary surfaces. CarPlay gets code-path-only treatment with zero polish time, per the contract's own instruction.

Concrete risks I'd flag before anyone starts building:

First, there's a nasty inversion in this project: the single most safety-critical requirement (interruption correctness under a real phone call, Bluetooth route change, force-quit) is the *least* verifiable in the environment this will actually be reviewed in. Whoever reviews this build will almost certainly do it in Simulator first, where you cannot place a real call or trigger a real Bluetooth handoff. That means the flagship trust guarantee is the one most likely to get a superficial "looks fine" pass unless the build phase is explicit that Simulator-passing is not the same as scenario-verified, exactly per DEC-prompt_contract-002.

Second, CarPlay's gate may be tighter than "needs a paid account" implies. My understanding (ASSUMPTION/general knowledge, not fetched) is that the CarPlay audio-app entitlement historically requires a specific request/approval from Apple even for local development and testing via Xcode's CarPlay simulator scene, not just a paid Apple Developer Program membership — a paid account is necessary but may not be sufficient. That should get confirmed as fact rather than repeating the assumption that a paid account alone unlocks it; if wrong, the gap note overpromises what upgrading the account would fix.

Third, HealthKit correlation's "connected" state is probably not the common case in review conditions. Nobody reviewing this app will have real sleep/activity history matched to demo journal entries unless it's hand-seeded into the Simulator's Health app for that exact purpose. That means the "not connected / denied" honest-degradation path is what most reviewers will actually see day-to-day, and it should be built and polished as the primary state, not the fallback branch — the connected state is the one that needs the seeded-data workaround to even demo.

Fourth, the App Group + shared SwiftData container isn't just plumbing, it's real integration risk: the widget's timeline provider, the Live Activity, the Share Extension, and the main app all touching one shared local store concurrently is exactly the kind of surface where schema mismatches or write contention produce silent staleness — which would look like "the widget shows an old entry" and get misdiagnosed as a caching bug rather than what it actually is, a shared-store consistency bug.

Fifth, sentiment from NaturalLanguage is coarse — positive/negative/neutral polarity, not a clinically meaningful mood measure — and the UI needs to set that expectation plainly (a small score/label, framed as a rough signal) rather than imply the app understands the user's emotional state, both because it'd be dishonest and because overclaiming here is the kind of thing that erodes trust fast in a journaling app specifically.

For the first build, my implication is: bias every hour of build time toward the five core-loop requirements and the App Group foundation under them, since that foundation is what widget/Live Activity/Share Extension/App Intents all depend on later — get that shared-store plumbing right once rather than retrofitting it after the widget already exists. Treat HealthKit's denied/not-connected state as the default design case. Treat CarPlay purely as a compiling code path with an accurate, specific Gap note once its entitlement requirements are actually confirmed rather than assumed. And build the demo-entries seed data to include a HealthKit-correlated day and a broken-link example specifically, since those are the two states most likely to otherwise go unseen in a normal review pass.
