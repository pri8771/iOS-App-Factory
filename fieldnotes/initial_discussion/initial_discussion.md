```
Build a polished, fully offline-first iOS voice-journaling app called
"Fieldnotes". Native Apple stack only: SwiftUI + SwiftData, AVFoundation
for recording, Speech framework for on-device transcription, Natural­
Language framework for on-device tagging/sentiment, PencilKit for sketch
annotations. No backend, no accounts, no network dependency for any core
feature — everything must work in airplane mode. Follow the
ios-app-factory-rules. If a requested capability needs something this
project genuinely cannot provide (a special Apple entitlement, a paid
developer account feature, server-side ML), do NOT fake or stub it —
record it as an explicit gap with what it would actually take.

Core features (complete over broad — ship fewer things fully working):

1. Voice entries: record audio journal entries with a live waveform
   view while recording. Recording must survive being interrupted by a
   phone call, Siri, or the app being backgrounded, and must resume
   or cleanly finalize the entry rather than corrupt/lose it — get
   AVAudioSession category/interruption handling genuinely right, this
   is the hardest technical part of the app.
2. On-device transcription: transcribe each recording using Speech
   framework (on-device recognition only — reject/flag if only
   server-based recognition is available for a locale). Transcript is
   editable after the fact; edits must not desync from the audio
   timeline (tapping a transcript sentence seeks the audio to that
   point).
3. Auto-tagging & mood: run NaturalLanguage tokenization/sentiment on
   each transcript to suggest tags and a mood score. Suggestions are
   editable/dismissible — never silently apply an AI guess as fact.
4. Sketch annotations: attach PencilKit sketches to any entry (finger
   or Pencil), stored alongside the audio/transcript.
5. Bi-directional linking: entries can @-mention/link other entries;
   each entry shows a "linked from" backlinks section computed live
   from the local store (no manual backlink maintenance) — same
   integrity discipline as a graph/notes app: linking, unlinking, and
   deleting an entry must never leave a dangling or duplicate backlink.
6. Search: full-text search across transcripts AND tags/mood, with
   results ranked by a real relevance score you define and document
   (not just substring match order).
7. HealthKit correlation (read-only, explicit permission): show each
   entry's mood alongside that day's HealthKit sleep/activity summary
   if authorized, and degrade to "not connected" honestly if denied —
   never block core journaling on this permission.
8. Home-screen widget + Live Activity: widget shows the latest entry's
   mood/snippet; a Live Activity shows elapsed time and live waveform
   while actively recording, ending cleanly when the recording stops
   or the app is killed mid-recording (no orphaned Live Activity).
9. Share Extension (separate target): accept shared text or a photo
   from other apps and create a new Fieldnotes entry from it.
10. App Intents: "Start a voice entry" and "Search my journal" exposed
    to Shortcuts/Siri.
11. CarPlay: a minimal CarPlay scene for hands-free start/stop
    recording while driving. This requires Apple's CarPlay audio-app
    entitlement, which a personal free developer account cannot
    obtain — if that's confirmed true in this environment, build the
    CarPlay scene code path correctly but record in Gaps that it
    cannot actually run/ship without that entitlement, rather than
    silently omitting the feature or pretending it works.

Priorities, in order: (a) audio-session interruption correctness — a
lost or corrupted recording is the worst possible failure, (b) backlink
graph integrity, (c) honest degradation of every permission-gated
feature (Speech, HealthKit, CarPlay). Use Decimal/Int for anything
numeric that isn't inherently floating (durations in seconds as
TimeInterval is fine; don't invent unnecessary Decimal use here — this
app's money-precision lesson from prior apps doesn't apply, there's no
currency). Seed a "demo entries" toggle in Settings with realistic
sample entries, transcripts, tags, and backlinks so no screen is empty
on first review. Provide a clear way to run it in the iOS Simulator via
Xcode, and call out anywhere CarPlay/HealthKit/Speech behave differently
in Simulator vs. a real device.
```

### Round 1


**Codex (Product Strategist · User Advocate) — Round 1**

Product promise: Fieldnotes is an offline-first iOS voice journal that lets a single user capture diary entries reliably in the real world, then reliably recall them through timeline-anchored, editable transcript snippets, tags, mood hints, backlinks, and local health context without any backend, account, or network dependency.

Primary user and scenario: a privacy-first solo journaler who captures entries while moving through interruptions—walking, commuting, meeting, or driving setup—where the app must not lose or corrupt a recording if the phone rings, Siri appears, or the app is backgrounded.

Core loop: start recording from the app (or Siri/App Intent), capture audio with live waveform while writing a durable local session, finalize safely after interruption or stop, transcribe on-device when available, suggest editable tags and rough mood polarity, allow transcript edits that remain anchored to audio timestamps, maintain backlink integrity via stable entry IDs and live reverse-link computation, and make entries searchable immediately for retrieval and editing.

Hard scope boundaries: in-scope is a single app named Fieldnotes with shared App Group + SwiftData store across app, widget, Live Activity, share extension, and intents, with core loop done to correctness first and widgets/Live Activity next, and share extension/app intents/car-play implemented as code paths with honest gaps where Apple policy or hardware/developer limits block execution; out-of-scope is any fake network fallback, cloud sync, account login, server transcription, or silently claimed features, and out-of-scope for this phase is polishing every surface equally before the interruption-safe recording core and backlink graph are proven stable.

Measurable success criteria: one sentence in review: “Fieldnotes works offline and is trustworthy under interruption,” demonstrated by manual evidence of interruption-safe recording for at least one clean pass each of incoming call, Siri, backgrounding, force-quit during active recording, and low-storage (if feasible), plus 20+ total manual recording runs total; 100% of @-mentions resolve by stable UUID and never break on rename, with no dangling duplicate backlinks after link or delete operations; transcript editing never desyncs tap-to-seek because seeks resolve by immutable anchors; search returns ranked results by a documented relevance score across transcript + tags + mood + metadata and explicitly includes untranscribed entries by tags/mood/sketch; HealthKit is shown as denied/not-connected by default with a clearly visible non-blocking path and optional connected state when authorized; every feature status at later phases is clearly marked as guaranteed, degrades, or gapped with evidence. Biggest risk to avoid: trying to optimize surfaces (widget/widget intent/carplay) before the recorder and data-integrity path is stable, because that produces a polished-looking but untrustworthy product; this risk must be explicitly preserved as a hard sequencing rule.

**Claude (Design Lead · Systems Thinker) — Round 1**

Here's how I'd frame this, coming at it from screens-and-flows first rather than feature list first.

The product promise I'd land on: Fieldnotes is the app where you talk out loud about your day and trust that what you said is still there, still searchable, and still connected to everything else you've said — even when reality (a phone call, a dead Speech locale, a force-quit) tries to interrupt or degrade the capture. The word "trust" is doing real work in that sentence — this isn't a transcription app or a mood tracker, it's a promise that the recording layer and the link graph never lie to you about their own state.

Primary user and scenario: someone journaling solo, in short unplanned bursts — walking, in the car before driving off, decompressing after something happened — who talks for 30 seconds to 3 minutes, expects it to become text they can skim later, and occasionally goes back and stitches entries together conceptually (this connects to what I said last month). The scenario that matters most isn't the happy path of "record → transcript → done," it's "record → interrupted by a call → what happens to the 40 seconds before the call and the 10 seconds after I resume." That's the actual product, UX-wise: the interruption recovery flow needs its own designed states, not just error-toast treatment bolted onto the happy path.

Core loop, as I'd draw it as a flow: tap record → live waveform + elapsed time (recording screen is intentionally boring/stable, no cleverness, because this is the one screen that must never surprise the user) → stop or auto-finalize on interruption → transcript appears with a clear "on-device transcribing…" state if it's not instant → user skims transcript, taps a sentence to confirm audio-seek works, edits a word or two → tag/mood chips appear as suggestions with a visibly different visual treatment from confirmed metadata (dashed border, "suggested" label, tap to accept/dismiss — never pre-checked as if already true) → user optionally @-mentions another entry, sees autocomplete resolve to a real entry by ID → entry saved, backlinks section on the mentioned entry updates live next time it's viewed. That whole loop is the app. Everything else — widget, Live Activity, Share Extension, App Intents, CarPlay, HealthKit — is a satellite view into the same loop, not a second loop.

The information architecture question I want to flag now, because it'll bite later if it's not decided: what are the actual top-level tabs/screens? I'd argue for three: a Timeline/list of entries (the home surface, also what the widget mirrors), Search (its own tab, not just a magnifying glass buried in Timeline, because relevance-ranked search across transcript+tags+mood is a named, documented feature — it deserves to feel like a real destination), and Settings (demo toggle, HealthKit connection state, on-device Speech status per locale). Entry detail is a pushed screen from Timeline or Search, not a tab. I don't think a fourth tab for "graph view" is warranted for v1 — backlinks surface inline at the bottom of an entry, not as a separate visual graph explorer; a literal node-graph view is exactly the kind of scope-creep chrome that would eat build time this app can't spare, and the prompt never asked for one.

Biggest risk to my own framing: I'm designing as if the entry detail screen can stay simple, but it actually has to carry a lot of simultaneous state — audio player position, editable transcript with per-sentence tap targets, tag chips (suggested vs confirmed), a mood indicator, an optional sketch, an @-mention list, and a backlinks section — on one phone-sized screen without anything overlapping or feeling like a form dump. That's the screen most likely to become a cluttered mess if it's not deliberately laid out in collapsible sections (audio player pinned at top, transcript as the main scroll body, tags/mood/sketch/backlinks as a footer stack below the transcript). I'd treat that screen's layout as its own design problem, not an assembly of the other features' UI.

Hard scope boundaries I want stated plainly so nobody quietly expands them later: no cloud sync, no account system, no server-side anything ever, no analytics/telemetry, no third-party SDKs, no in-app purchase or monetization surface, no literal graph-visualization screen, no multi-user/sharing-between-people feature (Share Extension is one-way import from other apps, not sharing entries out to people), no editing of raw audio (trim/splice) — audio is append-only per entry, only the transcript is editable. CarPlay gets zero visual polish time by design (already decided). Live Activity and widget get a single fixed layout each, no user-customizable widget sizes/configurations for v1.

Measurable success criteria, stated so a build-verification pass can actually check them rather than vibe-check them: (1) a recording survives all five named interruption scenarios with zero data loss across 20+ manual runs, verified per-scenario not aggregate; (2) tap-any-transcript-sentence seeks audio within some tight tolerance (I'd say ≤300ms) and this still holds after the user has edited that sentence's text; (3) deleting an entry that other entries mention leaves zero dangling backlinks and the forward mention visibly flips to a broken-link state, verified by an actual before/after check, not just "looks right"; (4) search returns the documented relevance ordering on a fixed two-entry test case, not just "something comes back"; (5) every permission-gated feature (Speech locale support, HealthKit auth, CarPlay entitlement) shows its real state — never a placeholder pretending to be live data — verified by actually toggling permission off and checking the screen, not just reading the code.

One more system-level thing worth deciding now rather than discovering mid-build: what does "entry" mean when Speech transcription hasn't finished yet, or never will (on-device unavailable)? The user needs to be able to record entry #2 while entry #1 is still transcribing in the background — transcription must be async and queued, not blocking, and the Timeline list needs a per-entry state indicator (transcribing / unavailable / ready) so the list itself never lies about what's actually there yet.
