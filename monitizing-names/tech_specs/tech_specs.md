## Final Output

### Architecture overview
A single Next.js (App Router, TypeScript) application running as one Node.js server process — no separate frontend/backend split, no edge runtime. Server Components render the Home page (hero, story, leaderboard) with the seed listing and current offers already in the initial HTML response. Route Handlers under `app/api/*` serve the same Node process. Persistence is a single embedded SQLite file via `better-sqlite3` in WAL mode. No client-side routing beyond the single page; the two sheets (offer form, checkout) are in-memory UI state, optionally reflected in a URL hash for a shareable deep link. This is the smallest architecture that satisfies SSR-first-paint, a real shared backend for the offer list, and the state-machine requirements from design_handoff — a separate API service or hosted DB would add operational surface with no corresponding benefit at this scale.

### Data models
- `Listing` — single row (modeled as a table, not a hardcoded constant, so seed script and schema stay honest): id, headline, disclaimerText, dueMonth, dueYear, storyText, createdAt.
- `Offer` — id, listingId, alias, storyText, `amountCents` (integer, never float — keeps the $9,999,999 adversarial value exact through sort/display), status ('open' | 'hidden'), reportCount, hiddenAt (nullable — soft-delete marker), createdAt (server-assigned, authoritative for the amount-desc/earliest-tiebreak sort), sessionToken (DB-internal only, never serialized to any API response).
- `Report` — targetType ('listing' | 'offer'), targetId, sessionToken, createdAt, with a unique constraint on (targetType, targetId, sessionToken) enforcing one-report-per-session at the DB layer.

### Persistence strategy
Embedded SQLite file (`better-sqlite3`, WAL mode for read concurrency under polling). Offer table indexed on (status, amountCents DESC, createdAt ASC) so the sorted public list is served directly by the query, never re-sorted client-side. Report auto-hide is a soft delete: crossing 3 reports sets `hiddenAt`; public queries filter `WHERE hiddenAt IS NULL`; rows are never hard-deleted, matching the recoverable-not-destroyed requirement from detailed_discussion. SQLite's single-writer serialization makes concurrent near-simultaneous submissions resolve deterministically without explicit application-level locking.

### Testing strategy
Four test classes are treated as non-negotiable, chosen because they map directly to this project's own named risk history rather than generic coverage: (1) content-filter unit tests running abusive-input and legitimate-non-English-name cases side by side; (2) an API test simulating a persistence write failure after the checkout animation would have completed, asserting the failure state renders with entered data intact and that success never renders first; (3) a Playwright pass using the exact pinned adversarial values (60-char alias, three tied amounts, $9,999,999) across light/dark and mobile/desktop; (4) a test that clears localStorage mid-session and confirms a previously-reported offer becomes reportable again without the UI throwing.

## Final Output

### Architecture overview
A single Next.js (App Router, TypeScript) application running as one Node.js server process — no separate frontend/backend split, no edge runtime. Server Components render the Home page (hero, story, leaderboard) with the seed listing and current offers already in the initial HTML response. Route Handlers under `app/api/*` serve the same Node process. Persistence is a single embedded SQLite file via `better-sqlite3` in WAL mode. No client-side routing beyond the single page; the two sheets (offer form, checkout) are in-memory UI state, optionally reflected in a URL hash for a shareable deep link. This is the smallest architecture that satisfies SSR-first-paint, a real shared backend for the offer list, and the state-machine requirements from design_handoff — a separate API service or hosted DB would add operational surface with no corresponding benefit at this scale.

### Data models
- `Listing` — single row (modeled as a table, not a hardcoded constant, so seed script and schema stay honest): id, headline, disclaimerText, dueMonth, dueYear, storyText, createdAt.
- `Offer` — id, listingId, alias, storyText, `amountCents` (integer, never float — keeps the $9,999,999 adversarial value exact through sort/display), status ('open' | 'hidden'), reportCount, hiddenAt (nullable — soft-delete marker), createdAt (server-assigned, authoritative for the amount-desc/earliest-tiebreak sort), sessionToken (DB-internal only, never serialized to any API response).
- `Report` — targetType ('listing' | 'offer'), targetId, sessionToken, createdAt, with a unique constraint on (targetType, targetId, sessionToken) enforcing one-report-per-session at the DB layer.

### Persistence strategy
Embedded SQLite file (`better-sqlite3`, WAL mode for read concurrency under polling). Offer table indexed on (status, amountCents DESC, createdAt ASC) so the sorted public list is served directly by the query, never re-sorted client-side. Report auto-hide is a soft delete: crossing 3 reports sets `hiddenAt`; public queries filter `WHERE hiddenAt IS NULL`; rows are never hard-deleted, matching the recoverable-not-destroyed requirement from detailed_discussion. SQLite's single-writer serialization makes concurrent near-simultaneous submissions resolve deterministically without explicit application-level locking.

### Testing strategy
Four test classes are treated as non-negotiable, chosen because they map directly to this project's own named risk history rather than generic coverage: (1) content-filter unit tests running abusive-input and legitimate-non-English-name cases side by side; (2) an API test simulating a persistence write failure after the checkout animation would have completed, asserting the failure state renders with entered data intact and that success never renders first; (3) a Playwright pass using the exact pinned adversarial values (60-char alias, three tied amounts, $9,999,999) across light/dark and mobile/desktop; (4) a test that clears localStorage mid-session and confirms a previously-reported offer becomes reportable again without the UI throwing.
