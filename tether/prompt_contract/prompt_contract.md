Tether is a long-distance app for any two people separated by miles — partners, best friends, a parent and a kid abroad, siblings on different continents. It turns the exact distance between you into ONE gorgeous, co-created daily artifact you both hold, answer, and post: the **distance card**. ## Core loop (concrete user actions)
1. **Pair.** On first launch you name your person and share a join link/code. The card literally cannot be created solo — the invite is the mechanic, not a growth afterthought. (For solo testing and the UI-crawl gate, a "Preview with a sample partner" path fully simulates the second user so every downstream state is reachable offline.)

4. **Answer.** You type a one-line reply. The card stays half-lit until BOTH have answered — this two-sided gated reveal is the heartbeat of the app. When your person answers, you feel a two-beat "heartbeat" haptic and the card completes: both answers slide in, the tether snaps taut with a crisp tick.
5. **Share.** Pick a skin, toggle animated vs. still, export to Stories/Messages. Free = static PNG with a join watermark; Tether+ = animated MP4/Live Photo.
6. **Archive + streak.** Every completed card threads into a vertical Timeline — your relationship as a scrollable archive — and extends your answer streak.
7. **Count down to reunion.** A Reunion countdown (paid) tracks the next time you'll be together; hitting a milestone or zero produces its own hero card worth posting.

===== MY CONTRIBUTION (QA/Risk, Skeptic hat) =====

Before anyone gets excited about the globe and the amber glow, I want to flag where this spec is going to fight the build in ways that won't show up until someone actually tries to make the gates pass.

The single biggest tension in this prompt is "the invite is the mechanic, not a growth afterthought" versus "must compile and be fully traversable OFFLINE." Those two requirements are in direct conflict unless the sample-partner path is treated as a first-class, fully-scripted state machine — not a demo stub bolted on later. If "Preview with a sample partner" is implemented as a shortcut that skips the state machine, we've built something that looks done but never actually exercises `awaitingBoth → awaitingThem/awaitingMe → complete` with real data races (both answer within the same second, one answers then edits, app is killed mid-submit). I want it explicit in the contract: the sample partner must go through the identical SyncService protocol as a real partner, on a delay timer, so the gated-reveal logic is genuinely tested, not faked with a hardcoded "already complete" card.

Second risk: the design-lint gate ("forbids inline Color(...)/UIColor(...) and raw .font(.system(size:)) anywhere else") is stated as a hard rule but nobody has said how it's enforced — is this a build script (regex/grep over the diff), a SwiftLint custom rule, or just an assertion in code review? If it's not an actual automated gate, it's a promise that silently rots the moment velocity picks up. I'd treat "the lint gate exists and runs" as a testable requirement in its own right, separate from "the palette is respected."

Third: the amber-only rule is a strong, specific, and easy-to-violate constraint. Every progress indicator, every "record" streak flame icon, every selected-tab state, every slider thumb is an obvious place someone reaches for amber because it's the brand color. The failure mode isn't a crash, it's slow bleed — amber creeping onto badges, streak counters, or the paywall CTA "because it needs to pop." The contract needs a bright line: amber = tether arc, two endpoints, and the single "light the tether" primary action. Nothing else. If a later phase wants amber on a badge, that's a violation to flag, not a judgment call to wave through.

Fourth, the two-sided gated reveal is called "the app's core correctness invariant" and told to have test coverage — good, but the prompt doesn't specify what happens on edit-after-submit, on both users answering the same prompt differently after a timezone rollover (whose "day" is it — is Card.date keyed to UTC, to person A's local day, or to person B's? Day boundaries are exactly where long-distance apps break, since the two people are, by definition, in different timezones and "today's card" can mean different calendar days for each person around midnight). I want a decision rule locked now: Card.date is anchored to one canonical timestamp (e.g., UTC day boundary or Connection-creation-anchored day), not to either person's local calendar day, so there's no ambiguity about which prompt is "today's" for both sides.

Fifth, the paywall says "Free = static PNG export, never paywalled for the daily card" but also "Tether+ = more than one connection." What happens to an existing free user's data if they've somehow got two connections (e.g., after a subscription lapses)? The prompt doesn't say — reasonable default: downgrade gracefully, don't delete data, just restrict creation of new connections and lock the UI to the single most-recent one, with the others visible read-only or clearly indicated as locked. This needs to be a stated decision rule so a later phase doesn't invent silent data loss.

Sixth — CoreMotion parallax and Reduce Motion: the prompt says "Reduce Motion → static globe, cross-fade instead of draw-on. Haptics still fire." That's good, but there's no mention of what happens when the simulator (which has no CoreMotion attitude data) is the only offline test environment — parallax must degrade to a neutral/static angle rather than crash or throw when CMDeviceMotion is unavailable, which is the norm in Simulator. I'd make "graceful no-op on missing CoreMotion hardware" an explicit hard requirement, since this is exactly the kind of thing that passes in isolation but crashes the very "traversable in Simulator offline" gate the whole spec is staked on.

Seventh, on the haptics: "Two-beat heartbeat when your person opens/answers" implies a live signal from the partner's action while the app is foregrounded or backgrounded (push-triggered). In the local-first/offline build there's no real partner device — so this haptic can only be demonstrated via the simulated partner's delayed answer while the app is open. That should be stated as the actual testable requirement (haptic fires when the simulated partner's timed answer lands while app is foregrounded), not the (currently untestable-offline) claim about background push haptics, which is out of scope for this build and belongs in the production/sync-seam bucket.
