```
Build a visually stunning, fully offline iOS app called "Aura" — a
daily generative "vibe card." Native Apple stack only: SwiftUI +
SwiftData, Core Image / Metal (CIFilter compositions or a custom
Metal shader) for procedural generative art, Swift Charts for the
recap view, StoreKit 2 for local in-app purchases (no backend needed —
App Store handles receipts/entitlements locally). No accounts, no
network, no third-party SDKs — everything on-device, forever. Follow
the ios-app-factory-rules.

CONCEPT: once a day, the user answers 2-3 quick prompts (a mood
picker, one or two tap-to-select word/emoji chips, optionally the
on-device time of day). From that input plus a per-day deterministic
seed, generate a unique abstract generative-art "Aura" card — think
painterly gradient blooms, particle fields, or flow-field line art,
NOT a literal illustration — paired with a short generated caption
built from a curated local phrase bank (never a hallucinated/unsafe
LLM call — this is deterministic, on-device, and instant). The card
must look genuinely beautiful: this is the single most important
requirement in this build. If the generative output looks like
placeholder gradients or a design-101 exercise, the build has failed
its actual goal even if it compiles and passes gates.

CORE FEATURES (favor complete over broad):
1. Daily check-in flow: fast (under 10 seconds), delightful, satisfying
   micro-interactions (haptics, spring animations) on every tap. Once
   completed, locked until the next calendar day (device local time
   zone) — handle timezone travel and DST without allowing two cards
   the "same day" or skipping a day.
2. Generative card engine: a real, documented deterministic algorithm
   mapping (date seed + mood + chips) -> a reproducible but visually
   varied composition (palette, shape field, motion-blur/particle
   density). Same inputs on the same day always render the same card;
   different days must feel meaningfully different from each other,
   not like the same template recolored. This is the technical heart
   of the app — treat it with the same rigor as an algorithm module,
   not incidental UI.
3. Collection & streaks: a scrollable archive/grid of past cards
   (like a photo grid), a streak counter, and a "your Aura over time"
   trend view (mood distribution via Swift Charts).
4. Monthly/seasonal "Wrapped": after each calendar month, generate a
   shareable recap — a short animated sequence or a single composite
   poster of that month's dominant palette/mood story (Spotify-Wrapped
   style). This is a primary viral surface — must render as a
   beautiful, portrait (9:16) export.
5. Share export: every single card AND the monthly Wrapped must export
   as a high-resolution image (and ideally a short looping video/Live
   Photo-style clip of the generative animation) sized correctly for
   Instagram/TikTok Stories (1080x1920), via the native share sheet.
   A small, tasteful, dismissible-only-via-purchase watermark on free
   exports is the monetization hook (see below) — it must never be so
   intrusive it kills the shareability that drives virality.
6. Monetization (StoreKit 2, local only): one non-consumable "Aura+"
   unlock via native IAP removing the export watermark and unlocking
   extra palette themes + the ability to regenerate a card once per
   day if unsatisfied (free tier: no regeneration). Handle purchase,
   restore purchases, and the Simulator's inability to complete real
   StoreKit transactions honestly — use a local StoreKit configuration
   file for Simulator testing and say so explicitly, don't fake a
   purchase succeeding without going through StoreKit's real API.
7. Widget: home-screen widget showing today's card once generated, or
   an inviting "your Aura is waiting" state before check-in.
8. Notifications (local only, opt-in): a gentle daily reminder if the
   user hasn't checked in yet, respecting Focus/Do Not Disturb norms
   and permission denial gracefully.

PRIORITIES, in order: (a) the generative art must be genuinely
beautiful and varied — treat this as a design/craft problem, iterate
on the actual visual output, not just "does it render"; (b) the
deterministic seeding algorithm must be correct and tested (same
inputs -> same card, always); (c) the share-export pipeline must
produce real, correctly-sized, good-looking image/video files, not a
plain screenshot of the UI. Seed a "demo history" toggle with 30+ days
of varied past cards so the archive/Wrapped/trend screens are never
empty on first review. Provide a clear way to run it in the iOS
Simulator via Xcode, and honestly flag anything StoreKit-transaction-
related that cannot be fully verified without a real device/sandbox
account.
```

### Round 1


**Codex (Product Strategist · User Advocate) — Round 1**

Aura is a private, offline-first iOS app that turns one quick daily mood ritual into a deterministic, beautiful “Aura” card artifact you can revisit, collect, and share, while enforcing a clear free/paid line for export polish.  

The primary user is an aesthetic-minded mobile user who wants a fast, low-friction daily moment—usually in the morning or before bed—with no setup burden: tap a mood and 1–2 chips, get a unique card in the same session, and feel motivated to return tomorrow because the card feels intentionally crafted, not generic.  

The core loop is: user opens app → check-in UI with haptic/spring-feedback taps → seed-driven generative render from date + mood + chips (+frozen generation context) → cache-rendered card + caption saved locally and shown as today’s Aura → optional archive/Wrapped/share/export interactions feed streak and mood trend engagement → next local day the check-in resets for a new card.  

Hard scope boundaries: build one app (`Aura`, iOS 17+, SwiftUI + SwiftData + Core Image/Metal + Swift Charts + StoreKit 2), no accounts, no network, no third-party SDKs, no cloud/iCloud sync, and no fake IAP behavior; render once at generation time and persist the image for all consumers (UI, widget, export); watermark is small, dismissible-only via purchase, and never blocks the center of the art; StoreKit verification honesty must be explicit in docs; no video export as a requirement for this phase.  

Measurable success criteria: first rendered card appears in under 10 seconds on first run without forced onboarding; identical inputs for the same day always produce identical cards while adjacent days/chip combinations look materially different; no duplicated cards from timezone/DST/backward-clock edge cases and no duplicate “same-day” cards after manual time changes; demo mode clearly marks seeded days and is excluded from real streak/counters unless explicitly enabled; archive and trend/wrapped surfaces feel alive within seeded history (not empty-state theater) with smooth empty/loading/success/error states; exported 1080×1920 images are clean, card-only visuals with correct aspect and meaningful caption placement.  

Biggest objection I’d defend against is a technically correct build that looks like a polished placeholder gradient workshop instead of an art object, so the final output must preserve a strict visual-quality bar: actual rendered art review across multiple mood/seed/chip combinations before considering this phase complete.

**Claude (Design Lead · Systems Thinker) — Round 1**

Thinking about this as a daily object a person picks up twice — once in the morning or at night to check in, and once more to glance at the widget or flip through the archive — the one-sentence promise I'd lock in is: Aura turns a ten-second daily mood check-in into one deterministic, genuinely beautiful generative-art card that the user collects, tracks over time, and can share, entirely on-device with no account and no network. The primary user is someone who already has some kind of small daily ritual (journaling app, horoscope app, habit tracker) and wants the payoff to feel like receiving something rather than logging something — they open the app at a fairly predictable moment (first coffee, or right before bed), and the entire interaction from "empty home screen" to "card in hand" needs to survive being done half-asleep with one thumb.

On information architecture, I'd settle the navigation shape now rather than let it drift: a four-destination structure — Today, Archive, Wrapped, Settings — with the mood-distribution/streak trend view folded in as a segmented control inside Archive rather than its own tab. Five-plus tabs on an app this size reads as feature-padding, and trends are naturally "archive, but summarized," not a separate destination someone reaches for independently. Today is a single screen with three states baked in from day one: not-yet-checked-in (the prompt flow), checked-in-and-revealed (today's card, streak count, share button), and — this is the one I want written down explicitly now because it's easy to lose — the widget-tap deep link. If the user taps the "your Aura is waiting" widget state, it has to drop them directly into the check-in flow, not just foreground the app to a screen that still requires a second tap; that's a real lever on the sub-10-second promise and it's an IA decision, not a later polish item.

The core loop, stated as a state machine rather than a feature list: app opens → check device-local calendar day against last-completed-day → if already done, render cached card; if not, enter check-in → mood pick → chip pick(s) → optional time-of-day capture, frozen at this exact moment → generate once, persist the rendered image + its recipe → reveal with haptic + spring → archive/streak/trend all update from that one persisted record → optional share export → close. Repeats every calendar day; every month boundary additionally unlocks a Wrapped recap built from that month's persisted cards.

Two edge cases in that loop I don't think should wait for a later phase to surface, because they're IA/state-machine decisions, not implementation detail: first, what happens if the app is force-quit mid check-in — I'd resolve this as check-in being non-committing until the final step, so a partial mood-pick with no chips yet is not "in progress" from the lock's point of view, it just restarts the flow on relaunch (pre-filling the last partial pick is a nice-to-have, not required). Second, first-launch default state: per the earlier demo-history decision, a genuine brand-new install should show a real, well-designed empty state on day one — not demo data turned on by default — with demo mode being something a reviewer or the user explicitly flips on, visibly labeled the whole time it's active, and off by default for anyone actually using the app for real.

Hard scope boundaries I want in the record for this phase specifically, beyond what's already locked upstream: no social layer of any kind (no feed of other users' cards, no comments, no following — this is a private object, not a shared one); no editing or undoing a submitted check-in once the day is locked (the card is a record of that day, not a draft); at most one canonical card per calendar day, where a paid regeneration replaces the stored card for that day rather than creating a second entry the archive has to reconcile; and no cross-device continuity of any kind, including no "your data is safe if you reinstall" promise, since that would require iCloud sync we've already excluded.

For success criteria I'd hold the app to: time-to-first-card under 10 seconds of actual interaction with zero forced tutorial screens; the check-in state machine handling force-quit, timezone travel, and backward clock changes without ever producing two cards for one day or silently skipping a day; archive, trend, and Wrapped screens never looking empty-by-accident (either genuinely empty-and-well-designed on a fresh real install, or populated by clearly-labeled demo data); and a share export that a person would actually post, which I'd operationalize as "not visibly a screenshot, correct 1080x1920 dimensions, watermark never touching the focal art or caption." The one thing I'd flag as explicitly out of scope for this phase to resolve, and instead handed to whatever phase designs the actual generative algorithm: the exact size of the mood/chip vocabulary and how many seed dimensions it produces — that's an architecture decision, not a product-promise decision, and this phase shouldn't pretend to settle it by accident.
