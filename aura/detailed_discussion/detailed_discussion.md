Codex is still dark this round, so I'll keep pushing on my own list rather than padding it with restatement — there are a few real gaps I skipped over the first time through.

The one that bugs me most: nobody has said what happens when a user buys Aura+ *in the middle of a day that already has a completed card*. The expanded palette library is one of the three unlocks, and the deterministic engine presumably maps mood/chip/date to a composition using whatever palette set is "active" at generation time. So what happens on the day someone actually converts? They check in at 8am on the free tier, get a card from the free palette set, then buy Aura+ at 2pm. Does today's already-rendered, already-persisted card silently upgrade to draw from the new palette set retroactively? It shouldn't — that would break the "rendered once, persisted, never re-derived" architecture decision from product_research, and it would also mean the same (date+mood+chips) seed produces two different outputs depending on purchase timing, which is a determinism violation nobody's named yet. I think the rule has to be explicit: entitlement changes affect only cards generated *after* the purchase, plus the one regeneration credit if the user chooses to spend it — a purchase must never auto-mutate an already-persisted render. This is a one-line rule but it's exactly the kind of thing that gets silently gotten wrong if "check entitlement, pick palette set" is written as a live computed property instead of something snapshotted at generation time.

Second thing: the international date line case is genuinely different from the DST/backward-clock cases we already covered, and I don't think our existing decision actually handles it. DEC-prompt_contract-006 and the per_app_product_brief timezone rule are both framed around "don't let someone get two cards in one day or skip a day via clock manipulation" — good, that covers cheating and DST. But picture someone flying Tokyo → LA, which crosses the date line westward in wall-clock-forward time: they could legitimately complete a check-in at 11pm Tokyo time, land ~10 hours later, and now it's still "yesterday" in LA local time. Or flying the other direction, they could gain a day and suddenly be eligible to check in twice within an 18-hour span with no manipulation at all. If the lock is keyed purely to "last completed calendar day in the active timezone," a legitimate traveler going eastward across the Pacific could rack up two check-ins in under 24 real-world hours, and going westward could produce what looks like a skipped day even though they did nothing wrong. Neither of those is "cheating" but both will look like bugs to whoever's testing this by literally changing the Simulator's timezone, which is exactly the test the QA criteria already call for. I don't think we need to solve this with some elaborate real-time-elapsed-hours rule — that adds complexity for a vanishingly rare case — but we do need to explicitly decide the tradeoff and write it down: local calendar day wins, full stop, even if that means a transoceanic flight yields two cards in under 24 hours or what looks like a one-day gap in the streak. That's a fine outcome, but if we don't say it out loud now, whoever builds the streak logic will "fix" it into something more convoluted the first time they see the edge case in testing, and probably break the simpler DST case doing it.

Third, smaller thing extending my own point from last round: I said the widget needs an explicit reload trigger on check-in completion. It also needs that same trigger on regeneration — if a paying user taps regenerate, the widget is showing a cached render of the pre-regeneration card until something tells WidgetKit to refresh. That's the same bug in a second location, not a new bug, but it needs to be named as its own call site or someone will wire the reload into the check-in-completion function and consider the job done, missing the second path entirely.

Last one, and I think this is a real product/support gap rather than a technical one: we've separately decided (a) no cloud sync, no cross-device/reinstall continuity, and (b) restore purchases must have an honest, defined "nothing to restore" / success state. That's technically correct per our own boundaries, but "I restored my purchase and lost everything" is exactly the one-star-review sentence this produces if the restore success state doesn't say anything about it. The fix is cheap — the restore confirmation copy should say something like "Aura+ restored. None of this contradicts anything on the books; it's four concrete additions: no retroactive entitlement mutation of already-persisted cards, an explicit date-line/travel tradeoff decision (local-calendar-day wins, even if it produces a same-flight double-checkin or apparent gap), widget reload on regeneration as its own call site, and restore-purchase copy that preempts the "did I just lose my history" support ticket.
