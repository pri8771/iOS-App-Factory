## Original Prompt

```
Build a polished, fully offline iOS spaced-repetition flashcard app called "Recall". Native Apple stack ONLY: SwiftUI + SwiftData for persistence, Swift Charts for stats. No backend, no accounts, no third-party SDKs, no network of any kind — the app must work in airplane mode forever, all data on-device. Follow the ios-app-factory-rules. Runnable in the iOS Simulator via Xcode; provide clear run instructions.

HARD RULE ON GAPS: Anything that would need infrastructure this project cannot provide (cloud sync, shared/community decks, a deck marketplace) must NOT be faked or stubbed. Record each honestly as a gap with a short note on what building it for real would take. Do not add placeholder UI that pretends these work.

CORE FEATURES (favor complete over broad):
1. Decks & cards: create/edit/archive decks; cards have a front, back, and optional note. Card editing must be fast and keyboard-friendly.
2. Spaced-repetition scheduling: implement the SM-2 algorithm (ease factor, interval, repetition count) with Again/Hard/Good/Easy grading. THIS IS THE HEART OF THE APP. Implement it as its own standalone, pure, tested module — provably right, not plausibly right. Unit tests MUST cover: first reviews, lapses resetting the interval, ease-factor floors, and day-boundary handling in the device's local time zone (a "day" is a calendar day).
3. Review session: shows due cards for a chosen deck (or all decks); front → tap to reveal → grade. Session summary at end (cards reviewed, again-rate, time spent). Must handle interruption gracefully — quitting mid-session loses nothing.
4. Stats: per-deck and overall — due-forecast bar chart for next 30 days, daily review-count history, and retention rate (% graded Good/Easy). Handle empty and sparse data gracefully.
5. Deck import/export: export any deck to CSV; import cards from a two-column CSV (front, back) with a preview step and per-row error reporting — never silently drop a row.
6. Review reminders: one optional LOCAL notification per day ("You have N cards due") at a user-chosen time; respect permission denial gracefully. No push, no server.

PRIORITIES (in order): (1) SM-2 module correctness above all — proven via its tests; (2) review-flow speed; (3) honest empty states. Include a "demo data" toggle in Settings that seeds two decks with a realistic review history so stats screens are never empty on first look.
```

### Round 1


**Codex (Product Strategist · Pragmatist) — Round 1**

Design language: “Scheduled Trust Instrument” — the app should feel like a precision instrument for spacing your memory, not a deck scrapbook or gamified trainer, so every visual element should communicate timing, state, and next action clearly before asking for the user’s attention.  
Emotional target: The first screen should make the user feel in control and confident that every review action is real and immediately persisted.  
Signature interaction: A “reveal-and-grade” card strip where the card front is a high-contrast panel with a single-tap reveal, then four graded actions (Again/Hard/Good/Easy) animate to a crisp queued-state transition and instantly update the next-card queue without any modal delay, reinforcing speed + trust.  
Default look to reject: plain SwiftUI `List` + standard `TabView` + default `Text`/`Button` styles. Three concrete differences: replace flat rows with grouped, card-like deck modules that display due state and cap status together; replace generic tab chrome with a fixed 3-tab shell using semantic icon+text labels and per-tab semantic surfaces so no control is purely icon-only; replace default control-heavy forms with a keyboard-first review composer that keeps focus and action context across rapid card entry; replace default notification/settings surfaces with explicit honesty messaging (what’s blocked, what’s allowed offline, and why some items are not present).  

Screen inventory:  
Study tab: Deck Library, Add/Edit Deck, Card Quick-Add/Edit, Study Scope selector, Review Session, Session Summary.  
Stats tab: Overview, Per-deck Analytics, Forecast Drill-down, Sparse/Empty Stats guidance.  
Settings & Tools tab: App Setup + plan status, Notification controls (global toggle + per-deck times), CSV import/export toolchain (preview/commit flow), Demo Data, Subscription status (restore/plan text), Gap & Limitations register.  

Primary user flow: Launch into Study tab → Empty/loading/ready deck library → create deck or study selected deck/all decks → review session starts with due-filtered cards by current local day/timezone → front/tap reveal/grade with immediate sync → flow returns to next card or completes → completion summary only after full queue processed → return to deck list with current due counts updated; from Settings Tools user can import/export/seed demo/set reminders/adjust plan, and at any time can inspect stats with no dependency on completing review.  

State model per screen:  
Deck Library has Loading, Empty (no decks), Loaded (deck cards + due pills + archived bucket), Muted-Capped (plan warning but no data loss), and Error.  
Deck/Card Editor has Idle, Typing (front/back/note focused and validating), Save-In-Flight, Saved, and Save-Failed with retry + inline error text.  
Review session has Ready (due query snapshot), Revealing, Grading (button-selected), Saving (explicit persisted point), Interrupted (in-memory card pointer restored from persisted progress), and Completed (summary state only).  
Session Summary has None (hidden), Completed (cards/reliability metrics), and Dismissed/Return.  
Stats Overview has Empty (no real activity), Sparse (1–2 points with placeholders), and Populated with three chart states + explanatory empty microcopy for missing history.  
CSV Import has File-Chosen, Parsing, Preview (per-row status: valid / malformed-reason / duplicate / BOM / encoding / CRLF-LF / cap-blocked), Commit-Pending, Importing, and Completed/No-Import states.  
CSV Export has Deck-Selected, Exporting, Success with file save confirmation, and Permission/Share Sheet unavailable fallback message.  
Reminder settings have Enabled/Denied (with OS permission path), Scheduled, Recompute-Pending (post-change refresh), and No-Due (count suppression).  
Demo Data toggle has Off/On-Visible, On-Catalog, and Removed (all demo artifacts fully purged from real aggregates).  

Accessibility notes:  
All grading actions must include explicit text labels and VoiceOver hints, never color-only states; focus order must stay stable during reveal and grading; progress and due counts use plain language for screen readers; all charts include textual alternatives for no-voice-over users to understand “0/low/sparse” states; error and empty states must be announced in full sentence form; dynamic text should never collide with fixed geometry (sized containers, predictable row heights).  

Biggest risk: the design can drift into polished extras and accidentally imply outcomes that are not yet true (for example, summaries or stats that appear before session completion), which breaks the trust claim more than any missing flourish. The final phase output must preserve this contract as the core design principle: every visible state must be truthful, every destructive/plan-limit state must be explicit, and no placeholder outcome screens or disabled affordances are allowed for blocked/in-scope-missing infrastructure.

**Claude (Design Lead · User Advocate) — Round 1**

I'll ground this in a specific person rather than an abstract user: Maria, a nursing-license candidate with about 800 pharmacology cards, who drills on the subway with no signal, twice a day, in ten-minute bursts, and who switched to Recall specifically because a previous app once told her a session was "complete" and then she discovered on her laptop that half her grades never saved. Screen inventory, mapped onto the already-locked 3-tab shell. ## Final Output

**Design language:** "The Honest Ledger" — the app should read like a well-kept logbook, not a gamified trainer: calm, information-dense, almost no ornamental color. Tabular numerals for anything that counts (due counts, chart axes). A single reserved amber accent used only for "due today" badges and genuinely-confirmed-save moments; everything else lives in an ink/graphite palette. Rationale: this app's whole competitive claim is that it never lies about what happened, and Duolingo-style gamification (streak flames, confetti, engagement color) reads to an ex-Anki/Quizlet audience as manipulation, not motivation — the opposite of the trust this app is selling.

**Emotional target:** On the main screen, the user should feel the specific calm of "I know exactly where I stand today" — not excitement, not urgency, not streak-guilt.

**Signature interaction:** Tap-to-reveal settles the answer into place in under 200ms with no bounce or overshoot (explicitly not a 3D card-flip — cute once, annoying by card #40, and review-flow speed is priority #2, non-negotiable). The four grade buttons rise from the bottom edge in the same beat, each carrying a distinct haptic weight on an ascending ladder from Again (light) to Easy (firm), so grading has a tactile signature a user can feel without fully looking at the screen.

**Rejected default look, named concretely:** a plain `NavigationStack` `List` of decks with disclosure chevrons; a stock `Form` for settings; system blue as accent/links; four equal-width color-coded (red/orange/green/blue) grade pills with no other distinguishing feature; a default Swift Charts bar chart with generic gridlines and no direct labeling; a green "Saved!" toast after every grade. **Screen inventory (3-tab shell):**
- *Study*: Deck List (due counts, "Study All" entry, empty state for zero decks, distinct "all caught up" success substate), Deck Detail/card list (archive toggle, add-card entry), Card Editor sheet (front focused on open, Return advances fields, "Save & Add Another"), Review Session (progress indicator, reveal/grade loop, honest "End Session" affordance), Session Summary (reachable only on full queue completion).
- *Stats*: Overview (forecast/history/retention, demo data excluded by default) and per-deck drill-down, each with distinct empty vs. sparse vs. success states.

**Primary flow:** Launch → Study tab, deck list with due counts already computed → pick a deck or Study All → reveal/grade loop with immediate per-card persistence → summary only if the queue genuinely finished → back to deck list with counts reflecting reality. A user can live entirely in this loop and never open Stats or Settings.

**State model highlights:** Deck List — loading/empty/success/"all caught up"/plan-capped/error. Card Editor — idle/typing/save-in-flight/saved/save-failed-with-retry. Review Session — ready/revealing/grading/saving/interrupted-resume/completed, plus a "cap hit mid-session" state rendered as a small non-blocking inline notice (never a modal, so it doesn't break tap rhythm) per the locked requirement that hitting a cap must not corrupt or block an in-progress session. Session Summary — none/completed/dismissed, never fabricated. Stats — empty/sparse/populated with distinct copy per state, never a chart drawn from fabricated-looking flat data. CSV Import — file-chosen/parsing/preview-with-per-row-errors/importing/result. Reminders — not-asked/granted/denied, each with honest, non-nagging copy.

**Accessibility notes:** Grading buttons carry real accessibility labels ("Again, forgot," etc.), not glyphs alone — satisfied structurally by the shape/position/label staircase, not a tooltip bolted on later. Card front/back text scales with Dynamic Type including accessibility sizes without pushing grade buttons off-screen (card content scrolls; the button area is reserved in the bottom safe area). Reduced-motion disables the reveal-settle animation; haptics remain since they aren't motion. Palette is contrast-checked in both light and dark. Charts carry Swift Charts accessibility summary labels so due-forecast numbers aren't locked behind a visual-only bar.

## Final Output

**Design language:** "The Honest Ledger" — the app should read like a well-kept logbook, not a gamified trainer: calm, information-dense, almost no ornamental color. Tabular numerals for anything that counts (due counts, chart axes). A single reserved amber accent used only for "due today" badges and genuinely-confirmed-save moments; everything else lives in an ink/graphite palette. Rationale: this app's whole competitive claim is that it never lies about what happened, and Duolingo-style gamification (streak flames, confetti, engagement color) reads to an ex-Anki/Quizlet audience as manipulation, not motivation — the opposite of the trust this app is selling.

**Emotional target:** On the main screen, the user should feel the specific calm of "I know exactly where I stand today" — not excitement, not urgency, not streak-guilt.

**Signature interaction:** Tap-to-reveal settles the answer into place in under 200ms with no bounce or overshoot (explicitly not a 3D card-flip — cute once, annoying by card #40, and review-flow speed is priority #2, non-negotiable). The four grade buttons rise from the bottom edge in the same beat, each carrying a distinct haptic weight on an ascending ladder from Again (light) to Easy (firm), so grading has a tactile signature a user can feel without fully looking at the screen.

**Rejected default look, named concretely:** a plain `NavigationStack` `List` of decks with disclosure chevrons; a stock `Form` for settings; system blue as accent/links; four equal-width color-coded (red/orange/green/blue) grade pills with no other distinguishing feature; a default Swift Charts bar chart with generic gridlines and no direct labeling; a green "Saved!" toast after every grade. Concrete replacements: (1) decks are custom card modules showing a due-count chip in tabular numerals plus a day-progress bar, not disclosure-chevron rows; (2) grading is an ascending staircase of four distinctly-shaped/positioned/labeled buttons, not same-shaped color pills, so color-blind and VoiceOver users read effort level from shape and position, not hue; (3) no system blue anywhere — ink/graphite palette with the single reserved amber accent; (4) the 30-day forecast chart visually and directly labels "today" rather than burying it as one more gray bar; (5) no post-grade toast/banner — confirmation is structural only (card leaves the due stack, counter silently decrements), because a "Saved" banner mid-session visually implies completion the app hasn't reached yet.

**Screen inventory (3-tab shell):**
- *Study*: Deck List (due counts, "Study All" entry, empty state for zero decks, distinct "all caught up" success substate), Deck Detail/card list (archive toggle, add-card entry), Card Editor sheet (front focused on open, Return advances fields, "Save & Add Another"), Review Session (progress indicator, reveal/grade loop, honest "End Session" affordance), Session Summary (reachable only on full queue completion).
- *Stats*: Overview (forecast/history/retention, demo data excluded by default) and per-deck drill-down, each with distinct empty vs. sparse vs. success states.
- *Settings & Tools*: root list; CSV Export (deck picker → share sheet); CSV Import (file picker → per-row status preview table [OK/malformed-reason/duplicate/BOM/encoding/CRLF-LF/cap-blocked] → confirm → result); Reminders (tri-state permission handling: not-asked/granted/denied-with-Settings-path, plus per-deck time override for Plus); Demo Data toggle (visible description of what removal purges); Plan/Subscription (Free vs. Plus comparison, purchase, Restore Purchases, offline-purchase-exception copy stated plainly); Gap & Limitations register as its own real, readable screen.

**Primary flow:** Launch → Study tab, deck list with due counts already computed → pick a deck or Study All → reveal/grade loop with immediate per-card persistence → summary only if the queue genuinely finished → back to deck list with counts reflecting reality. A user can live entirely in this loop and never open Stats or Settings.

**State model highlights:** Deck List — loading/empty/success/"all caught up"/plan-capped/error. Card Editor — idle/typing/save-in-flight/saved/save-failed-with-retry. Review Session — ready/revealing/grading/saving/interrupted-resume/completed, plus a "cap hit mid-session" state rendered as a small non-blocking inline notice (never a modal, so it doesn't break tap rhythm) per the locked requirement that hitting a cap must not corrupt or block an in-progress session. Session Summary — none/completed/dismissed, never fabricated. Stats — empty/sparse/populated with distinct copy per state, never a chart drawn from fabricated-looking flat data. CSV Import — file-chosen/parsing/preview-with-per-row-errors/importing/result. Reminders — not-asked/granted/denied, each with honest, non-nagging copy.

**Accessibility notes:** Grading buttons carry real accessibility labels ("Again, forgot," etc.), not glyphs alone — satisfied structurally by the shape/position/label staircase, not a tooltip bolted on later. Card front/back text scales with Dynamic Type including accessibility sizes without pushing grade buttons off-screen (card content scrolls; the button area is reserved in the bottom safe area). Reduced-motion disables the reveal-settle animation; haptics remain since they aren't motion. Palette is contrast-checked in both light and dark. Charts carry Swift Charts accessibility summary labels so due-forecast numbers aren't locked behind a visual-only bar.
