Build a polished, fully offline iOS spaced-repetition flashcard app called "Recall". Native Apple stack ONLY: SwiftUI + SwiftData for persistence, Swift Charts for stats. PRIORITIES (in order): (1) SM-2 module correctness above all — proven via its tests; (2) review-flow speed; (3) honest empty states. Include a "demo data" toggle in Settings that seeds two decks with a realistic review history so stats screens are never empty on first look.

The product promise is: Recall lets offline-first self-directed learners move through flashcards on-device with an auditable, deterministic SM-2 review engine that keeps every due date and progress state trustworthy even when interruptions happen.

The core loop is: quickly create/edit keyboard-driven decks and cards, choose a deck or all-decks review, flip front to back, grade with Again/Hard/Good/Easy, persist each grade immediately, and return to the next due card until the queue is complete, then review a summary and continue via simple daily habits plus optional reminders.

**Claude (Design Lead · Systems Thinker) — Round 1**

Here's my read on this, coming at it as the person who has to actually draw the screens and live with the edge cases.

The one-sentence promise I'd lock in: Recall is an offline flashcard app that tells you exactly which cards you need to review today and never lies to you about your progress. Everything else — decks, CSV, stats, reminders — is in service of that one sentence. If a proposed feature doesn't serve "show me the right cards today, honestly," it doesn't belong in this build.

Primary user and scenario: someone with an existing pile of atomic facts (vocab, exam terms, whatever) who opens the app once or twice a day, often with no connectivity, taps into a deck or "all decks," burns through the due stack in a few minutes, and closes the app. The scenario I keep coming back to as the one that has to be bulletproof is: user is mid-review on a subway, loses the app to a phone call or the OS just kills it, reopens ten minutes later. If that moment doesn't feel seamless — if a graded card reappears, or the session summary shows numbers that don't match what actually happened — the entire "provably right" premise collapses in the user's head even if the SM-2 math underneath is flawless. Design-wise this means the review screen can never treat the session as a single in-memory object that gets flushed at the end; each grade has to feel like a saved fact the instant you tap it, not part of a batch waiting to commit.

Core loop, as I'd draw it: Home (deck list, each deck showing its due count) → tap a deck or "Study All" → Review Session (front, tap/space to reveal back, then Again/Hard/Good/Easy) → repeat until due stack is empty → Session Summary (count, again-rate, time spent) → back to Home, due counts updated. That's it. Stats and CSV and Settings are satellite screens reachable from a tab bar or a menu, not part of the loop itself — a user who never opens Stats in their life should still get the full value of the app.

On information architecture, I'd push for a simple tab structure: Study (deck list + review entry), Stats, Settings — three tabs, nothing deeper. Deck detail (edit cards, archive, export/import) hangs off tapping a deck from the Study tab, not its own tab. Card editing needs to be a very boring, very fast form: front field, back field, optional note, and hitting return/tab should move you to the next field or the next new card without touching the mouse/trackpad-equivalent — this is the one place where "keyboard-friendly" is a real constraint we could easily under-build if we treat it as a nice-to-have SwiftUI form instead of designing the tab order deliberately.

The scope boundary I want stated explicitly and not softened: no sub-decks, no card media, no cloud, no accounts, no social — already locked upstream, but I'll add one from a systems-thinking angle: no cross-deck merge or dedup logic, no "smart" auto-tagging or difficulty inference beyond what SM-2 itself produces. The temptation on a "polished" app is to sprinkle in one clever feature (auto-suggested deck from CSV headers, smart deck recommendations) that's technically local-only but adds a whole new correctness surface unrelated to the SM-2 core. I'd rule that class of feature out entirely, not just the infra-dependent ones.

The one open question flagged from the prior phase — whether demo-seeded decks count toward real stats — I'll resolve now rather than let it drift: demo decks must be visibly tagged (a persistent badge/label wherever they appear: deck list, review session header, stats breakdowns) and excluded from the "overall" stats aggregate and any streak by default, with per-deck stats for them shown separately if the user drills into that specific demo deck. Reasoning: the entire point of the demo toggle is "let a reviewer see populated charts without lying about the user's real history." If demo reviews silently blended into the real retention rate, then (a) turning demo data off later would need to somehow un-blend history that was never separable, and (b) a real user's very first honest "0% because I haven't reviewed anything yet" empty state — which this project explicitly prioritizes as a design value — would be quietly replaced by fabricated numbers. That's a contradiction we shouldn't ship. Demo data should be trivially removable (a Settings action that deletes the two seeded decks and everything tied to them) with no residue in real stats.

Measurable success criteria I'd hold this build to: (1) SM-2 unit tests pass and demonstrably match a known external reference progression, zero tolerance for "close enough"; (2) a scripted force-quit-mid-session test shows zero data loss — graded cards stay graded, ungraded cards stay due; (3) every one of the six core screens (deck list, review, session summary, stats, CSV import preview, settings/reminders) has a real, designed empty state, not a blank screen, verified by actually emptying the data and looking; (4) CSV round-trip (export a deck, reimport it) reproduces every card with zero silent drops, verified against a real fixture, not just a hand-written one; (5) the whole app runs start-to-finish in airplane mode with zero crashes or hangs from any implicit network call. If any of those five can't be demonstrated, the app isn't done, regardless of how much UI exists.

The biggest risk to my own framing: by insisting on such a narrow three-tab, no-side-features scope, we could end up with something that feels thin next to Quizlet-caliber apps. I think that's an acceptable trade given the audience already established — but it means the visual/interaction polish (typography, spacing, transitions between reveal and grade, the "swoosh" of a card leaving the due stack) has to carry a lot of the "polished" promise on its own, since we're deliberately not carrying it with feature breadth.
