**Claude (Frontend Engineer · Visionary) — Round 1**

Concurrency and state-ownership are the parts of this app that are easy to get subtly wrong even with every prior decision already locked, so that's where I want to plant the flag for tech_specs, plus one genuinely new idea for review speed.

Module layout: two local Swift packages plus the app target. `RecallScheduling` holds `Clock`/`SystemClock`, `Grade`, `SchedulingState`, and `SM2Engine` — zero Foundation date singletons, everything takes an injected `now: Date` and `calendar: Calendar`. `RecallCSV` holds `CSVRow`, the row-status enum, `CSVParser.parseImportPreview`, and `CSVParser.exportCSV` — also pure, no I/O, callers hand it `Data` and get `Data`/`[CSVRowStatus]` back. Both ship their own Swift Testing targets and are added as local package dependencies of the app target, not folder references. Inside the app target: `Persistence/` (the three `@Model` types, `ModelContainerFactory` with the versioned-schema/migration-plan scaffolding and the error-recovery path, and repository protocols with SwiftData-backed implementations), `Services/` (`ReminderScheduler`, `PlanGate`, `DemoDataSeeder`, `GapRegisterContent`), `Features/Study|Stats|Settings/` each with view + `@Observable` view-model pairs, `Navigation/` with one `Hashable` route enum per tab, and `DesignSystem/` holding `Theme.swift` plus the locked component set including `GradeStaircase`, `DemoDataTag`, `InlineCapNotice` as their own files.

On data models: `Deck(id, name, createdAt, archivedAt: Date?, isDemo, reminderHour: Int?, reminderMinute: Int?)`, `Card(id, front, back, note: String?, easeFactor, intervalDays, repetitionCount, dueDate, lastReviewedAt: Date?, isDemo, deck relation)`, `ReviewLog(id, timestamp, grade, easeFactorBefore/After, intervalBefore/After, repetitionBefore/After, card relation)` — append-only enforced by simply never exposing an update method on the repository, only `insert`. Deck→Card and Card→ReviewLog are both cascade-delete relationships. `isDemo` on Card is written once at creation from the parent deck and never re-derived.

The concurrency boundary I want explicit in the spec: there is exactly one `ModelContainer`, and the `ModelContext` that view models write through is main-actor-confined — every grade save and every deck/card CRUD call happens on the main actor, synchronously, as already locked. But stats aggregation (30-day forecast, history, retention) must NOT run on that same path inline in a view's `body`, or every re-render recomputes a full table scan over `ReviewLog`. So I want a second, background `@ModelActor` — `StatsComputationActor` — that owns its own read-only `ModelContext` against the same container, triggered by `ModelContext.didSave` notifications (or after a session ends), and publishes results into a small `@Observable @MainActor StatsCache` that chart views simply read. This is a genuinely separate concurrency domain from the write path and needs to be named as such in the spec, not left as "compute stats somewhere." Similarly, CSV parsing of a multi-hundred-row file is pure CPU work with no MainActor requirement — it should run via a plain `Task` off the view model's main-actor-inherited context by explicitly awaiting a `nonisolated` parse function, not block the import-preview screen while it churns.

State management and navigation: three independent `@Observable` view models rooted per tab, each owning a `NavigationPath`-equivalent typed route array (`[StudyRoute]`, `[StatsRoute]`, `[SettingsRoute]`) rather than raw `NavigationPath` type-erasure, so parallel build lanes get compile-time-checked routes instead of stringly-typed ones. `ReviewSessionViewModel` is the one place holding the locked snapshot-array architecture concretely: `queue: [PersistentIdentifier]`, `currentIndex: Int`, and a `grade(_:)` method that does the synchronous save then advances the index — never re-fetches. `PlanGate` is a single `@Observable` object owning cap math (deck count, non-demo card count vs. Free limits) and StoreKit entitlement state, injected once via environment so cap checks in the card editor, CSV import preview, and deck creation flow all read the same source rather than three separate cap-counting implementations drifting apart.

My one push beyond what's already locked: give the review session real hardware-keyboard acceleration — space or return to reveal, and 1/2/3/4 (or arrow keys) mapped straight to Again/Hard/Good/Easy via `.keyboardShortcut`, additive to the existing tap-based staircase, with a small `Meta`-styled hint row so it's discoverable rather than a hidden trick. This is genuinely free from a risk standpoint (system API, zero new frameworks, doesn't touch the locked accessibility contract since it's purely additive to tap targets that still work identically) and it's a real difference for the persona this app is built for — someone doing hundreds of cards a day is exactly who benefits from never touching the screen between reveal and grade, and it's a direct, uncomplicated expression of priority #2. The risk I'd flag on my own idea: it must not become a second, undocumented way to satisfy the non-color-dependent grading requirement — VoiceOver users still get the staircase's real accessibility labels, keyboard shortcuts are a bonus for sighted power users, not a replacement path, and reduced-motion/Dynamic Type behavior must stay exactly as already specified regardless of input method.

Testing strategy maps directly onto the layers above: `RecallSchedulingTests` and `RecallCSVTests` are pure Swift Testing suites with zero SwiftData/UIKit; a `RecallPersistenceTests` target runs CRUD/cascade/append-only assertions against an in-memory `ModelContainer`; `RecallIntegrationTests` covers `StatsComputationActor` triggering off save notifications, `ReminderScheduler` reschedule logic at the four refresh points, and CSV import preview → commit; `RecallUITests` holds the force-quit `app.terminate()` test and the Study-All multi-deck reorder-proofing test already required. The one thing I want the tech spec to preserve verbatim from this pass: the background stats actor and the main-actor write path are two distinct, named concurrency domains, not "SwiftData handles it" hand-waved into one paragraph — that distinction is what keeps a future contributor from "simplifying" stats computation back onto the main thread and reintroducing per-render table scans.

## Final Output

**Architecture overview:** Three layers, matching `ios_architecture_review` concretely: (1) two local Swift packages — `RecallScheduling` (Clock, Grade, SchedulingState, SM2Engine — pure, zero Foundation date singletons) and `RecallCSV` (CSVRowStatus, CSVParser — pure, no I/O), each with its own Swift Testing target; (2) a SwiftData repository layer in the app target (`Persistence/`) with real error handling (no `try!`) and `VersionedSchema`/migration scaffolding from v1; (3) SwiftUI + `@Observable` view models in `Features/Study|Stats|Settings/`, plus `Navigation/` (typed per-tab route enums), `DesignSystem/` (Theme.swift + locked components), and `Services/` (ReminderScheduler, PlanGate, DemoDataSeeder, GapRegister). Two named concurrency domains: the main-actor synchronous write path (every grade save, every CRUD op) and a separate background `StatsComputationActor` (`@ModelActor`) that recomputes forecast/history/retention off `ModelContext.didSave` notifications and publishes into a `@MainActor @Observable StatsCache` — this split is now explicit in the spec so a future "simplification" can't quietly move stats math back onto the main thread and reintroduce per-render table scans.

**Data models:** Deck/Card/ReviewLog frozen shape, plus two concrete additions: `Deck.reminderHour`/`reminderMinute` (optional) implement per-deck Plus reminder overrides, and stats retention is modeled as `nil` (not `0.0`) when sample size is zero so "no data yet" and "0% retention" never collapse into the same value. `ReviewLog` stays append-only by construction — the repository exposes only `insert`, no update method exists at all.

**Persistence strategy:** One `ModelContainer` for the app's lifetime via `ModelContainerFactory` returning `Result<ModelContainer, RecallDataError>` (no crash-on-corrupt-store), routed to a recovery screen on failure. Due status is always a computed predicate (`dueDate < startOfTomorrow(now, calendar)`), never stored. Per-grade save is synchronous on the main actor; on save failure the card stays visible marked "unsaved" with a retry affordance — never a faked decrement or fabricated advance.

**Review session correctness:** Snapshot an ordered `[UUID]` queue once at session start (already locked); new this round — if a queued card ID is missing/stale at grading time, skip it and record it, don't crash or fabricate a grade. This gets its own required test.

**CSV:** Three columns (front/back/optional note), fully enumerated `CSVRowStatus` (ok/emptyFront/emptyBack/wrongColumnCount/malformedQuoting/invalidEncoding/duplicateInFile/duplicateInDeck/capBlocked) as one shared contract type — no case left to prose.

**Testing strategy:** `RecallSchedulingTests` + `RecallCSVTests` (pure, Swift Testing) → `RecallPersistenceTests` (in-memory `ModelContainer`, CRUD/cascade/append-only) → `RecallIntegrationTests` (stats-actor trigger-on-save, reminder reschedule at the four refresh points, CSV preview→commit) → `RecallUITests` (force-quit `app.terminate()`, Study-All reorder-proofing, and the new stale-ID mid-session skip case).

## Final Output

**Architecture overview:** Three layers, matching `ios_architecture_review` concretely: (1) two local Swift packages — `RecallScheduling` (Clock, Grade, SchedulingState, SM2Engine — pure, zero Foundation date singletons) and `RecallCSV` (CSVRowStatus, CSVParser — pure, no I/O), each with its own Swift Testing target; (2) a SwiftData repository layer in the app target (`Persistence/`) with real error handling (no `try!`) and `VersionedSchema`/migration scaffolding from v1; (3) SwiftUI + `@Observable` view models in `Features/Study|Stats|Settings/`, plus `Navigation/` (typed per-tab route enums), `DesignSystem/` (Theme.swift + locked components), and `Services/` (ReminderScheduler, PlanGate, DemoDataSeeder, GapRegister). Two named concurrency domains: the main-actor synchronous write path (every grade save, every CRUD op) and a separate background `StatsComputationActor` (`@ModelActor`) that recomputes forecast/history/retention off `ModelContext.didSave` notifications and publishes into a `@MainActor @Observable StatsCache` — this split is now explicit in the spec so a future "simplification" can't quietly move stats math back onto the main thread and reintroduce per-render table scans.

**Data models:** Deck/Card/ReviewLog frozen shape, plus two concrete additions: `Deck.reminderHour`/`reminderMinute` (optional) implement per-deck Plus reminder overrides, and stats retention is modeled as `nil` (not `0.0`) when sample size is zero so "no data yet" and "0% retention" never collapse into the same value. `ReviewLog` stays append-only by construction — the repository exposes only `insert`, no update method exists at all.

**Persistence strategy:** One `ModelContainer` for the app's lifetime via `ModelContainerFactory` returning `Result<ModelContainer, RecallDataError>` (no crash-on-corrupt-store), routed to a recovery screen on failure. Due status is always a computed predicate (`dueDate < startOfTomorrow(now, calendar)`), never stored. Per-grade save is synchronous on the main actor; on save failure the card stays visible marked "unsaved" with a retry affordance — never a faked decrement or fabricated advance.

**Review session correctness:** Snapshot an ordered `[UUID]` queue once at session start (already locked); new this round — if a queued card ID is missing/stale at grading time, skip it and record it, don't crash or fabricate a grade. This gets its own required test.

**CSV:** Three columns (front/back/optional note), fully enumerated `CSVRowStatus` (ok/emptyFront/emptyBack/wrongColumnCount/malformedQuoting/invalidEncoding/duplicateInFile/duplicateInDeck/capBlocked) as one shared contract type — no case left to prose.

**Testing strategy:** `RecallSchedulingTests` + `RecallCSVTests` (pure, Swift Testing) → `RecallPersistenceTests` (in-memory `ModelContainer`, CRUD/cascade/append-only) → `RecallIntegrationTests` (stats-actor trigger-on-save, reminder reschedule at the four refresh points, CSV preview→commit) → `RecallUITests` (force-quit `app.terminate()`, Study-All reorder-proofing, and the new stale-ID mid-session skip case).
