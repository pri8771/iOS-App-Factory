CORE FEATURES (favor complete over broad):
1. Decks & cards: create/edit/archive decks; cards have a front, back, and optional note. Card editing must be fast and keyboard-friendly.
2. Spaced-repetition scheduling: implement the SM-2 algorithm (ease factor, interval, repetition count) with Again/Hard/Good/Easy grading. THIS IS THE HEART OF THE APP. Implement it as its own standalone, pure, tested module — provably right, not plausibly right. 5. Deck import/export: export any deck to CSV; import cards from a two-column CSV (front, back) with a preview step and per-row error reporting — never silently drop a row.
6. Review reminders: one optional LOCAL notification per day ("You have N cards due") at a user-chosen time; respect permission denial gracefully. No push, no server.

PRIORITIES (in order): (1) SM-2 module correctness above all — proven via its tests; (2) review-flow speed; (3) honest empty states. Include a "demo data" toggle in Settings that seeds two decks with a realistic review history so stats screens are never empty on first look.

One concrete build-mechanics point nobody's raised yet: with four lanes editing the same Xcode project concurrently, `project.pbxproj` is the classic conflict magnet — every new file addition rewrites it. Xcode 15+'s folder-based synchronized groups (`fileSystemSynchronizedGroups`) means dropping a new `.swift` file into a lane's owned folder auto-includes it in the target with no pbxproj diff. I want that turned on from the bootstrap task, otherwise "who owns which files" doesn't actually prevent merge pain — it just delays it to every commit.

On lane assignment, I'm mapping the four fixed lanes to what project_plan already locked rather than reinventing groupings:

`data_domain` owns the two pure packages (RecallScheduling, RecallCSV) and everything SwiftData — Deck/Card/ReviewLog, ModelContainerFactory, the two repositories, RecallDataError. This is deliberately the most isolated lane: zero SwiftUI imports, so it can run fully ahead of UI work and its test suite (RecallSchedulingTests, RecallCSVTests, RecallPersistenceTests) is the actual gate everything else waits behind, per the locked sequencing.

`services_utilities` owns the background/non-visual machinery that sits on top of persistence: PlanGate, StatsComputationActor + StatsCache, ReminderScheduler, SubscriptionService/StoreKit config, DemoDataSeeder. All of these read repositories but never import SwiftUI.

`primary_ui` owns every screen and view model: DeckList/DeckDetail/CardEditor/ReviewSession/SessionSummary, Stats screens, Settings & Tools screens (CSV import/export UI, Reminders UI, Plan/Subscription UI, Gap & Limitations screen), navigation route enums, RootTabView, AppRootState's view-facing half.

`polish_resilience` owns the cross-cutting correctness/experience layer: Theme.swift, the three do-not-regress components (GradeStaircase, DemoDataTag, InlineCapNotice), the haptic ladder, PrivacyInfo.xcprivacy, and — this is the important part — the entire RecallUITests target, because the force-quit SIGKILL test, the stale-ID skip test's UI-level proof, and the Study-All reorder-proofing test are the single most important artifacts in this whole project and I don't want them owned by whichever lane happens to be building the feature under time pressure. Same lane also owns final GapRegisterEntry content consolidation and the automated test asserting its required disclosure strings.

The one deliberately overlapping file is GapRegisterEntry.swift — polish_resilience is its integrator (final say, owns the merge), but data_domain/services_utilities file short content stubs into it at their own milestones (the StoreKit-exception line lands when subscription ships, the iCloud-backup line lands when persistence ships) rather than everyone touching it freely at once.

Forbidden-zone rule: no lane edits another lane's owned files directly. If a lane needs a signature change on a shared contract type (say, `ReviewSessionViewModel` needs a new field `StatsCache` also wants), that's a named cross-lane change proposed in a task, not a silent edit — same discipline tech_specs already applied to `interfaces-json`.

How we'll know it works: each task's acceptance criteria are concrete tests already named in project_plan — SM-2/CSV suites green, persistence CRUD+cascade+recovery-screen tests, the StatsComputationActor latency ceiling (3s/3,000 cards/3yr), the real force-quit `app.terminate()` XCUITest with the save-boundary pause, the stale-ID skip test, the real-world CSV fixture round-trip, and the Gap & Limitations disclosure-string assertion. Nothing here is "looks done" — every gate is a test that either passes or doesn't.

My biggest actual worry with this plan isn't the lane split, it's sequencing risk: primary_ui's review-session task can't meaningfully start until data_domain's repositories are stable, and if data_domain slips, three lanes stall behind it. I think that's an acceptable, already-accepted risk (project_plan explicitly made domain-layer-green the hard gate) rather than something to re-litigate here, but it means data_domain's early tasks need to be the first ones a build worker picks up, full stop, not treated as one lane among four equally-paced tracks.

### Round 2


**Codex (Frontend Engineer · Skeptic) — Round 2**

I’m siding with Claude on this phase’s practical split: the coarse 13-task draft is too top-heavy for parallel execution and leaves the hardest guarantees (especially `app.terminate()` correctness) living inside whichever lane is under pressure. Claude’s split is better and, with Codex’s extra constraint that only CSV import can be trimmed, it gives us a deterministic execution path. Gemini still has no substantive substitute to challenge that.

On naming, we need one filesystem contract now: use `recall-ios` root as the workspace and `Recall/` as the app target directory (`recall-ios/Recall...`), with packages under `Packages/`. No one creates `RecallIOS/` or `recall-ios/RecallIOS` paths. To keep lanes from colliding, `Recall.xcodeproj` is owned by `primary_ui` only, and we use `fileSystemSynchronizedGroups` so feature lanes can add source files without fighting `project.pbxproj`. `data_domain` owns pure packages + persistence model/repo tests; `services_utilities` owns cross-cutting app services; `primary_ui` owns screens/navigation and feature view models; `polish_resilience` owns the do-not-regress components, high-value test artifacts, gap/register content, and stabilization verification. Critical safety tests (`force-quit`, stale-ID skip, gap assertion, stabilization) stay in `polish_resilience` so they don’t disappear when feature scope is squeezed.

Acceptance-wise, this ordering is explicit: bootstrap and package work can start immediately in parallel, then domain contracts go green, then persistence, then review session, then stats, then CSV/subscription, then final hardening. Handoff rule: every task ships compile-safe extension points (protocols/DI), and lane-local files cannot import layers above their own.
