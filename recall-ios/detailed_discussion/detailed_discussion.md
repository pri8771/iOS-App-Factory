**Claude (QA & Risk · Skeptic) — Round 1**

I want to pressure-test the things that are still fuzzy enough to bite us during build, not restate what's already locked. Four of these I think are real landmines, not nitpicks.

First, the SM-2 spec still isn't actually pinned down, and "SM-2" is a name, not a formula everybody agrees on. Original SuperMemo-2 grades on a 0–5 quality scale and doesn't have a native "Hard" button; Anki's implementation diverges from literal SM-2 on lapse handling (Anki uses relearning steps and a configurable "new interval %" on lapse, not a hard reset to rep 0 with interval 1) and on how Hard/Easy modify the ease factor and interval multiplier. If we don't commit, in writing, to one exact variant — mapping Again/Hard/Good/Easy to specific ease deltas, specific interval multipliers, and a specific lapse behavior (does a lapse zero out repetition count? does interval reset to 1 day or to some fraction of the previous interval? does ease decrease by exactly 0.2 on Again and by how much, if any, on Hard?) — two engineers implementing "SM-2" from the same prompt will produce different schedules and both will defensibly claim correctness. I'd rather over-specify now: adopt literal SuperMemo-2 arithmetic (EF' = EF + (0.1 − (5−q)×(0.08+(5−q)×0.02)), floor EF at 1.3, I(1)=1, I(2)=6, I(n)=I(n−1)×EF for n>2, repetition count resets to 0 and interval resets to 1 on any grade below "Good") with an explicit, documented mapping of the four UI buttons to quality scores (Again=2, Hard=3, Good=4, Easy=5 is one reasonable mapping, but it has to be a decision, not an implementation detail someone invents while coding), and Hard must still move the ease factor and interval, not just skip the "success" path — Hard is a passing grade in this scheme, not a lapse. Whatever we pick, the worked-example cross-check against a known Anki progression is going to show visible divergence from Anki's own numbers, because Anki isn't pure SM-2 — that divergence has to be explained in the spec, not treated as a bug to chase.

Second, there's a real contradiction sitting between two already-locked decisions. DEC-prompt_contract-004 requires export→import to round-trip losslessly, but the prompt (and every phase since) also specifies import as strictly a two-column CSV (front, back), while export presumably includes the optional note as a third column since notes are part of the card model. If a card has a note, exporting then re-importing that same CSV cannot be lossless under a two-column-only importer — the note silently disappears, which is exactly the "never silently drop data" failure this whole feature exists to prevent. This needs an explicit resolution before CSV design: either import accepts an optional third column for notes (making it a two-or-three-column format, still strict and still front/back validated) or "round-trip losslessly" is redefined to mean "front/back content round-trips losslessly, notes are a known non-round-tripping field" and that limitation is stated plainly in the UI. I'd push for the former — a three-column CSV with note optional is barely more parsing work and actually satisfies the lossless promise instead of asterisking it.

Third, day-boundary math is more subtle than "use Calendar, not raw Date," which is already decided, but the open question is which timezone and which reference point. If a card becomes due while the device is in America/Los_Angeles, and the user flies to America/New_York and opens the app mid-flight after landing, is "due" evaluated against the device's current timezone at query time (correct, per DEC-prompt_contract-002) — meaning the same instant can flip from "not due" to "due" or vice versa purely because the phone's clock changed timezone, with no review having happened? That's the intended behavior per the calendar-day rule, but it needs to be an explicit, tested case (not just DST), because it means due-status is not a stable function of time alone — it's a function of time and current device locale, and the notification due-count DEC-prompt_contract-005 already requires can genuinely go stale or flip between scheduling and firing if the user crosses timezones overnight. That should be named as an accepted, documented limitation exactly the way notification staleness already is ([REDACTED:high_entropy]), not discovered as a surprise later.

Fourth on interruption safety: the force-quit test we've locked in tests the case where the OS kills the app between review taps. The sharper failure mode is a kill during the SwiftData write itself — if grading triggers `context.save()` and the process is terminated mid-write, does SwiftData/SQLite leave a consistent state? This is generally true for SQLite (atomic commit), but the spec should explicitly require a synchronous, explicit `save()` per grade rather than relying on `ModelContext.autosaveEnabled` — autosave batches on a timer/scene-phase basis and would reopen exactly the data-loss window the whole feature is designed to close. This needs to be a stated architectural constraint, not left to whoever writes the review view.

A few smaller edge cases that need an explicit answer rather than an implicit one: what "duplicate" means in CSV import (I'd define it as case-sensitive exact front+back match, checked both within the imported file and against existing non-archived cards in the target deck, each duplicate getting its own visible per-row reason distinct from malformed rows); whether archived decks and their cards still count against the Free 3-deck/300-card cap (I'd say yes — archiving isn't deletion, and letting users dodge the cap by archiving then unarchiving would make the cap meaningless); whether card deletion is in scope at all (the prompt only names deck archive explicitly, but "edit" cards implicitly requires delete for it to be usable, and deleting a card should be allowed to also delete its ReviewLog history, which means today's retention-rate stat can retroactively change after a delete — that's honest, not a bug, but worth stating so nobody "fixes" it later); and accessibility on the grading buttons — Again/Hard/Good/Easy can't be color-coded alone (red/orange/green/blue) since that fails for color-blind users and VoiceOver users need distinct accessible labels, not just glyphs, given accessibility is already a stated product requirement, not polish.

One privacy note worth locking now: the daily local notification body text ("You have N cards due") must never include card content, deck names, or subject matter, since lock-screen notification previews are visible to anyone glancing at the phone — a count is safe, "5 due in Spanish Verbs" or a card front leaking through is a real privacy regression for someone studying, say, medical board material on a shared device.

Final assumption I'd lock rather than leave open: the app's SwiftData store is not excluded from the user's normal iCloud device backup — that's an OS-level backup, not app-initiated sync, so it's consistent with the offline-forever contract, and it's actually the only loss-prevention a user gets if they lose the device. But if a user restores an old backup onto a second device while continuing to use the first, the two stores will silently diverge with no merge logic (consistent with the already-locked no-cross-deck-merge non-goal) — that should be named explicitly as a limitation in the gap register rather than assumed away, since "why do my two phones disagree" is a predictable support question for exactly the audience this app targets.
