```
Build a polished, fully offline iOS spaced-repetition flashcard app called "Recall". Native Apple stack ONLY: SwiftUI + SwiftData for persistence, Swift Charts for stats. No backend, no accounts, no third-party SDKs, no network of any kind — the app must work in airplane mode forever, all data on-device. Follow the ios-app-factory-rules. Runnable in the iOS Simulator via Xcode; provide clear run instructions.

HARD RULE ON GAPS: Anything that would need infrastructure this project cannot provide (cloud sync, shared/community decks, a deck marketplace) must NOT be faked or stubbed. CORE FEATURES (favor complete over broad):
1. Decks & cards: create/edit/archive decks; cards have a front, back, and optional note. Card editing must be fast and keyboard-friendly.
2. Spaced-repetition scheduling: implement the SM-2 algorithm (ease factor, interval, repetition count) with Again/Hard/Good/Easy grading. THIS IS THE HEART OF THE APP. Implement it as its own standalone, pure, tested module — provably right, not plausibly right. Unit tests MUST cover: first reviews, lapses resetting the interval, ease-factor floors, and day-boundary handling in the device's local time zone (a "day" is a calendar day).

4. Stats: per-deck and overall — due-forecast bar chart for next 30 days, daily review-count history, and retention rate (% graded Good/Easy). Handle empty and sparse data gracefully.
5. Deck import/export: export any deck to CSV; import cards from a two-column CSV (front, back) with a preview step and per-row error reporting — never silently drop a row.
6. Review reminders: one optional LOCAL notification per day ("You have N cards due") at a user-chosen time; respect permission denial gracefully. No push, no server.

PRIORITIES (in order): (1) SM-2 module correctness above all — proven via its tests; (2) review-flow speed; (3) honest empty states. Include a "demo data" toggle in Settings that seeds two decks with a realistic review history so stats screens are never empty on first look.
```

### Round 1


**Codex (Backend / Systems Engineer · Systems Thinker) — Round 1**

I would lock this as a single, local-only iOS app with one long-lived source of truth in SwiftData and a strict purity boundary between scheduling, storage, and rendering. The data should never be the UI, and the UI must never be the scheduler. The core correctness claim (“never lies about what is due”) is a state-management problem, not just a rendering problem.

The strongest architecture choice is to keep the app in three coordinated layers. The domain layer is a pure Swift package-like module: SM-2 engine, card state transitions, due-date computations, and CSV parse/serialize helpers; this layer has no SwiftData types and no UI calls. The persistence layer is a thin SwiftData repository with explicit query methods for deck/card/review lookups and atomic write operations. The presentation layer is SwiftUI + `@Observable` view models that consume repository protocols and emit state machines per screen. That keeps SM-2 testable, prevents accidental coupling, and gives a clean seam for the interruption/force-quit behavior.

For Apple framework choice, the stack is locked to SwiftUI, SwiftData, Foundation, Swift Charts, UserNotifications, UniformTypeIdentifiers, StoreKit 2, and OSLog where needed for non-user-visible diagnostics. There is no place for third-party persistence, networking, queueing, or utility layers here. If we introduce anything not in that list, it should be justified by measurable complexity reduction and pass permissive licensing constraints, but this app should not need any.

SwiftData model shape should be fixed early and treated as immutable in spirit after build-start: Deck/Card/ReviewLog with explicit relationships and delete behavior. Card fields should support grading, due calculation input/output, and note text. ReviewLog must remain append-only by design, not mutable, and deletion should cascade so no orphaned log rows remain. Deck archive is model state only, not deletion, so capped-resource and history calculations must continue to include archived content per contract expectations. Card-level due status should be computed at query time from local “start of tomorrow” in the current device timezone; never store a mutable is-due boolean. This avoids stale dueness and keeps one source of scheduling truth.

For session behavior, I strongly reject a live query-driven review list. If the review queue is driven by a live `@Query`, every grade can mutate dueDate and immediately reshape the query order and shrink the queue under the user, which appears as data-loss-like behavior. Use one initial due-card query, snapshot the IDs into an in-memory queue at session start, and iterate by index. On relaunch, do not restore a fake session object; recompute from truth and the due-query. This is simpler, safer, and aligns with forced-kill correctness.

Per-grade persistence is an explicit synchronous write path against the live `ModelContext`, not autosave and not deferred batching. It is the only way to guarantee the force-quit contract. I would call this out in architecture docs as a deliberate performance tradeoff: there may be one-frame stutter on older devices, but it is acceptable because correctness beats responsiveness for this product. The review button should stay disabled only for that write boundary, then advance.

Persistence architecture for settings and subscription can stay local via SwiftData for app config (selected reminder time, plan mode, demo toggle, last-refresh marker, deck scope) plus StoreKit entitlement state derived on demand. If you put these in `@AppStorage`, you save implementation effort but increase test scaffolding complexity; SwiftData consistency across one transaction model is cleaner for deterministic UI state and easier migration planning.

Permissions and privacy are constrained and clear: only one runtime permission is needed for core behavior, notifications. The app can function fully without it, so the flow must be graceful and non-blocking. The privacy surface is small: no location, no camera, no microphone, no contacts, no photos, no analytics, no crash reporting upload, no accounts, no backend SDK. File import/export needs no extra privacy entitlement beyond standard document picker usage; imported content stays local and is not transmitted.

For StoreKit, use StoreKit 2 with `Product.products(for:)`, `Transaction.updates`, `Transaction.currentEntitlements`, and finish transactions. Entitlement checks should be cached in-memory and re-queried on active/restore/purchase events. Purchase/restore is the only sanctioned network touch in this app and must be explicitly called out as an OS-level exception to “works forever offline.” After purchase succeeds, all app features and gates should continue offline using on-device transaction cache/state. Add one restore path and don’t show paywalls that gate core correctness behavior.

Reminder behavior should be local notifications only, no push, no background fetch, no remote scheduling. Given iOS constraints on notification body staleness, schedule with `repeats: false` and reschedule at fixed refresh points (foreground, background, post-session, and day boundary when observed). If app isn’t opened between days, a reminder for that day may not exist; this is not a silent bug but an explicit documented limitation. Notification payload should never include deck/card content, only count.

ML/AR feasibility is a hard no for this phase and product promise. ML-based scheduling is explicitly out; using ML for OCR, NLP card creation, handwriting recognition, or card similarity would be out-of-scope, would increase permission risk, and risks violating the trust-first offline promise.

Dependency policy is strict: no new third-party frameworks; no Alamofire/SwiftyJSON/Realm-like replacements; avoid “helper” packages unless absolutely unavoidable. CSV and encoding edge handling should be implemented in-house with deterministic tests and explicit error taxonomy. If someone proposes a parser dependency, it must be permissive-license compatible (Apache/MIT/BSD) and still be rejected unless it removes clear, demonstrable risk.

Testability strategy has to be architecture-driven from day one. Unit tests target pure SM-2 math, queue snapshot behavior, timezone/day-boundary predicate correctness, duplicate and malformed-row classifications, and cap-hit logic. Persistence tests should run against an in-memory SwiftData container for idempotent CRUD, cascade delete, and replay-safe review log append semantics. Integration tests should verify interruption semantics (grade + immediate save + relaunch), reminder permission branches, and CSV import preview/result states. UI tests are useful for per-row status visibility and state transitions, but should be paired with non-UI deterministic tests so correctness does not depend on animation timing. The biggest objection I’d raise to this direction is complexity overhead from repository abstractions in a small app, but that overhead is justified because it protects the offline-correctness guarantee and makes the forced interruption and scheduling guarantees demonstrable rather than assumed.

The final tech spec must preserve: injected-clock SM-2 purity, no live-query review queue, synchronous per-card commit, snapshot queue in session flow, strict schema freeze, only documented local permission surface, StoreKit exception handling, and explicit offline-limitation language for reminders/backup/Timezone flips so no user-visible feature is implied but not guaranteed.

**Claude (QA & Risk · Closer) — Round 1**

Starting from the failure modes nobody's named yet, because "provably right, not plausibly right" has to apply to the whole app shell, not just the SM-2 formula.

The biggest hole I see: every SwiftData tutorial in the wild wires up `ModelContainer` with `try!`, which means if the on-device store ever fails to open — corrupted file, disk full, a lightweight-migration inference that SwiftData can't actually perform automatically — the app hard-crashes on launch with no recovery path. For an app whose entire pitch is "never lies to you about your progress," a crash loop that eats someone's three years of review history is the worst possible failure. I want this locked now: `ModelContainer` init must be wrapped in real error handling at the App root, with a fallback screen ("Recall couldn't open your data" + options to retry or, as an explicit last resort, start fresh) rather than a crash. And since the schema is "frozen early" per prior phases, that's exactly when to also set up `VersionedSchema`/`SchemaMigrationPlan` scaffolding now, even with a single version — it costs nothing today and it's the only thing standing between "we need to add a field for the App Store review team's requested bug fix" and silently corrupting every existing user's ReviewLog six months from now.

On module boundaries: the SM-2 engine and the CSV pipeline both need to physically live in their own Swift package targets with zero import of SwiftUI, SwiftData, or Foundation's `Date()`/`Calendar.current` singletons — only injected `Clock`/`Calendar` values. That's not new relative to what's already locked, but I want to be blunt about why it matters for this phase specifically: if these live as files inside the main app target, nothing stops a future edit from reaching for `Date()` directly as a "quick fix," and the whole DST/timezone test matrix becomes theater. Two separate local packages, no exceptions.

Framework set is genuinely simple and I don't think there's any daylight to debate: SwiftUI, SwiftData, Swift Charts, StoreKit 2, UserNotifications, OSLog, Swift Testing for the pure-logic suites, XCUITest for anything that needs a real process (critically, the force-quit test). No ML, no ARKit, no CoreML — nothing in the locked feature set justifies them, so there's nothing to argue about there; I'd rather state that plainly than leave it as an open question for tech_specs to rediscover.

On the force-quit interruption test specifically, since it's the single most important test in the whole app: "kill the simulator mid-session" cannot be a manual QA step that happens once and then bit-rots. XCUITest's `app.terminate()` sends a real SIGKILL to the app process from the test runner — that's the actual sanctioned mechanism, and it should be a scripted, CI-runnable test: launch, grade N cards, call `app.terminate()` at a point timed around the synchronous save, relaunch, and assert the exact due/graded split. If this isn't an automated test, "provably right" quietly becomes "we tried it once."

Privacy: this app needs a Privacy Manifest (`PrivacyInfo.xcprivacy`) for App Store submission — this is easy to miss because the instinct is "we have zero network calls, why would we need a privacy manifest," but Apple's May-2024 requirement is keyed on *API usage* (UserDefaults, file-timestamp APIs, etc.), not network usage, and a zero-network app can still trip it. I'd rather name this now as a concrete build-verification checklist item than have it surface as a surprise App Store rejection after everything else is done. Separately: the notification permission prompt must not fire at cold launch — it should only fire when the user actively turns on Reminders in Settings, both because it's the right UX and because a denied first-ask is much harder to recover from than a contextual one.

StoreKit needs three concrete things nailed down, not left implicit: a `.storekit` configuration file checked into the project so Plan/Subscription is testable in Simulator without a sandbox account, including scripted tests for expire/refund/renewal via Xcode's StoreKit testing controls; the paywall screen must carry a privacy-policy and terms-of-use link, which is an Apple 3.1.2 App Review requirement for auto-renewing subscriptions, not a nice-to-have; and the purchase-tap-while-offline path needs an explicit, bounded error state ("You need an internet connection to complete this purchase") — not a spinner that just hangs, since that's the one real network call in the whole app and it's the one place a naive implementation will silently violate the "never lie about what's happening" principle by leaving the user staring at nothing.

One CSV gotcha worth locking in now: files coming from the document picker are security-scoped URLs, and forgetting `startAccessingSecurityScopedResource()`/`stopAccessingSecurityScopedResource()` around the read is a classic bug that works fine in dev (same process, same session) and then intermittently fails for real users pulling files from iCloud Drive or a Files provider. This needs to be named as a required pattern in the CSV import implementation, not discovered during manual testing.

Dependency decision is easy: zero third-party packages, full stop. Hand-roll the CSV parser rather than pulling in any SPM CSV library — we already have a locked, exhaustive per-row error taxonomy (malformed, duplicate, cap-blocked, BOM/encoding, CRLF/LF) that a generic library wasn't designed around anyway, so a hand-rolled parser is actually less work than fighting someone else's abstraction, and it keeps us at zero supply-chain surface.

Last thing, small but worth stating explicitly so it doesn't get silently dropped: keep exactly one `ModelContainer` instance for the whole app (not one per scene), so that iPad multitasking or any future multi-window scenario can't produce two contexts racing on the same store. And the Gap & Limitations screen, since it's a correctness-adjacent requirement and not just a UI nicety, should have its own automated test asserting the screen renders and contains the required disclosure strings — otherwise "must be documented" is exactly the kind of soft requirement that quietly disappears under time pressure with nobody able to prove it happened.

## Final Output

**Architecture:** Three layers — (1) a pure domain layer (SM-2 engine + CSV parser) shipped as its own local Swift package with zero SwiftUI/SwiftData imports and no direct `Date()`/`Calendar.current` calls, only injected clock/calendar; (2) a thin SwiftData repository layer with explicit query/write methods; (3) SwiftUI + `@Observable` view models per screen. Exactly one `ModelContainer` instance for the whole app lifetime.

**Frameworks locked:** SwiftUI, SwiftData, Swift Charts, StoreKit 2, UserNotifications, UniformTypeIdentifiers, OSLog, Swift Testing (pure-logic suites), XCUITest (process-level tests, especially force-quit). No ML/CoreML/ARKit — nothing in the locked feature set justifies them.

**Persistence:** Deck/Card/ReviewLog schema (already frozen in design_handoff) built with real `ModelContainer` error handling — no `try!` — and a fallback recovery screen if the store fails to open; `VersionedSchema`/`SchemaMigrationPlan` scaffolding is set up from day one even at version 1, since retrofitting migration support later risks corrupting existing review history. Due status stays a computed predicate, never a stored boolean, per the already-locked rule.

**Review session:** Reaffirms the design_handoff snapshot-array architecture (no live `@Query` driving the queue) and synchronous per-grade save against the live `ModelContext`. The force-quit test must be an automated, scripted XCUITest (`app.terminate()`) run in CI, not a manual step.

**Permissions/privacy:** Only one runtime permission exists (notifications), requested only when the user opts into Reminders — never at cold launch. A Privacy Manifest (`PrivacyInfo.xcprivacy`) is required for submission despite zero network calls. No location/camera/microphone/contacts/photos/analytics/crash-reporting/accounts.

**StoreKit:** StoreKit 2 with `Transaction.updates` listener from launch, cached entitlement state re-queried on active/purchase/restore. A `.storekit` configuration file is checked into the project with scripted expire/refund/renewal tests. Paywall carries privacy-policy/terms-of-use links (App Review 3.1.2). Purchase attempted while offline shows an explicit bounded error, not a hang — this is the one sanctioned network touch in the whole app.

**Dependencies:** Zero third-party packages, confirmed. Hand-rolled CSV parser (already justified by the locked, exhaustive per-row error taxonomy). CSV import wraps document-picker reads in `startAccessingSecurityScopedResource()`/`stopAccessingSecurityScopedResource()`.

**Testing:** Unit tests (Swift Testing) for SM-2 math, day-boundary/timezone predicates, CSV row classification, cap-hit logic. Persistence tests against an in-memory SwiftData container for CRUD/cascade-delete/append-only ReviewLog behavior. Integration tests for interruption semantics, reminder permission branches, CSV import flow. UI tests paired with deterministic non-UI tests so correctness never depends on animation timing. The Gap & Limitations screen gets its own automated test asserting required disclosure strings render.
