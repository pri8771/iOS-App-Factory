**Claude (Frontend Engineer · Systems Thinker) — Round 1**

I want to start from the data layer and work outward, because the thing that will actually break this app isn't a color choice, it's an architectural shortcut in how the review screen talks to SwiftData. The frozen schema needs four model types: Deck (id, name, createdAt, archivedAt: Date?, isDemo: Bool), Card (id, front, back, note: String?, easeFactor, intervalDays, repetitionCount, dueDate, lastReviewedAt, deck relationship, and a denormalized isDemo copied from its parent deck at creation time — not derived via join on every query, because at the 300–3,000 card scale this persona actually lives at, joining out to Deck.isDemo on every stats aggregation is the kind of thing that's invisible in a demo with twelve cards and visibly janky once someone has three years of real study history), and ReviewLog (id, card relationship, timestamp, grade, qualityBefore/after state snapshot), which I want to treat as strictly append-only and never mutated in place — that's not just tidiness, it's the concrete schema-level expression of the cloud-readiness decision from per_app_product_brief about immutable card-history events, and if we don't enforce it as an architectural rule now, someone will "fix" a ReviewLog row in place during a bug fix eight months from now and quietly break that future option. Due-status evaluation should not be stored as a boolean; it's computed at query time as card.dueDate < startOfTomorrow(deviceCalendar), where startOfTomorrow is a plain Date instant recomputed fresh at each query — that's how the calendar-day-at-query-time rule actually gets implemented as an efficient, indexable SwiftData predicate rather than as prose intention that nobody translates into code.

The place I want to push hardest, because I think it's a real landmine nobody upstream has named yet: the Review Session must not be driven by a live @Query. If the due-card list for a session is a live SwiftData query, then grading a card mutates its dueDate immediately, which triggers a refetch mid-session, which can reorder or shrink the visible queue out from under the user's thumb — especially in Study All mode where multiple decks interleave and the sort order isn't stable across a live refetch. That will look exactly like a bug (cards vanishing, the "7 of 23" counter jumping) even though the underlying data is perfectly safe. The fix is to snapshot an ordered array of Card IDs once when the session starts, and have the session engine step through that frozen array by index; the query is used only to construct the initial snapshot, never to drive what's rendered mid-session. This also gives us interruption-safety almost for free and more honestly than trying to persist and restore session state: on relaunch after a force-quit, don't try to resume the old snapshot at all — just run the due query fresh. Graded cards already have updated dueDates from their synchronous save, so they're automatically excluded; ungraded cards never got touched, so they're automatically still due. There's no separate "resume point" to get wrong, and there's no path by which a fabricated summary can appear, because the summary view only ever exists as a render of the in-memory session engine's final state, and that engine is gone the instant the process dies. I'd rather build interruption-safety as an emergent property of "recompute from truth" than as an explicit save/restore mechanism with its own edge cases.

On the synchronous per-grade save: it has to run on the main actor against the live ModelContext, which means there's an honest, small cost — a slow save on an old device could introduce a barely perceptible stutter between the grade tap and the next card appearing. Given the fixed priority order, that's the correct trade to take, but I want it named explicitly so nobody "optimizes" it into a background save later and reopens the exact data-loss window this whole architecture exists to close.

For state management generally, I don't want one big ObservableObject god-object. Most screens should read directly off @Query and let SwiftData be the source of truth; the only places that need a dedicated @Observable controller are the ones with real async workflow: the ReviewSessionEngine described above, a CSVImportPipeline (file read → parse → per-row validation against malformed/duplicate/cap rules → preview model → commit), and a lightweight EntitlementStore that mirrors StoreKit's Transaction.currentEntitlements into a cached boolean, refreshed at scenePhase transitions to .active and right after a purchase or restore completes, per the standard StoreKit 2 pattern of keeping a long-lived Transaction.updates listener running from app launch. Reminders follow the same "recompute at real moments, not on a timer" philosophy: because a UNCalendarNotificationTrigger's body text is fixed at schedule time, and repeats:true would freeze that text forever, the only correct implementation is repeats:false, re-scheduled fresh (remove-pending, then re-add for "tomorrow" at the chosen time) at each of the four refresh points — foreground, background/resign-active, post-session-completion, and day rollover if the app happens to be open across midnight. That means concretely: if a user doesn't open the app at all between two consecutive days, day two's notification was never actually created, not just "stale" — which is a sharper and more accurate way to write the limitation-register copy than the vaguer staleness language used so far.

For stats performance at scale, computing the 30-day forecast and daily history by iterating all ReviewLog rows inline in a SwiftUI view body will visibly lag once someone has a couple thousand logs, and it'll re-run on every unrelated re-render. I'd rather compute chart series in a background ModelActor, triggered off context-save notifications rather than on every view update, and cache the last computed series in a small observable store that the chart views just read. This also gives a clean seam for the demo-data exclusion filter to live in exactly one place instead of being re-implemented per chart.

Now the concrete visual system, carrying the Honest Ledger language into real values. ### DESIGN SPEC — Motion & Haptics
Reveal settle: spring, response 0.18s, dampingFraction 0.86 (critically damped — no visible overshoot), not a 3D flip. Grade buttons rise from the bottom edge staggered ~20ms apart on the same curve so the staircase visibly assembles. Reduced Motion disables the spring (content appears instantly via `@Environment(\.accessibilityReduceMotion)`) but never removes haptics. Session-summary counters count up once, linearly, only on genuine completion.
**Haptic ladder (resolved against iOS's actual 5 discrete `UIImpactFeedbackGenerator` styles, which are not a clean linear intensity scale):** Again = `.light`, Hard = `.medium`, Good = `.heavy`, Easy = `.heavy` immediately followed by a second `.light` pulse — giving Easy a distinctly "extra" top-of-ladder feel without inventing an intensity iOS doesn't have. Must be validated on a physical device; Simulator haptic playback isn't representative. No-op fallback on unsupported hardware with zero functional change. No persistent "Saved" confirmation ever appears mid-session — confirmation is structural only (card leaves the stack, counter decrements).

### DESIGN SPEC — Accessibility
Grade buttons carry explicit `accessibilityLabel`s ("Again, forgot" / "Hard, struggled" / "Good, recalled" / "Easy, knew instantly") — shape/position convey nothing to VoiceOver, so labels are mandatory, not a backup. Card content sits in a `ScrollView`; the grade-button row is pinned via `.safeAreaInset(edge: .bottom)`, guaranteeing Dynamic Type growth can never push buttons off-screen. Minimum tap target 44×44. Charts carry `accessibilityLabel`/`accessibilityValue` summaries (e.g., "17 cards due in the next 7 days") so due-forecast data isn't visual-only. Tabular numerals everywhere a count appears. No icon-only controls anywhere. Empty/loading/error/complete states are announced. Palette contrast-checked in both light and dark.

### Architecture constraints carried into build (not visual, but directly protect locked UX guarantees)
- **Review Session must not be driven by a live `@Query`.** Snapshot an ordered array of due Card IDs once at session start; step through it by index. This prevents a mid-session grade from triggering a refetch that reorders or shrinks the visible queue (especially in Study All across decks) — a subtle bug that would look exactly like data loss even though nothing was actually lost.
- **Interruption-safety is implemented as "recompute the due query fresh from truth on relaunch,"** not as an explicit save/restore of session state. Graded cards already have updated `dueDate`s from their synchronous save and are automatically excluded; ungraded cards are automatically still due. There is no separate resume-point to get wrong.
- **SwiftData schema:** `Deck(id, name, createdAt, archivedAt: Date?, isDemo: Bool)`, `Card(id, front, back, note: String?, easeFactor, intervalDays, repetitionCount, dueDate, lastReviewedAt, deck relation, isDemo — denormalized copy from the parent deck at creation time, not derived via join on every query)`, `ReviewLog(id, card relation, timestamp, grade, before/after state snapshot)` — **strictly append-only, never mutated in place**, since that's the concrete schema-level expression of the immutable-event-log cloud-readiness path already locked in `per_app_product_brief`.
- **Due status is a computed predicate** (`card.dueDate < startOfTomorrow(deviceCalendar)`, recomputed fresh per query) — never a stored boolean.
- **Per-grade save runs synchronously on the main actor against the live `ModelContext`.** This is an accepted, named small cost (a possible barely-perceptible stutter on old devices) — not something to "optimize" into a background save later, which would reopen the exact data-loss window the interruption-safety guarantee exists to close.
- **Reminders use `repeats: false`, re-scheduled at each of four refresh points** (foreground, background, post-session, day rollover) by removing the pending request and re-adding one for "tomorrow." If the app isn't opened at all between two consecutive days, day two's notification was simply never created — the gap register should say "never created," a sharper and more accurate framing than generic "staleness."
- **Stats series (forecast/history) are computed in a background `ModelActor`, triggered by context-save notifications, and cached in a small observable store** that chart views read — not recomputed inline in the view body on every re-render. The demo-data exclusion filter lives in exactly one place, this store, rather than being reimplemented per chart.

- **Stats:** Overview (root) → per-deck drill-down (push).
- **Settings & Tools:** grouped root list (CSV Export, CSV Import, Reminders, Demo Data, Plan & Subscription, Gap & Limitations, About/Run Instructions); CSV Import and Plan present as sheets for their multi-step flows.
No disabled affordances anywhere for non-goal features — gap items are plain read-only rows linking to the Gap & Limitations register.

### DESIGN SPEC — Screen States (per screen, condensed)
- **Deck List:** loading (skeleton cards) → empty (`tray.2`, "No decks yet," "Create your first deck" → opens Card Editor flow directly) → all-caught-up (distinct icon/copy: "Nothing due today — check back tomorrow," never reuses the empty graphic) → success (sorted due-desc then name) → error (retry). Over-cap renders an inline, non-blocking cap notice row; never blocks launching a study session.
- **Deck Detail:** loading skeleton → empty deck ("Add your first card") → success (fast-edit rows) → archived filter (visually de-emphasized, not hidden) → error with inline retry.
- **Card Editor:** idle (front focused) → typing (inline validation, front/back required) → saving (Save button spinner, destructive actions disabled) → saved (inline confirmation text in the sheet header only — never a toast) → error (inline retry, stays on screen).
- **Review Session:** ready → revealing (settle animation) → grading (staircase stable at bottom) → saving (explicit lock until the synchronous save commits) → interrupted-resume (relaunch simply re-runs the due query — no separate resume state) → completed → cap-hit-mid-session (`InlineCapNotice`, non-dismissible-by-swipe, non-blocking, reads roughly "You've reached your plan's card limit — this session continues, but new cards can't be added until you upgrade or trim your decks"). The "leave early" control reads **"End session — your progress is saved,"** never a loss-warning dialog, since nothing is ever actually lost.
- **Session Summary:** reachable only on true completion; on any render failure, fall back to Deck List with inline "session was interrupted" copy — never a fabricated summary.
- **Stats Overview / Deck Drill-down:** loading (placeholder bars) → empty ("No review history yet," "Start first review") → sparse (real handful of points + "Still building your review history" caption, not a flat placeholder) → success (real 30-day forecast/history/retention, demo data excluded) → error (retry + last-known-safe note).
- **CSV Export:** idle (deck picker) → exporting → success (file location + share action) → permission-unavailable (Files-app path guidance, no crash).
- **CSV Import:** file-picked → parsing → preview (every row gets a status chip: OK / empty front-back / wrong columns / quote-line issue / encoding-BOM / CRLF-LF / duplicate / cap-blocked) → commit-pending (commit button labels the real count, e.g. "Import 41 of 47 cards," so exclusions are visible in the action itself) → importing (locked, spinner) → completed (imported/failed counts + reasons retained on screen) → error (parse-level message, pick another file).
- **Reminders:** not-requested (trigger prompt) → granted (time picker + last-refresh state) → denied (non-nagging explanation + one-tap path to Settings). Per-deck time override visible for all users; Free sees an upgrade path without losing the base reminder.
- **Demo Data:** off ("Enable demo data") → on (two seeded decks, `DemoDataTag` everywhere relevant) → turn-off (explicit confirmation, zero-residue wording, demo markers vanish from aggregates immediately).
- **Plan/Subscription:** free (caps + what's included) → plus (caps removed + per-deck reminder customization) → purchase (StoreKit flow + Restore) → lapsed (existing content stays fully visible; only new creation blocks).
- **Gap & Limitations:** static, loaded list with effort notes (StoreKit offline exception, notification staleness, timezone-crossing due flips, iCloud backup divergence, full non-goals list); no controls, no fake status indicators.

### DESIGN SPEC — Motion & Haptics
Reveal settle: spring, response 0.18s, dampingFraction 0.86 (critically damped — no visible overshoot), not a 3D flip. Grade buttons rise from the bottom edge staggered ~20ms apart on the same curve so the staircase visibly assembles. Reduced Motion disables the spring (content appears instantly via `@Environment(\.accessibilityReduceMotion)`) but never removes haptics. Session-summary counters count up once, linearly, only on genuine completion.
**Haptic ladder (resolved against iOS's actual 5 discrete `UIImpactFeedbackGenerator` styles, which are not a clean linear intensity scale):** Again = `.light`, Hard = `.medium`, Good = `.heavy`, Easy = `.heavy` immediately followed by a second `.light` pulse — giving Easy a distinctly "extra" top-of-ladder feel without inventing an intensity iOS doesn't have. Must be validated on a physical device; Simulator haptic playback isn't representative. No-op fallback on unsupported hardware with zero functional change. No persistent "Saved" confirmation ever appears mid-session — confirmation is structural only (card leaves the stack, counter decrements).

### DESIGN SPEC — Accessibility
Grade buttons carry explicit `accessibilityLabel`s ("Again, forgot" / "Hard, struggled" / "Good, recalled" / "Easy, knew instantly") — shape/position convey nothing to VoiceOver, so labels are mandatory, not a backup. Card content sits in a `ScrollView`; the grade-button row is pinned via `.safeAreaInset(edge: .bottom)`, guaranteeing Dynamic Type growth can never push buttons off-screen. Minimum tap target 44×44. Charts carry `accessibilityLabel`/`accessibilityValue` summaries (e.g., "17 cards due in the next 7 days") so due-forecast data isn't visual-only. Tabular numerals everywhere a count appears. No icon-only controls anywhere. Empty/loading/error/complete states are announced. Palette contrast-checked in both light and dark.

### Architecture constraints carried into build (not visual, but directly protect locked UX guarantees)
- **Review Session must not be driven by a live `@Query`.** Snapshot an ordered array of due Card IDs once at session start; step through it by index. This prevents a mid-session grade from triggering a refetch that reorders or shrinks the visible queue (especially in Study All across decks) — a subtle bug that would look exactly like data loss even though nothing was actually lost.
- **Interruption-safety is implemented as "recompute the due query fresh from truth on relaunch,"** not as an explicit save/restore of session state. Graded cards already have updated `dueDate`s from their synchronous save and are automatically excluded; ungraded cards are automatically still due. There is no separate resume-point to get wrong.
- **SwiftData schema:** `Deck(id, name, createdAt, archivedAt: Date?, isDemo: Bool)`, `Card(id, front, back, note: String?, easeFactor, intervalDays, repetitionCount, dueDate, lastReviewedAt, deck relation, isDemo — denormalized copy from the parent deck at creation time, not derived via join on every query)`, `ReviewLog(id, card relation, timestamp, grade, before/after state snapshot)` — **strictly append-only, never mutated in place**, since that's the concrete schema-level expression of the immutable-event-log cloud-readiness path already locked in `per_app_product_brief`.
- **Due status is a computed predicate** (`card.dueDate < startOfTomorrow(deviceCalendar)`, recomputed fresh per query) — never a stored boolean.
- **Per-grade save runs synchronously on the main actor against the live `ModelContext`.** This is an accepted, named small cost (a possible barely-perceptible stutter on old devices) — not something to "optimize" into a background save later, which would reopen the exact data-loss window the interruption-safety guarantee exists to close.
- **Reminders use `repeats: false`, re-scheduled at each of four refresh points** (foreground, background, post-session, day rollover) by removing the pending request and re-adding one for "tomorrow." If the app isn't opened at all between two consecutive days, day two's notification was simply never created — the gap register should say "never created," a sharper and more accurate framing than generic "staleness."
- **Stats series (forecast/history) are computed in a background `ModelActor`, triggered by context-save notifications, and cached in a small observable store** that chart views read — not recomputed inline in the view body on every re-render. The demo-data exclusion filter lives in exactly one place, this store, rather than being reimplemented per chart.
