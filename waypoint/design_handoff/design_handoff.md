## Original Prompt

```
Build a polished, fully offline iOS trip-planning app called "Waypoint".
Native Apple stack only: SwiftUI + SwiftData for persistence, MapKit for
all mapping, ActivityKit for Live Activities, EventKit for calendar
export. No backend, no accounts, no third-party SDKs, no network calls
except on-device MapKit/local geocoding (which works offline-cached but
may need network for tile fetch — if a feature would require live
network for correctness, don't fake it; record it as a gap). Follow the
ios-app-factory-rules.

Core features (complete over broad — ship fewer things fully working):

1. Trips & itinerary: create trips with a date range; each trip has
   multiple days; each day has an ordered list of stops (place name,
   address, optional MapKit-resolved coordinate, time window, notes,
   category icon). Reorder stops via drag-and-drop within a day AND
   across days. Get date math right across the trip's date range,
   including a trip that starts and ends on the same day and a
   single-day trip.

2. Map view: a MapKit view per day showing all of that day's stops as
   annotations connected by a route line (MKDirections walking/driving,
   gracefully degrading to a straight-line polyline with a visible
   "approximate" indicator if MKDirections has no network). Tapping a
   stop centers the map and highlights it; tapping a map pin selects
   the corresponding itinerary row (two-way binding).

3. Expense splitting: a per-trip list of travelers (name, no accounts).
   Log expenses (amount, payer, split method: equal / exact amounts /
   percentage) against any subset of travelers. A settle-up screen
   computing the minimum set of payments to zero every balance (the
   classic debt-simplification graph problem — get this genuinely
   correct, including rounding remainders so amounts always sum
   exactly). Use Decimal, never Double, for money.

4. Packing lists: per-trip checklist, templates the user can save and
   reapply to future trips, a "packed %" indicator.

5. Live Activity: while a trip is "active" (today falls within its date
   range), a Live Activity / Dynamic Island showing the current or next
   stop and time until it, updating as stops are checked off. Must
   degrade gracefully (no crash, no Live Activity) on devices/OS
   versions without support, and when the user denies the permission.

6. Calendar export: export a day's stops as EventKit calendar events
   (with the user's explicit permission), one event per stop honoring
   its time window; must not create duplicate events if exported twice
   for the same day — detect and either skip or update existing ones.

7. Home-screen widget (WidgetKit, separate target): shows the active
   trip's next stop, or "no active trip" honestly if none.

8. iPad: itinerary list and map must work as a genuine two-column split
   view on iPad, not just a stretched phone layout.

Priorities: the debt-simplification math, the drag-reorder data
integrity (no duplicate/lost stops across days), and honest degradation
of every system-permission-gated feature (Live Activities, Calendar,
location) — never fake success when a permission is denied or a
capability is unavailable in the Simulator. Explicitly call out in a
Gaps section anything requiring infrastructure this project can't
provide (live traffic data, real-time flight tracking, iCloud trip
sync). Seed a "demo trip" toggle in Settings with realistic multi-day
sample data so no screen is empty on first review. Provide a clear way
to run it in the iOS Simulator via Xcode.
```

### DESIGN SPEC — Component Inventory
- **TicketStubStopCard** — perforated left edge, category icon badge, time range in Ledger Numeral, notes reflow taller under Dynamic Type (never clip). Used: day view stop list.
- **DayRibbon** — full-tab mode ≤7 days, compact numeral-only mode >7 days, same underlying day-index model for both. Used: day view header.
- **LedgerPageFlip** — shared `ViewModifier`/custom transition for cross-day moves (one implementation, not per-call-site). Used: drag-reorder across days.
- **CategoryPin** — custom `Marker`/`Annotation`, enum-keyed, each case carries a symbol + accessibility label. Used: map view.
- **RunningBalancePreview** — live-updating split total as you type. Used: add-expense sheet.
- **SettleUpLedgerRow** — payer→payee + amount in Ledger Numeral, collapsible "show the math" strip. Used: settle-up screen.
- **DemoStampBadge** — one component, referenced identically by trip switcher, day view header, widget, and Live Activity. Used: anywhere demo data appears.
- **PackingTally** — ledger-style fraction, not a progress bar. Used: packing checklist.
- **CalendarExportSummarySheet** — explicit created/updated/skipped counts. Used: calendar export confirmation.
- **EmptyStateCard** — icon + one-line copy + primary action, reused across every empty state. Used: day view, settle-up, packing, trip switcher.

### DESIGN SPEC — Navigation
Not a tab-bar app — tab bars imply co-equal destinations, which this IA explicitly rejects. Root: `NavigationStack` (iPhone) / `NavigationSplitView` (iPad) starting at the trip switcher. Day view is the persistent detail destination once a trip is selected; travelers/expenses/settle-up/packing/calendar export/settings are sheets or push destinations off a toolbar that's always present on the day view. **iPad split-view scope is narrow and specific**: the two-pane split (itinerary list / map) activates only inside the day view — trip switcher, settle-up, and packing stay full-width even on iPad. Wrapping the whole app in one top-level `NavigationSplitView` is the wrong implementation and would silently violate DEC-prompt_contract-011.

**Two-way pin/row selection** (flagged as the single highest state-management risk in the app): one source of truth, `@State selectedStopID: PersistentIdentifier?` owned by the day view. Both map annotation selection and list row highlight read/write that same value — never two separate `@State` vars synced via `.onChange`. Tap-stop → `ScrollViewReader.scrollTo` + animated `MapCameraPosition` to a fixed span (not zoom-to-fit); tap-pin → reverse, same setter.

**Atomic drag sequencing**: the SwiftData move happens in a single transaction/save that completes *before* the page-flip animation resolves — animation is sequenced off write completion, never run optimistically ahead of it, so a real write failure can't be visually lied about. Route line only recomputes once a drop completes, never on intermediate drag frames.

**Cross-target sharing**: Theme.swift and shared components (DemoStampBadge, CategoryPin, Ledger Numeral text styles) must live in a shared Swift Package or shared-sources group importable by the main app, the WidgetKit extension, and the Live Activity target — set this up from the start or the demo marker will visually drift across surfaces within a few build iterations, breaking DEC-prompt_contract-006.

### DESIGN SPEC — Screen States
- **Day view**: empty (new trip, zero stops → EmptyStateCard, action = add first stop) vs. complete (all stops checked off on a day → distinct "complete" treatment, not empty).
- **Settle-up**: three distinct states, not one — no expenses yet (plain empty state, never a misleading "$0 owed" that reads as a real answer); balanced (explicit "Settled" state, visually distinct from the no-data state); outstanding balances (full SettleUpLedgerRow list with arithmetic strip).
- **Map view**: loading (fetching route) is visually distinct from approximate-fallback (route unavailable) — one is transient, one is a standing condition; different treatment, not just different text.
- **Calendar export**: four distinct outcomes, each with its own icon/copy — first-time success, re-export with updates, permission denied, externally-deleted-event detected. Do not collapse these into one generic sheet with swapped text.
- **Trip switcher**: empty (no trips at all, not even demo) vs. populated (Active/Upcoming/Past groups, demo trip visibly stamped).
- **Packing checklist**: empty (no items yet) vs. populated (PackingTally + list).

### DESIGN SPEC — Motion & Haptics
- Ledger page flip: spring (response ≈0.45, dampingFraction ≈0.8); `UIImpactFeedbackGenerator(.medium)` fires at the moment the page visually closes (tied to data landing, not finger-lift or drag-start).
- Check off a stop: light impact + 0.2s ease-out strike-through.
- Settle-up reaching zero: `UINotificationFeedbackGenerator(.success)` fires once, on the transition from unbalanced→balanced only, never on every screen load.
- All other navigation: system default push/pop — no invented motion on screens without narrative weight.

### DESIGN SPEC — Accessibility
- "Move to..." is a first-class context-menu item on every stop card (not hidden behind edit mode).
- Custom map pins carry real `.accessibilityLabel`s naming category + stop name.
- Every icon-only toolbar control (map toggle, add-stop, settings gear) gets an explicit `.accessibilityLabel`.
- RunningBalancePreview announces value changes via `.accessibilityValue`.
- DayRibbon compact numerals carry full labels ("Day 8, March 14"), never a bare digit.
- Card contrast verified in both light and dark before ship; Dynamic Type reflows ticket-stub cards taller — a clipped time or dollar amount is a trust failure, not a cosmetic bug, and blocks ship.

### DESIGN SPEC — Spacing
Base unit: 8pt. Named steps: `xs=4` (icon-to-label gaps) · `sm=8` · `md=12` · `lg=16` (default card padding) · `xl=24` (section gaps) · `xxl=32` · `xxxl=40` (major screen breaks).

### DESIGN SPEC — Semantic Color Palette (light / dark)
- Background: `#F7F1E3` / `#1C1810` (warm paper / deep ink-brown — never pure black)
- Surface (cards): `#FFFDF6` / `#26211A`
- Text primary (ink): `#2B2118` / `#EDE4D3`
- Text secondary: `#6B5D4F` / `#A89B87`
- Accent (brass/amber — replaces system blue everywhere, incl. tab selection, buttons, links, drag-highlight): `#A66F1E` / `#D9A44E`
- Success/positive (forest — packed, positive balance; kept visually distinct from accent): `#3F5D3A` / `#7FA873`

- Error (validation, permission-denied): `#A23B2E` / `#E0796A`
- Hairline/divider: `#D8CBB4` / `#3A3327`

All roles must pass WCAG contrast against their own background and against surface in both appearances before ship, per DEC-design_discussion-001's constraint — paper/ink-brown is the riskiest pairing and should be checked first.

### DESIGN SPEC — Corner Radii
`small=6` (chips, badges) · `medium=12` (buttons, sheets) · `large=20` (ticket-stub card non-perforated corners). The perforated left edge is a custom `Shape` (`TicketStubBackground`), not a corner radius — one reusable implementation, never redrawn per screen.

### DESIGN SPEC — Component Inventory
- **TicketStubStopCard** — perforated left edge, category icon badge, time range in Ledger Numeral, notes reflow taller under Dynamic Type (never clip). Used: day view stop list.
- **DayRibbon** — full-tab mode ≤7 days, compact numeral-only mode >7 days, same underlying day-index model for both. Used: day view header.
- **LedgerPageFlip** — shared `ViewModifier`/custom transition for cross-day moves (one implementation, not per-call-site). Used: drag-reorder across days.
- **CategoryPin** — custom `Marker`/`Annotation`, enum-keyed, each case carries a symbol + accessibility label. Used: map view.
- **RunningBalancePreview** — live-updating split total as you type. Used: add-expense sheet.
- **SettleUpLedgerRow** — payer→payee + amount in Ledger Numeral, collapsible "show the math" strip. Used: settle-up screen.
- **DemoStampBadge** — one component, referenced identically by trip switcher, day view header, widget, and Live Activity. Used: anywhere demo data appears.
- **PackingTally** — ledger-style fraction, not a progress bar. Used: packing checklist.
- **CalendarExportSummarySheet** — explicit created/updated/skipped counts. Used: calendar export confirmation.
- **EmptyStateCard** — icon + one-line copy + primary action, reused across every empty state. Used: day view, settle-up, packing, trip switcher.

### DESIGN SPEC — Navigation
Not a tab-bar app — tab bars imply co-equal destinations, which this IA explicitly rejects. Root: `NavigationStack` (iPhone) / `NavigationSplitView` (iPad) starting at the trip switcher. Day view is the persistent detail destination once a trip is selected; travelers/expenses/settle-up/packing/calendar export/settings are sheets or push destinations off a toolbar that's always present on the day view. **iPad split-view scope is narrow and specific**: the two-pane split (itinerary list / map) activates only inside the day view — trip switcher, settle-up, and packing stay full-width even on iPad. Wrapping the whole app in one top-level `NavigationSplitView` is the wrong implementation and would silently violate DEC-prompt_contract-011.

**Two-way pin/row selection** (flagged as the single highest state-management risk in the app): one source of truth, `@State selectedStopID: PersistentIdentifier?` owned by the day view. Both map annotation selection and list row highlight read/write that same value — never two separate `@State` vars synced via `.onChange`. Tap-stop → `ScrollViewReader.scrollTo` + animated `MapCameraPosition` to a fixed span (not zoom-to-fit); tap-pin → reverse, same setter.

**Atomic drag sequencing**: the SwiftData move happens in a single transaction/save that completes *before* the page-flip animation resolves — animation is sequenced off write completion, never run optimistically ahead of it, so a real write failure can't be visually lied about. Route line only recomputes once a drop completes, never on intermediate drag frames.

**Cross-target sharing**: Theme.swift and shared components (DemoStampBadge, CategoryPin, Ledger Numeral text styles) must live in a shared Swift Package or shared-sources group importable by the main app, the WidgetKit extension, and the Live Activity target — set this up from the start or the demo marker will visually drift across surfaces within a few build iterations, breaking DEC-prompt_contract-006.

### DESIGN SPEC — Screen States
- **Day view**: empty (new trip, zero stops → EmptyStateCard, action = add first stop) vs. complete (all stops checked off on a day → distinct "complete" treatment, not empty).
- **Settle-up**: three distinct states, not one — no expenses yet (plain empty state, never a misleading "$0 owed" that reads as a real answer); balanced (explicit "Settled" state, visually distinct from the no-data state); outstanding balances (full SettleUpLedgerRow list with arithmetic strip).
- **Map view**: loading (fetching route) is visually distinct from approximate-fallback (route unavailable) — one is transient, one is a standing condition; different treatment, not just different text.
- **Calendar export**: four distinct outcomes, each with its own icon/copy — first-time success, re-export with updates, permission denied, externally-deleted-event detected. Do not collapse these into one generic sheet with swapped text.
- **Trip switcher**: empty (no trips at all, not even demo) vs. populated (Active/Upcoming/Past groups, demo trip visibly stamped).
- **Packing checklist**: empty (no items yet) vs. populated (PackingTally + list).

### DESIGN SPEC — Motion & Haptics
- Ledger page flip: spring (response ≈0.45, dampingFraction ≈0.8); `UIImpactFeedbackGenerator(.medium)` fires at the moment the page visually closes (tied to data landing, not finger-lift or drag-start).
- Check off a stop: light impact + 0.2s ease-out strike-through.
- Settle-up reaching zero: `UINotificationFeedbackGenerator(.success)` fires once, on the transition from unbalanced→balanced only, never on every screen load.
- All other navigation: system default push/pop — no invented motion on screens without narrative weight.

### DESIGN SPEC — Accessibility
- "Move to..." is a first-class context-menu item on every stop card (not hidden behind edit mode).
- Custom map pins carry real `.accessibilityLabel`s naming category + stop name.
- Every icon-only toolbar control (map toggle, add-stop, settings gear) gets an explicit `.accessibilityLabel`.
- RunningBalancePreview announces value changes via `.accessibilityValue`.
- DayRibbon compact numerals carry full labels ("Day 8, March 14"), never a bare digit.
- Card contrast verified in both light and dark before ship; Dynamic Type reflows ticket-stub cards taller — a clipped time or dollar amount is a trust failure, not a cosmetic bug, and blocks ship.

### Claude Design / external tooling decision
**No external Claude Design pass required.** The token values, component list, and state matrix above are complete enough for a SwiftUI builder to write Theme.swift and the core views directly with zero invented values. Optional (non-blocking) polish: a scoped illustration pass for the `TicketStubBackground` perforated-edge texture and the `CategoryPin` icon set, since those are the two purely graphical elements that would benefit from an illustrator's eye over a programmatic shape. SF Symbols + a hand-coded perforation path are a fully sufficient fallback if that optional pass doesn't happen — build should proceed without waiting on it.
