## Original Prompt

```
Build a polished, fully offline iOS trip-planning app called "Waypoint".
Native Apple stack only: SwiftUI + SwiftData for persistence, MapKit for
all mapping, ActivityKit for Live Activities, EventKit for calendar
export. No backend, no accounts, no third-party SDKs, no network calls
except on-device MapKit/local geocoding (which works offline-cached but
may need network for tile fetch — if a feature would require live
network for correctness, don't fake it; record it as a gap). Follow the
ios-app-factory-rules.

Core features (complete over broad — ship fewer things fully working):

1. Trips & itinerary: create trips with a date range; each trip has
   multiple days; each day has an ordered list of stops (place name,
   address, optional MapKit-resolved coordinate, time window, notes,
   category icon). Reorder stops via drag-and-drop within a day AND
   across days. Get date math right across the trip's date range,
   including a trip that starts and ends on the same day and a
   single-day trip.

2. Map view: a MapKit view per day showing all of that day's stops as
   annotations connected by a route line (MKDirections walking/driving,
   gracefully degrading to a straight-line polyline with a visible
   "approximate" indicator if MKDirections has no network). Tapping a
   stop centers the map and highlights it; tapping a map pin selects
   the corresponding itinerary row (two-way binding).

3. Expense splitting: a per-trip list of travelers (name, no accounts).
   Log expenses (amount, payer, split method: equal / exact amounts /
   percentage) against any subset of travelers. A settle-up screen
   computing the minimum set of payments to zero every balance (the
   classic debt-simplification graph problem — get this genuinely
   correct, including rounding remainders so amounts always sum
   exactly). Use Decimal, never Double, for money.

4. Packing lists: per-trip checklist, templates the user can save and
   reapply to future trips, a "packed %" indicator.

5. Live Activity: while a trip is "active" (today falls within its date
   range), a Live Activity / Dynamic Island showing the current or next
   stop and time until it, updating as stops are checked off. Must
   degrade gracefully (no crash, no Live Activity) on devices/OS
   versions without support, and when the user denies the permission.

6. Calendar export: export a day's stops as EventKit calendar events
   (with the user's explicit permission), one event per stop honoring
   its time window; must not create duplicate events if exported twice
   for the same day — detect and either skip or update existing ones.

7. Home-screen widget (WidgetKit, separate target): shows the active
   trip's next stop, or "no active trip" honestly if none.

8. iPad: itinerary list and map must work as a genuine two-column split
   view on iPad, not just a stretched phone layout.

Priorities: the debt-simplification math, the drag-reorder data
integrity (no duplicate/lost stops across days), and honest degradation
of every system-permission-gated feature (Live Activities, Calendar,
location) — never fake success when a permission is denied or a
capability is unavailable in the Simulator. Explicitly call out in a
Gaps section anything requiring infrastructure this project can't
provide (live traffic data, real-time flight tracking, iCloud trip
sync). Seed a "demo trip" toggle in Settings with realistic multi-day
sample data so no screen is empty on first review. Provide a clear way
to run it in the iOS Simulator via Xcode.
```

**Claude (QA & Risk · Skeptic) — Round 1**

I want to push on the seams that haven't actually been nailed down yet, even though a lot of the hard math and permission-degradation stuff is already locked from earlier phases.

First, trip date-range editing after stops already exist. Nobody's said what happens when a user creates a 5-day trip, adds stops to day 4, then edits the trip to be 3 days. Do those day-4 stops get deleted, silently orphaned, or does the app refuse to shrink the range while stops exist on the trimmed days? This is the same category of bug as the drag-integrity problem everyone's worried about, just triggered by trip editing instead of dragging, and if it's not decided now it'll get built as an afterthought — probably as a silent cascade delete, which is a real data-loss risk nobody consented to. I'd resolve this now: shrinking a trip's date range that would orphan stops on removed days must block the edit and surface exactly which days/stops are affected, forcing the user to move or delete those stops first. Extending the range is trivially safe and needs no gate.

Second, the percentage-split remainder rule only covers rounding cents, not the case where user-entered percentages don't sum to 100 at all (which product_research explicitly flagged as an adversarial test case but never resolved into a UI/data rule). Does the app auto-scale entered percentages proportionally to sum to 100, reject the expense with a validation error, or store it as entered and let the imbalance flow into settle-up? These produce different settle-up totals for the same input, so this needs one deterministic answer, not "the algorithm should be smart about it." My vote: reject at entry time with a clear inline error ("percentages sum to 97%, add 3% somewhere") rather than silently rescaling, because silent rescaling is exactly the kind of "quiet reinterpretation of what the user typed" that violates the honesty principle already established for this app.

Third, drag-and-drop reordering has no accessible alternative on the table anywhere in this thread. VoiceOver users cannot perform a drag gesture reliably, and Apple's own HIG treats this as a real access requirement, not a nice-to-have. If the entire cross-day integrity guarantee is only exercised through a drag gesture, this app is unusable for a chunk of users and untestable by non-visual means. There needs to be a parallel "Move to..." action (context menu or edit-mode button) that goes through the exact same atomic SwiftData operation as the drag path — not a second, divergent code path that could reintroduce the duplication bug everyone's so focused on preventing in the gesture-based path.

Fourth, the demo-trip toggle's actual state machine has a gap: what happens on repeated on/off/on toggling? If toggling on always inserts a fresh demo trip, toggling it off and back on twice creates two demo trips, which is either confusing or a subtle duplication bug hiding behind a "feature." I'd lock this as: the demo trip is a singleton keyed by a stable identifier; toggling on either creates it if absent or does nothing if present; toggling off deletes that exact trip and nothing else (never touches real user trips even if their names or dates coincidentally overlap).

Fifth — and this feels like a sleeper risk — timezones. Stops have time windows, trips can plausibly span timezone changes if someone flies partway through (the prompt doesn't rule this out), and "today falls within the trip's date range" for Live Activity purposes depends entirely on which timezone is being used to compute "today." Nothing so far specifies whether stop times are stored in a fixed timezone (the trip's origin) or interpreted in the device's current timezone, and that ambiguity will produce genuinely different, hard-to-debug behavior for any trip crossing a timezone boundary. I'd rather explicitly scope this: all times are stored and displayed in the device's current local timezone at all times, with an explicit named Gap that true timezone-aware itineraries (e.g., a stop's time window fixed to its destination's local time regardless of device timezone) are out of scope — rather than silently getting this right for domestic trips and wrong for international ones without ever having decided it on purpose.

Finally, the debug/demo current-date injection hook from DEC-prompt_contract-009 needs a hard technical boundary stated now, not left to the build phase's judgment: it must be compiled out of release builds entirely (`#if DEBUG`), not just hidden behind a settings flag, because a settings-flag-only gate is discoverable and could let a real user or App Review reviewer put the app into a fake "trip is active" state that isn't actually true — which is precisely the kind of fake-success scenario this whole project is trying to avoid.
