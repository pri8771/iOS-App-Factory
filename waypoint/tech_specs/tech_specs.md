8. iPad: itinerary list and map must work as a genuine two-column split

location) — never fake success when a permission is denied or a
capability is unavailable in the Simulator. Explicitly call out in a

## Final Output

**Architecture**: One Xcode project, two build targets (Waypoint app, WaypointWidget extension), plus a local Swift Package **WaypointKit** imported by both. WaypointKit owns everything that must never visually or behaviorally drift across surfaces: the SwiftData model schema, Theme.swift, shared components (DemoStampBadge, CategoryPin, Ledger Numeral text style), and the plain services (StopReorderService, SettlementEngine, CalendarExportService, DemoSeeder, ActiveTripResolver, TravelerDeletionGuard, DayRangeGuard). The app target owns screen-specific UI (TripSwitcher, DayView+MapKit pane, StopDetail, Travelers/Expenses/SettleUp, Packing, CalendarExportSummarySheet, Settings). The widget target owns a thin NextStopWidget TimelineProvider and the Live Activity's ActivityConfiguration, both reading through the App Group–backed ModelContainer and rendering WaypointKit's shared components only — no reimplemented presentation logic. If local-SPM-package-with-@Model-across-two-targets hits real Xcode friction, the fallback is a shared-sources file group added to both targets — the hard invariant is "one copy of model/theme/component code," not the packaging mechanism.

**Data model**: Trip → Day (real persisted row per calendar day, never computed) → Stop (day is non-optional — the core drag-integrity invariant), plus Traveler, Expense/ExpenseSplit (amountCents/shareCents stored as the Int source of truth at rest, with a computed Decimal `amount` accessor for entry/display only — never two independently-stored representations), PackingItem, and PackingTemplate/PackingTemplateItem for the should-have reuse feature. All child collections cascade-delete with their Trip.

**New this round — a real gap closed**: deleting a Traveler who's a payer or split participant on any expense was completely unguarded. That's now blocked the same way the day-range shrink is blocked: `TravelerDeletionGuard.blockingExpenses(for:)` returns the referencing expenses, deletion is refused while that list is non-empty, and the UI must show exactly which expenses reference them.

**Persistence**: A versioned `Schema`/`SchemaMigrationPlan` from day one (`WaypointSchemaV1`) rather than an unversioned container, since later build slices (packing templates, calendar fields, Live Activity/widget/StoreKit fields) will all want schema changes — cheap to version now, painful to retrofit later. One `ModelConfiguration` with `cloudKitDatabase: .none` set explicitly (not just absent) and `groupContainer:` pointed at the App Group, shared by the app and widget extension; the same App Group backs the `#if DEBUG` current-date override.

**Concurrency**: StopReorderService and SettlementEngine stay synchronous/main-actor, operating directly on model objects with a passed `ModelContext` — no async work in either, which keeps the atomic-save-then-animate sequencing simple. CalendarExportService and MKDirections calls are genuinely async: they extract plain Sendable DTOs from model objects *before* crossing an `await` boundary, then apply results back on the main actor afterward — a live `PersistentModel` reference is never held across an awaited system call.

**Performance stance**: given trip/day/stop counts are small by construction, fetch `Trip` and traverse `trip.days`/`day.stops` directly, sorting in plain Swift, rather than reaching for relationship-traversing `#Predicate`s — simpler to reason about against the atomic-move invariant, with no dataset size here where predicate pushdown would matter. The widget gets a real `widgetURL` deep link (`waypoint://trip/<id>/day/<id>`) so tapping "next stop" actually opens that day — this is the already-committed widget feature actually working, not new scope.

**Testing**: carries forward the locked strategy (in-memory `ModelContainer` XCTest for SettlementEngine/StopReorderService, Move-to-driven repeated cross-day stress test, manual verification of the actual finger-drag) and adds two new adversarial cases: the traveler-deletion guard, and a stress-trip perf sanity check (30 days × 10 stops, 8 travelers, 40 expenses) confirming the settlement engine's minimum-transaction result stays correct at scale, not just at demo scale.

## Final Output

**Architecture**: One Xcode project, two build targets (Waypoint app, WaypointWidget extension), plus a local Swift Package **WaypointKit** imported by both. WaypointKit owns everything that must never visually or behaviorally drift across surfaces: the SwiftData model schema, Theme.swift, shared components (DemoStampBadge, CategoryPin, Ledger Numeral text style), and the plain services (StopReorderService, SettlementEngine, CalendarExportService, DemoSeeder, ActiveTripResolver, TravelerDeletionGuard, DayRangeGuard). The app target owns screen-specific UI (TripSwitcher, DayView+MapKit pane, StopDetail, Travelers/Expenses/SettleUp, Packing, CalendarExportSummarySheet, Settings). The widget target owns a thin NextStopWidget TimelineProvider and the Live Activity's ActivityConfiguration, both reading through the App Group–backed ModelContainer and rendering WaypointKit's shared components only — no reimplemented presentation logic. If local-SPM-package-with-@Model-across-two-targets hits real Xcode friction, the fallback is a shared-sources file group added to both targets — the hard invariant is "one copy of model/theme/component code," not the packaging mechanism.

**Data model**: Trip → Day (real persisted row per calendar day, never computed) → Stop (day is non-optional — the core drag-integrity invariant), plus Traveler, Expense/ExpenseSplit (amountCents/shareCents stored as the Int source of truth at rest, with a computed Decimal `amount` accessor for entry/display only — never two independently-stored representations), PackingItem, and PackingTemplate/PackingTemplateItem for the should-have reuse feature. All child collections cascade-delete with their Trip.

**New this round — a real gap closed**: deleting a Traveler who's a payer or split participant on any expense was completely unguarded. That's now blocked the same way the day-range shrink is blocked: `TravelerDeletionGuard.blockingExpenses(for:)` returns the referencing expenses, deletion is refused while that list is non-empty, and the UI must show exactly which expenses reference them.

**Persistence**: A versioned `Schema`/`SchemaMigrationPlan` from day one (`WaypointSchemaV1`) rather than an unversioned container, since later build slices (packing templates, calendar fields, Live Activity/widget/StoreKit fields) will all want schema changes — cheap to version now, painful to retrofit later. One `ModelConfiguration` with `cloudKitDatabase: .none` set explicitly (not just absent) and `groupContainer:` pointed at the App Group, shared by the app and widget extension; the same App Group backs the `#if DEBUG` current-date override.

**Concurrency**: StopReorderService and SettlementEngine stay synchronous/main-actor, operating directly on model objects with a passed `ModelContext` — no async work in either, which keeps the atomic-save-then-animate sequencing simple. CalendarExportService and MKDirections calls are genuinely async: they extract plain Sendable DTOs from model objects *before* crossing an `await` boundary, then apply results back on the main actor afterward — a live `PersistentModel` reference is never held across an awaited system call.

**Performance stance**: given trip/day/stop counts are small by construction, fetch `Trip` and traverse `trip.days`/`day.stops` directly, sorting in plain Swift, rather than reaching for relationship-traversing `#Predicate`s — simpler to reason about against the atomic-move invariant, with no dataset size here where predicate pushdown would matter. The widget gets a real `widgetURL` deep link (`waypoint://trip/<id>/day/<id>`) so tapping "next stop" actually opens that day — this is the already-committed widget feature actually working, not new scope.

**Testing**: carries forward the locked strategy (in-memory `ModelContainer` XCTest for SettlementEngine/StopReorderService, Move-to-driven repeated cross-day stress test, manual verification of the actual finger-drag) and adds two new adversarial cases: the traveler-deletion guard, and a stress-trip perf sanity check (30 days × 10 stops, 8 travelers, 40 expenses) confirming the settlement engine's minimum-transaction result stays correct at scale, not just at demo scale.
