## Original Prompt

```
Build a polished, fully offline iOS trip-planning app called "Waypoint".
Native Apple stack only: SwiftUI + SwiftData for persistence, MapKit for
all mapping, ActivityKit for Live Activities, EventKit for calendar
export. No backend, no accounts, no third-party SDKs, no network calls
except on-device MapKit/local geocoding (which works offline-cached but
may need network for tile fetch — if a feature would require live
network for correctness, don't fake it; record it as a gap). Follow the
ios-app-factory-rules.

Core features (complete over broad — ship fewer things fully working):

1. Trips & itinerary: create trips with a date range; each trip has
   multiple days; each day has an ordered list of stops (place name,
   address, optional MapKit-resolved coordinate, time window, notes,
   category icon). Reorder stops via drag-and-drop within a day AND
   across days. Get date math right across the trip's date range,
   including a trip that starts and ends on the same day and a
   single-day trip.

2. Map view: a MapKit view per day showing all of that day's stops as
   annotations connected by a route line (MKDirections walking/driving,
   gracefully degrading to a straight-line polyline with a visible
   "approximate" indicator if MKDirections has no network). Tapping a
   stop centers the map and highlights it; tapping a map pin selects
   the corresponding itinerary row (two-way binding).

3. Expense splitting: a per-trip list of travelers (name, no accounts).
   Log expenses (amount, payer, split method: equal / exact amounts /
   percentage) against any subset of travelers. A settle-up screen
   computing the minimum set of payments to zero every balance (the
   classic debt-simplification graph problem — get this genuinely
   correct, including rounding remainders so amounts always sum
   exactly). Use Decimal, never Double, for money.

4. Packing lists: per-trip checklist, templates the user can save and
   reapply to future trips, a "packed %" indicator.

5. Live Activity: while a trip is "active" (today falls within its date
   range), a Live Activity / Dynamic Island showing the current or next
   stop and time until it, updating as stops are checked off. Must
   degrade gracefully (no crash, no Live Activity) on devices/OS
   versions without support, and when the user denies the permission.

6. Calendar export: export a day's stops as EventKit calendar events
   (with the user's explicit permission), one event per stop honoring
   its time window; must not create duplicate events if exported twice
   for the same day — detect and either skip or update existing ones.

7. Home-screen widget (WidgetKit, separate target): shows the active
   trip's next stop, or "no active trip" honestly if none.

8. iPad: itinerary list and map must work as a genuine two-column split
   view on iPad, not just a stretched phone layout.

Priorities: the debt-simplification math, the drag-reorder data
integrity (no duplicate/lost stops across days), and honest degradation
of every system-permission-gated feature (Live Activities, Calendar,
location) — never fake success when a permission is denied or a
capability is unavailable in the Simulator. Explicitly call out in a
Gaps section anything requiring infrastructure this project can't
provide (live traffic data, real-time flight tracking, iCloud trip
sync). Seed a "demo trip" toggle in Settings with realistic multi-day
sample data so no screen is empty on first review. Provide a clear way
to run it in the iOS Simulator via Xcode.
```

**Claude (Design Lead · User Advocate) — Round 1**

I want to name this design language precisely: **Trail Ledger** — the visual grammar of a well-kept paper logbook a trip captain carries, crossed with the tactile precision of a ledger book where numbers always have to balance. Rationale: the two things this app has staked its credibility on are itinerary integrity (never losing or duplicating a stop) and settlement math (numbers that sum to the cent) — a ledger's entire visual purpose is showing work that provably adds up, and a trail log's purpose is telling you plainly where you are and what's next. That's not a generic "travel app" aesthetic; it's specific to an app whose whole pitch is "trustworthy even when everything else about your trip is uncertain." Warm paper-toned backgrounds, deep ink/forest text, a brass or amber accent instead of system blue, tabular monospaced numerals for every time and every dollar amount so columns of numbers visually align and are scannable at a glance — that's Trail Ledger, and it would be wrong for almost any other app in this factory.

The person I'm building for is Priya, standing on a train platform with one bar of signal, four days into a trip with her partner and two friends. She doesn't want to browse — she wants to glance at her phone, see the next stop and how long until it, and later that night check whether Jake still owes her money before everyone splits up. The emotional target for the day view, which is the center of gravity of this whole app, is: she should feel like a competent captain glancing at a logbook that's always right, not like she's operating software. Calm, oriented, zero friction — never "let me figure out what this screen is telling me."

The signature interaction is the day ribbon: a horizontal strip of day tabs at the top of the day view, styled like ledger page tabs, that you swipe or tap through, with the stop list and map animating together underneath. The moment that really sells the atomicity guarantee — and this is the one hero interaction I'd actually build first — is dragging a stop onto a different day's tab: the destination tab visually "opens" like a ledger page flipping to receive it, the stop slides in, the page snaps shut with a haptic tick, and at every single frame of that animation the stop is visibly inside exactly one page. That's not just a nice motion — it's the UI telling the truth about the underlying atomic operation, which is exactly the trust this whole build is supposed to earn.

Here's what I'm explicitly rejecting, and why it matters that I name the differences concretely rather than just say "make it nicer." A default build of this app would be a plain SwiftUI List with system separators for stops, standard blue accent color and blue Back buttons, default red MKPinAnnotationView pins on the map, and a modal Form sheet for expense entry with plain labeled rows and a Save button you tap blind. I'm rejecting all four specifically: stops render as ticket-stub cards with a torn/perforated left edge (visually reinforcing "this is one leg of your trip," not a row in a database), the accent is a warm brass/amber with ink-toned text instead of system blue anywhere in the app, map pins are custom shapes keyed to the stop's category icon (a fork, a bed, a camera) rather than generic drops, and expense entry shows a live-updating running balance preview as you type each split — not just a static form you submit into a void. If a SwiftUI dev built this from a "clean and modern" brief with none of those four calls made, it would be indistinguishable from every other list-based utility app on the App Store, which is the opposite of what this app has earned through its math.

On screens: the trip switcher opens the app when there's more than one trip or none yet, grouped into Active/Upcoming/Past, with the demo trip visibly stamped (I'd render its ledger tab in a different ink color plus a literal "DEMO" stamp graphic, not just a text label, so it reads as unmistakably fake even in a glance). The day view is the hub — stop list on one side, map on the other (true two-pane on iPad, stacked with the map collapsible on iPhone), day ribbon on top, and this is where checking off a stop, tapping a pin to select a row, and dragging to reorder all live. Stop detail/edit is a sheet reachable from any stop. Trip create/edit handles the date range, including the shrink-guard flow where trying to remove days with stops shows exactly which stops are blocked, inline, not as a separate error screen. Travelers, add-expense, and settle-up are one tap off the day view via a persistent trip toolbar, never buried — settle-up in particular should show its math almost audit-style: who pays whom, and beneath that, in smaller ledger-style type, the arithmetic proving the amounts sum to the original total, because "trust me" is not this app's voice. Packing is a checklist screen with the packed-% as a ledger-style tally rather than a generic progress bar. Calendar export is a confirmation sheet showing which stops will become events and, on re-export, explicitly showing "3 updated, 0 created" rather than silently succeeding. Settings holds the demo toggle and any Pro/StoreKit surfaces. Live Activity and widget, given their locked should-have status, get designed but every piece of copy describing their state has to read honestly — "next: Ferry to Capri, 2h 10m," never a stale timestamp presented as live.

Every screen needs its real state set, not just the happy path: the day view empty state (a new trip with zero stops yet) needs actual designed content — an illustration-weight icon plus "Add your first stop" — not a blank paper background pretending to be intentional. Settle-up's empty state (no expenses logged yet) has to say that plainly rather than showing a fake "$0 owed to everyone" that looks like a real answer. Calendar export's error states (permission denied, event deleted externally) need distinct copy from each other, not one generic "something went wrong."

On accessibility: the Move-to action already locked in an earlier phase needs to be a first-class context-menu item on every stop card, not a hidden edit-mode toggle — Priya's mother-in-law using VoiceOver should find it as easily as the drag.
