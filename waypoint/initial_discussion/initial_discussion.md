## Original Prompt

```
Build a polished, fully offline iOS trip-planning app called "Waypoint".
Native Apple stack only: SwiftUI + SwiftData for persistence, MapKit for
all mapping, ActivityKit for Live Activities, EventKit for calendar
export. No backend, no accounts, no third-party SDKs, no network calls
except on-device MapKit/local geocoding (which works offline-cached but
may need network for tile fetch — if a feature would require live
network for correctness, don't fake it; record it as a gap). Follow the
ios-app-factory-rules.

Core features (complete over broad — ship fewer things fully working):

1. Trips & itinerary: create trips with a date range; each trip has
   multiple days; each day has an ordered list of stops (place name,
   address, optional MapKit-resolved coordinate, time window, notes,
   category icon). Reorder stops via drag-and-drop within a day AND
   across days. Get date math right across the trip's date range,
   including a trip that starts and ends on the same day and a
   single-day trip.

2. Map view: a MapKit view per day showing all of that day's stops as
   annotations connected by a route line (MKDirections walking/driving,
   gracefully degrading to a straight-line polyline with a visible
   "approximate" indicator if MKDirections has no network). Tapping a
   stop centers the map and highlights it; tapping a map pin selects
   the corresponding itinerary row (two-way binding).

3. Expense splitting: a per-trip list of travelers (name, no accounts).
   Log expenses (amount, payer, split method: equal / exact amounts /
   percentage) against any subset of travelers. A settle-up screen
   computing the minimum set of payments to zero every balance (the
   classic debt-simplification graph problem — get this genuinely
   correct, including rounding remainders so amounts always sum
   exactly). Use Decimal, never Double, for money.

4. Packing lists: per-trip checklist, templates the user can save and
   reapply to future trips, a "packed %" indicator.

5. Live Activity: while a trip is "active" (today falls within its date
   range), a Live Activity / Dynamic Island showing the current or next
   stop and time until it, updating as stops are checked off. Must
   degrade gracefully (no crash, no Live Activity) on devices/OS
   versions without support, and when the user denies the permission.

6. Calendar export: export a day's stops as EventKit calendar events
   (with the user's explicit permission), one event per stop honoring
   its time window; must not create duplicate events if exported twice
   for the same day — detect and either skip or update existing ones.

7. Home-screen widget (WidgetKit, separate target): shows the active
   trip's next stop, or "no active trip" honestly if none.

8. iPad: itinerary list and map must work as a genuine two-column split
   view on iPad, not just a stretched phone layout.

Priorities: the debt-simplification math, the drag-reorder data
integrity (no duplicate/lost stops across days), and honest degradation
of every system-permission-gated feature (Live Activities, Calendar,
location) — never fake success when a permission is denied or a
capability is unavailable in the Simulator. Explicitly call out in a
Gaps section anything requiring infrastructure this project can't
provide (live traffic data, real-time flight tracking, iCloud trip
sync). Seed a "demo trip" toggle in Settings with realistic multi-day
sample data so no screen is empty on first review. Provide a clear way
to run it in the iOS Simulator via Xcode.
```

## Transcript


### Round 1


**Codex (Product Strategist · User Advocate) — Round 1**

Waypoint is one app that turns a trip’s local itinerary, map, packing, and expense data into one trustworthy offline-first trip state machine on-device in SwiftUI + SwiftData, so a traveler can plan multi-day travel end-to-end without accounts, cloud sync, or fake network-dependent success claims.

The primary user is a couple, family, or small friend group coordinator planning a multi-day trip on one phone, and the core scenario is “I’m moving through day-by-day stops, need honest map routing and expense visibility even with weak signal, and want quick confidence that packing, route, and settlement math are all consistent.”

The core loop is: create a trip with a date range, add day-by-day stops with names, addresses, optional coordinates, notes, and time windows, reorder those stops within and across days, execute the trip while checking off stops (which updates map focus and activity surfaces), then review/check off packing progress and split settlement, with calendar export as a cleanup action.

Hard scope boundaries are: no backend, no accounts, no third-party SDKs, no CloudKit sync, no live traffic or real-time flight tracking, no cross-device collaborative editing, and no pretending a route/calendar/live feature worked when permission or capability was denied/unavailable.

Success is measurable only if: a user can create and reopen a single-day or multi-day trip with correct day math; any cross-day drag move preserves stop identity and time window in a single atomic move with no duplicated or orphaned stops; per-day maps render either actual directions or a visibly labeled approximate straight-line route fallback when directions are unavailable; settlements use decimal arithmetic with deterministic remainder handling and emit a minimum-transaction set that resolves all balances to zero exactly; packing shows correct packed percentage; EventKit export never creates duplicate events on re-export and updates existing ones or skips cleanly with explicit status; the iPad shows true independent two-column interaction between itinerary and map; demo data exists behind a toggle and is clearly marked “Demo”; and every permission-gated surface (Live Activity, EventKit, MapKit routing network need) degrades visibly and safely without crash or false success.

Biggest risk in this direction is that the trip model can be “correct enough” in demos but still break trust in production-like use, so the final output must preserve atomic state transitions (especially drag across days) and explicit failure handling as first-class behavior, not edge-case code paths.

**Claude (Design Lead · Systems Thinker) — Round 1**

Waypoint's product promise, stated as tight as I can make it: a single-device, fully offline iOS app that lets a small group of trip-mates build a day-by-day itinerary with drag-reordered stops, see each day on a map with honest routing (real or approximate, never faked), split shared costs down to the exact minimum set of settling payments, and pack without forgetting anything — with a Live Activity and widget that surface where the trip stands right now, all without ever touching a server or an account.

The primary user I'm designing for is the one person in the group who actually opens apps and organizes things — call them the trip owner. They're on their own phone, planning before the trip and referencing during it. The scenario that matters most isn't the planning-at-home session, it's mid-trip: standing outside a restaurant with three other people, dead phone signal, trying to answer "where do we go next, what time, and who still owes me for last night." Everything about the UI's information architecture should optimize for that moment, not for the pre-trip creation flow, even though creation is where the user spends more total screen time. That means the day view (stop list + map, synced) is the app's center of gravity, not the trips list — a returning user with an active trip should land inside "today," not at a folder of trips.

The core loop is: create or open a trip → look at today's day (list + map together) → act on a stop (check off, view time window, tap to see it on the map) → occasionally reorder stops as plans change → log an expense when money changes hands → check settle-up before the trip ends → repeat tomorrow. Packing and calendar export are lower-frequency loop-adjacent actions (done once near trip start), not part of the daily loop — I'd keep them one level down in the navigation, not co-equal tabs with the day view, or the IA implies they're used as often as the itinerary, which they're not.

Hard scope boundaries I want locked now, because they're exactly the things a less disciplined build would quietly let creep back in: no multi-device sync of any kind, not even "just for this session" via AirDrop or share sheets that could be mistaken for live sync; no notion of trip "sharing" that implies another person's phone sees updates — if a later phase proposes a QR-code trip export or similar, that's a new feature requiring its own decision, not an assumed extension of "expense splitting." No real-time data of any kind — flight status, live traffic, weather — even as a stretch goal; those are gaps, not partially-implemented placeholders. No login screen, no "sign in with Apple" even for device-only convenience — the app opens straight to content. And critically: the demo trip is a toggle in Settings, not a starter template silently seeded into a new user's first real trip — the empty state for a brand-new user with zero real trips must be a genuine empty state (an inviting "create your first trip" affordance), never the demo trip disguised as onboarding content.

The biggest risk to my own framing: by putting the day view at the center and treating trips-list as secondary, I'm making an information-architecture bet that could feel wrong to a user who has three upcoming trips and wants to compare or switch between them easily — if trip-switching becomes buried, that's a real usability cost. The mitigation is cheap though: a trip-switcher affordance always reachable from the day view (not a deep navigation-stack pop), so "today" stays the landing state without trapping the user there.

The detail I most want carried forward untouched into later phases: success here isn't "eight features present," it's specifically measurable as (1) a stop dragged across days twenty times in a row never duplicates or vanishes — this needs to be a repeatable test, not a one-time demo click, (2) a settle-up screen with five travelers and uneven percentage splits produces the mathematically minimal transaction count and the shown amounts sum to the exact original expense total to the cent, (3) every permission-gated surface (Live Activity request denied, Calendar access denied, MapKit with no network) has been made to actually fail and been watched failing gracefully, not just coded defensively, and (4) a new user's very first launch — no demo toggle flipped — shows real, honest empty states everywhere, with zero fabricated content on screen.
