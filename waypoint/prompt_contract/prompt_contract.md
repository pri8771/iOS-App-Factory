Now my read on this, wearing the QA/skeptic hat.

The biggest thing I want locked down before anyone starts building is that this prompt already names its own hardest failure modes, and later phases will be tempted to declare success on the easy 80% and hand-wave the rest. My job is to make sure "done" can't be claimed without evidence on exactly the parts that are easy to fake. Three areas deserve genuinely adversarial test cases, not just implementation:

Debt simplification is the one I trust least by default. "Minimum set of payments" is a real graph-reduction problem (greedy max-debtor/max-creditor settlement), and it's very easy to ship something that merely computes correct net balances but pays everyone individually instead of minimizing transactions — that would look right in a two-person test and be wrong the moment there are four or five travelers. The rounding requirement is the sharper trap: splitting $100 three ways in Decimal gives 33.33/33.33/33.34, and whoever eats the extra cent needs a deterministic, stated rule, not whichever traveler happens to be last in an array. I want a decision rule now: remainder cents go to a specific, documented position (e.g., first payer alphabetically, or the person who paid), and the sum of all splits for any expense must equal the original amount exactly, checked in code, not by eyeballing. Also: what happens when percentages entered by the user don't sum to 100, or an expense is split across a subset of travelers where the payer isn't included in the split? Those are testable edge cases and none of them can be quietly skipped.

Drag-and-drop reorder across days is the second trust-nothing area. "No duplicate/lost stops" sounds like a UI nicety but it's actually a data-model correctness question — moving a stop from Day 2 to Day 4 has to be one atomic operation on the SwiftData graph, not a delete-then-insert that can leave orphans if the app is backgrounded mid-drag. I'd also flag: when a stop moves to a different day, does its time window travel with it (probably now nonsensical if the trip's days have different structure) or get cleared? The prompt doesn't say, so I want that named as an assumption in the contract rather than decided silently later — my default vote is the time window is preserved as entered but the UI must visually flag it if it now falls outside typical hours, since silently clearing user data is its own bug.

The third area is honest degradation, and this is where I'm most skeptical of what a build phase will claim. Live Activities cannot be fully verified in the Simulator the way they render on-device with the actual Dynamic Island, and "today falls within the trip's date range" needs a single injected notion of "now" so it's actually testable without waiting for real calendar days to pass — I want a debug/demo-data hook for that, but it must never leak into what looks like real user data (that directly collides with the global rule against showing sample data as if it's real, so the demo trip needs a visible, unmistakable "Demo" marker, not just realistic content). ## Final Output

- **Cross-day/within-day reorder must be one atomic SwiftData operation** — no delete-then-insert that can orphan or duplicate a stop if the app backgrounds mid-drag.

- **CloudKit/iCloud sync is off by default and undocumented sync is forbidden** — SwiftData scaffolding must not silently enable it, since iCloud trip sync is an explicit non-goal.
- **Live Activity updates are local/scheduled only** — no push-token or server-driven update path, since that would require the backend this app explicitly forbids.

- **iPad split view must be verified as a genuine two-column interaction** (not a collapsed single-column NavigationSplitView) across at least two device sizes and both orientations — this becomes a build-verification checklist item, not just a code review of the view hierarchy.
- **Production-readiness requires observed degradation, not just guard clauses**: every permission-gated/capability-gated path (Live Activity, Calendar, denied network) must be shown to fail gracefully by actually triggering the denied/unavailable state, not inferred from reading the code.

Waypoint's contract is Codex's structure (hard requirements, non-goals, production-readiness definition, 32 numbered testable requirements) plus these resolved assumptions from Claude's review, now binding for every later phase:

- **Settlement must be true debt-simplification** (greedy max-debtor/max-creditor minimum-transaction reduction), not just per-person net payment pairs — a naive "everyone pays their own balance" implementation is a spec violation even if the balances are correct.
- **Remainder-cent rule, decided now**: when a split doesn't divide evenly, the leftover cent(s) go to the expense's payer, applied deterministically in code, and the sum of all split shares must equal the original Decimal amount exactly — checked programmatically, not eyeballed.
- **Cross-day stop moves preserve the stop's time window as entered**; the UI must visually flag it if the time now falls outside that day's normal range, rather than silently clearing user data.
- **Cross-day/within-day reorder must be one atomic SwiftData operation** — no delete-then-insert that can orphan or duplicate a stop if the app backgrounds mid-drag.
- **Demo trip data must be unmistakably marked "Demo"** in the UI — realistic content is fine, but it can never be visually indistinguishable from the user's real trips.
- **CloudKit/iCloud sync is off by default and undocumented sync is forbidden** — SwiftData scaffolding must not silently enable it, since iCloud trip sync is an explicit non-goal.
- **Live Activity updates are local/scheduled only** — no push-token or server-driven update path, since that would require the backend this app explicitly forbids.
- **"Now" for active-trip/Live Activity logic must run through a single, testable current-date reference** so activation windows can be verified in the simulator without waiting on real calendar days, without that hook ever leaking into what looks like real user data.
- **Calendar export dedup**: store the EventKit event identifier per stop at export time; re-export looks up and updates in place; the flow must also handle an event deleted externally or Calendar access revoked between exports, without falsely claiming success.
- **iPad split view must be verified as a genuine two-column interaction** (not a collapsed single-column NavigationSplitView) across at least two device sizes and both orientations — this becomes a build-verification checklist item, not just a code review of the view hierarchy.
- **Production-readiness requires observed degradation, not just guard clauses**: every permission-gated/capability-gated path (Live Activity, Calendar, denied network) must be shown to fail gracefully by actually triggering the denied/unavailable state, not inferred from reading the code.
