## Original Prompt

```
Build a polished, fully offline iOS trip-planning app called "Waypoint".
Native Apple stack only: SwiftUI + SwiftData for persistence, MapKit for
all mapping, ActivityKit for Live Activities, EventKit for calendar
export. No backend, no accounts, no third-party SDKs, no network calls
except on-device MapKit/local geocoding (which works offline-cached but
may need network for tile fetch — if a feature would require live
network for correctness, don't fake it; record it as a gap). Follow the
ios-app-factory-rules.

Core features (complete over broad — ship fewer things fully working):

1. Trips & itinerary: create trips with a date range; each trip has
   multiple days; each day has an ordered list of stops (place name,
   address, optional MapKit-resolved coordinate, time window, notes,
   category icon). Reorder stops via drag-and-drop within a day AND
   across days. Get date math right across the trip's date range,
   including a trip that starts and ends on the same day and a
   single-day trip.

2. Map view: a MapKit view per day showing all of that day's stops as
   annotations connected by a route line (MKDirections walking/driving,
   gracefully degrading to a straight-line polyline with a visible
   "approximate" indicator if MKDirections has no network). Tapping a
   stop centers the map and highlights it; tapping a map pin selects
   the corresponding itinerary row (two-way binding).

3. Expense splitting: a per-trip list of travelers (name, no accounts).
   Log expenses (amount, payer, split method: equal / exact amounts /
   percentage) against any subset of travelers. A settle-up screen
   computing the minimum set of payments to zero every balance (the
   classic debt-simplification graph problem — get this genuinely
   correct, including rounding remainders so amounts always sum
   exactly). Use Decimal, never Double, for money.

4. Packing lists: per-trip checklist, templates the user can save and
   reapply to future trips, a "packed %" indicator.

5. Live Activity: while a trip is "active" (today falls within its date
   range), a Live Activity / Dynamic Island showing the current or next
   stop and time until it, updating as stops are checked off. Must
   degrade gracefully (no crash, no Live Activity) on devices/OS
   versions without support, and when the user denies the permission.

6. Calendar export: export a day's stops as EventKit calendar events
   (with the user's explicit permission), one event per stop honoring
   its time window; must not create duplicate events if exported twice
   for the same day — detect and either skip or update existing ones.

7. Home-screen widget (WidgetKit, separate target): shows the active
   trip's next stop, or "no active trip" honestly if none.

8. iPad: itinerary list and map must work as a genuine two-column split
   view on iPad, not just a stretched phone layout.

Priorities: the debt-simplification math, the drag-reorder data
integrity (no duplicate/lost stops across days), and honest degradation
of every system-permission-gated feature (Live Activities, Calendar,
location) — never fake success when a permission is denied or a
capability is unavailable in the Simulator. Explicitly call out in a
Gaps section anything requiring infrastructure this project can't
provide (live traffic data, real-time flight tracking, iCloud trip
sync). Seed a "demo trip" toggle in Settings with realistic multi-day
sample data so no screen is empty on first review. Provide a clear way
to run it in the iOS Simulator via Xcode.
```

**Claude (QA & Risk · Closer) — Round 1**

Coming at this from the angle of what will actually break in review, not what looks fine in a design doc.

Start with the data model, because this is where the drag-reorder guarantee either holds or quietly doesn't. Day must be a real `@Model` entity owned by Trip, not a computed grouping derived from stop dates — you need somewhere to anchor a day that has zero stops (it's a required empty state) and somewhere for the ribbon/page-flip to point at during a drag. Each Stop needs an explicit `sortIndex: Int` attribute maintained by app code; do not rely on SwiftData relationship array order to represent sequence, because to-many relationship ordering is not a durable contract you should be betting stop-order correctness on. The atomic move operation itself should be one function — `moveStop(_:to:at:)` — that in a single pass reassigns the stop's `day` relationship, reindexes both the source day's and destination day's remaining stops, and saves once; wrap it so a thrown save calls `context.rollback()` rather than leaving a half-written state, and have both the drag path and the "Move to..." menu path call this exact function, never two implementations. I'd also push back on giving every screen its own ViewModel class — that's over-engineering for this scope. Use `@Query` directly in views for reads, and centralize all mutating logic in a small number of plain structs/services (a StopReorderService, SettlementEngine, CalendarExportService, DemoSeeder) that take a `ModelContext` as a parameter — that's your real unit-test seam, and it keeps views declarative.

On settlement math specifically: don't do the split arithmetic in `Decimal` division directly and hope the remainder rule falls out cleanly. Convert each expense amount to integer minor units (cents, `Int`) at the boundary, do all the equal/percentage/exact-split division and remainder-to-payer assignment in integer arithmetic where "sum of parts equals whole" is trivially exact and trivially assertable, and only convert back to `Decimal` for persistence and display. This makes the sum-identity assertion a one-line integer equality check instead of a Decimal-rounding argument, and it's what makes the 5-traveler adversarial test actually reliable rather than occasionally off by a cent due to rounding-mode ambiguity. This needs to be locked now, not left as an implementation detail, because it changes what the unit tests assert against.

Permissions: I want to make a call on location that I think the earlier phases left implicit and shouldn't. This app has no legitimate need for `CoreLocation` "when in use" access — MKDirections routes between two stop coordinates, not from the user's current position, and live GPS tracking is already a named non-goal. Don't request location permission at all in v1. If someone wants a "center map on me" nicety later, that's a new, explicit, separately-justified permission ask, not something that sneaks in because MapKit examples default to showing a blue dot. On Calendar: use the iOS 17 full-access API (`requestFullAccessToEvents`), not write-only, because the dedup flow requires looking an event back up by its stored identifier to update or detect external deletion, and write-only access is the wrong tool for that; declare `NSCalendarsFullAccessUsageDescription` and treat "denied," "restricted," and "write-only granted but full requested and refused" as three distinct handled states, not folded into one generic failure. On ActivityKit: `NSSupportsLiveActivities = YES` in Info.plist, `pushType: nil` on every `Activity.request` call (this is the actual enforcement point for the no-server-push decision, and it should be code-reviewed as a literal grep target during build verification), and check `ActivityAuthorizationInfo().areActivitiesEnabled` before ever attempting to start one — never let a denied/unsupported state reach the request call and surface as a crash or silent no-op with no user-visible explanation.

One correction I want on record before tech_specs locks target structure: the Live Activity is not a fourth Xcode target — ActivityKit's Dynamic Island/Live Activity UI is declared inside the same WidgetKit extension target as the home-screen widget, via an `ActivityConfiguration` alongside the `Widget`. So there are two targets total (main app, widget extension), and the shared-package requirement from design_handoff applies to both, but builders shouldn't go create a phantom separate Live Activity target — that would be wasted setup work and a possible source of the exact cross-target drift the design phase was trying to prevent.

The countdown-without-a-server problem needs a concrete answer, not "it updates somehow": use `Text(timerInterval:)` / a date-driven view inside the Live Activity's SwiftUI content so the system renders the "time until next stop" countdown continuously without the app process being woken up, and only call `Activity.update()` explicitly when the actual next-stop changes (a stop gets checked off, or the app becomes active and detects time has crossed into a new stop's window). If that distinction isn't made explicit now, someone will build a timer inside the app trying to push updates every minute, discover it doesn't work when backgrounded, and either fake it or silently drop the feature.

On the debug "current date" hook: it's not enough that it's `#if DEBUG`-only in the main app. The widget extension runs in a separate process and needs to agree with the main app on "today," or you'll get a widget showing a different active-trip state than the app during debug/demo verification. If this hook is going to be threaded through both targets for testability, it has to read from an App Group `UserDefaults` suite (still `#if DEBUG`-gated, still physically absent from release), not an in-process variable — otherwise the two processes silently disagree and someone "verifies" one and ships a lie in the other. Same App Group is needed for the widget's SwiftData store access via `ModelConfiguration(groupContainer:)`, so this is one App Group capability serving two purposes, set up once at project scaffolding time.

On MapKit degradation testing, I want to close a hole: the demo trip's "unresolvable route" stop cannot depend on an actual live MKDirections network failure at review time, because Simulator networking routes through the host Mac and may simply succeed depending on the reviewer's connection — which would silently un-verify the app's core differentiator. Seed that demo stop with coordinates that are structurally unroutable (e.g., across open ocean with no walking/driving path) so `MKError` fires deterministically regardless of network state, every single review, not just on a bad-wifi day.

StoreKit: even though it's could-have for this build, the architecture has to not preclude it, and I want to close the one ambiguity that's been left open across two prior phases — what "one active trip" means operationally. I'm deciding it now: the gate is the count of trips that currently exist (not cumulative-ever-created), enforced at trip-creation time by disabling "New Trip" and showing an upsell once a free user already has one trip; deleting a trip frees the slot. No `isLocked` flag on Trip, no partially-created-then-frozen trip state — the enforcement point is entirely at creation, which keeps the SwiftData model free of monetization concerns. Use a bundled `.storekit` configuration file in the scheme from day one so purchase/restore/cancel/lapse can actually be exercised in Simulator without a sandbox account — that's the only way build-verification can honestly claim the lapse-preserves-data path was observed rather than assumed.

Settlement math and the reorder service get plain XCTest unit tests against an in-memory `ModelContainer` with zero UI involvement.
