## Original Prompt

```
Build a polished, fully offline iOS trip-planning app called "Waypoint".
Native Apple stack only: SwiftUI + SwiftData for persistence, MapKit for
all mapping, ActivityKit for Live Activities, EventKit for calendar
export. No backend, no accounts, no third-party SDKs, no network calls
except on-device MapKit/local geocoding (which works offline-cached but
may need network for tile fetch — if a feature would require live
network for correctness, don't fake it; record it as a gap). Follow the
ios-app-factory-rules.

Core features (complete over broad — ship fewer things fully working):

1. Trips & itinerary: create trips with a date range; each trip has
   multiple days; each day has an ordered list of stops (place name,
   address, optional MapKit-resolved coordinate, time window, notes,
   category icon). Reorder stops via drag-and-drop within a day AND
   across days. Get date math right across the trip's date range,
   including a trip that starts and ends on the same day and a
   single-day trip.

2. Map view: a MapKit view per day showing all of that day's stops as
   annotations connected by a route line (MKDirections walking/driving,
   gracefully degrading to a straight-line polyline with a visible
   "approximate" indicator if MKDirections has no network). Tapping a
   stop centers the map and highlights it; tapping a map pin selects
   the corresponding itinerary row (two-way binding).

3. Expense splitting: a per-trip list of travelers (name, no accounts).
   Log expenses (amount, payer, split method: equal / exact amounts /
   percentage) against any subset of travelers. A settle-up screen
   computing the minimum set of payments to zero every balance (the
   classic debt-simplification graph problem — get this genuinely
   correct, including rounding remainders so amounts always sum
   exactly). Use Decimal, never Double, for money.

4. Packing lists: per-trip checklist, templates the user can save and
   reapply to future trips, a "packed %" indicator.

5. Live Activity: while a trip is "active" (today falls within its date
   range), a Live Activity / Dynamic Island showing the current or next
   stop and time until it, updating as stops are checked off. Must
   degrade gracefully (no crash, no Live Activity) on devices/OS
   versions without support, and when the user denies the permission.

6. Calendar export: export a day's stops as EventKit calendar events
   (with the user's explicit permission), one event per stop honoring
   its time window; must not create duplicate events if exported twice
   for the same day — detect and either skip or update existing ones.

7. Home-screen widget (WidgetKit, separate target): shows the active
   trip's next stop, or "no active trip" honestly if none.

8. iPad: itinerary list and map must work as a genuine two-column split
   view on iPad, not just a stretched phone layout.

Priorities: the debt-simplification math, the drag-reorder data
integrity (no duplicate/lost stops across days), and honest degradation
of every system-permission-gated feature (Live Activities, Calendar,
location) — never fake success when a permission is denied or a
capability is unavailable in the Simulator. Explicitly call out in a
Gaps section anything requiring infrastructure this project can't
provide (live traffic data, real-time flight tracking, iCloud trip
sync). Seed a "demo trip" toggle in Settings with realistic multi-day
sample data so no screen is empty on first review. Provide a clear way
to run it in the iOS Simulator via Xcode.
```

## Final Output

### Must-have features (with user story + acceptance criteria)

1. **Trip creation & date-range math** — *As a trip owner, I create a trip with a start/end date so the app builds the right number of days.* Acceptance: a trip with any date range (including a single-day trip and a trip that starts/ends the same day) produces the correct day count and day objects; no off-by-one at range boundaries.

2. **Day view with ordered, timed stops** — *As a trip owner, I see each day's stops in order with their time windows and notes.* Acceptance: stops render in explicit order with name, address, time window, notes, category icon; ordering persists across app relaunch.

3. **Cross-day/within-day drag-reorder (atomic) + accessible "Move to..." path** — *As a trip owner, I drag a stop to reorder it or move it to another day; as a VoiceOver user, I use a Move-to action instead.* Acceptance: both entry points call the identical atomic SwiftData operation; 10+ rapid cross-day drags of one stop leave exactly one instance of that stop in exactly one day at every intermediate state; no orphan/duplicate is ever observable.

4. **Per-day MapKit view with routing + honest fallback** — *As a trip owner, I see my day's stops connected by a route on a map, and I can trust the line even when there's no signal.* Acceptance: MKDirections walking/driving route renders when resolvable; when it isn't, a straight-line polyline renders with a visible "approximate" indicator — never a silent gap or crash; tapping a stop centers/highlights the map, tapping a pin selects the matching list row (two-way).

5. **Travelers + expense logging (equal/exact/percentage)** — *As a trip owner, I add travelers and log an expense split among any subset of them.* Acceptance: all three split methods work; percentage entries not summing to 100% are rejected at entry with an inline error stating the actual sum, never silently rescaled; all money uses Decimal.

6. **Settle-up (genuine debt-simplification)** — *As a trip owner, I open settle-up and see the fewest possible payments to zero every balance.* Acceptance: 5-traveler scenario with mixed split methods (including a non-100%-summing percentage rejected at entry) produces the mathematically minimal transaction count; shown amounts sum exactly to the original totals; remainder cents deterministically go to the payer; an in-code sum-identity assertion enforces this.

7. **Trip date-range shrink guard** — *As a trip owner, if I shrink my trip's dates, I'm told exactly which stops would be orphaned instead of losing them silently.* Acceptance: shrinking a range that would remove days with stops blocks the edit and lists the affected days/stops; extending the range is unrestricted.

8. **Demo trip toggle (singleton, honestly marked)** — *As a reviewer/first-time user, I can turn on realistic sample data without it being confused for my real trips.* Acceptance: toggle on creates the demo trip only if absent; toggle off deletes exactly that trip (keyed by stable identifier, never by name/date matching) and touches nothing else; the demo trip and its data carry a visible "Demo" marker everywhere it appears; it includes at least one stop with a deliberately unresolvable route so the approximate fallback is actually observed.

9. **Honest degradation as its own acceptance bar** — *As a user who denies a permission or runs on an unsupported device, I never see a fake success state.* Acceptance: Live Activity, Calendar access, MapKit routing without network, and location permission (if used) each have an observed — not just coded — denied/unavailable state: no crash, no fabricated success, a clear in-app explanation.

10. **Packing checklist + packed % (checklist itself, not templates)** — *As a trip owner, I check off packed items and see my packed percentage.* Acceptance: percentage recalculates correctly as items are checked/unchecked/added/removed, including 0-item and 0%-checked edge cases.

11. **Calendar export with idempotent dedup** — *As a trip owner, I export a day's stops to Calendar without permission and get one event per stop; exporting twice doesn't duplicate.* Acceptance: each stop's EventKit event identifier is stored at export time; re-export looks it up and updates in place; an externally-deleted event or revoked Calendar permission is handled as an explicit, non-crashing, non-lying state.

12. **iPad two-pane split view** — *As an iPad user, I see itinerary and map as genuinely independent panes, not a stretched phone layout.* Acceptance: verified as independent-pane interaction (not just NavigationSplitView usage) across at least two iPad sizes and both orientations.

### Should-have

- Live Activity / Dynamic Island (current/next stop + time-until, updates as stops are checked off) — verification is bounded by simulator/no-hardware limits; degrades to no-crash/no-Live-Activity on unsupported devices or denied permission.
- Home-screen widget (WidgetKit) showing active trip's next stop or an honest "no active trip" — same verification ceiling as Live Activity.
- Packing templates (save/reapply across trips).

### Could-have

- StoreKit/Pro-tier paywall (annual subscription + lifetime purchase, single active-trip-count gate).
- Trip Snapshot export (PDF/text/.ics, itinerary-only by default).
- Settlement audit-log / category-spend-breakdown reporting.

### Won't-build (named in Gaps, not silently absent)

- CloudKit/iCloud trip sync (any form).
- Any AirDrop/share-sheet mechanism resembling live sync.
- Real-time traffic data, live flight tracking, real-time weather.
- Cross-device collaborative editing.
- Destination-timezone-aware itineraries (stop times are device-local-timezone only).

### Must-have features (with user story + acceptance criteria)

1. **Trip creation & date-range math** — *As a trip owner, I create a trip with a start/end date so the app builds the right number of days.* Acceptance: a trip with any date range (including a single-day trip and a trip that starts/ends the same day) produces the correct day count and day objects; no off-by-one at range boundaries.

2. **Day view with ordered, timed stops** — *As a trip owner, I see each day's stops in order with their time windows and notes.* Acceptance: stops render in explicit order with name, address, time window, notes, category icon; ordering persists across app relaunch.

3. **Cross-day/within-day drag-reorder (atomic) + accessible "Move to..." path** — *As a trip owner, I drag a stop to reorder it or move it to another day; as a VoiceOver user, I use a Move-to action instead.* Acceptance: both entry points call the identical atomic SwiftData operation; 10+ rapid cross-day drags of one stop leave exactly one instance of that stop in exactly one day at every intermediate state; no orphan/duplicate is ever observable.

4. **Per-day MapKit view with routing + honest fallback** — *As a trip owner, I see my day's stops connected by a route on a map, and I can trust the line even when there's no signal.* Acceptance: MKDirections walking/driving route renders when resolvable; when it isn't, a straight-line polyline renders with a visible "approximate" indicator — never a silent gap or crash; tapping a stop centers/highlights the map, tapping a pin selects the matching list row (two-way).

5. **Travelers + expense logging (equal/exact/percentage)** — *As a trip owner, I add travelers and log an expense split among any subset of them.* Acceptance: all three split methods work; percentage entries not summing to 100% are rejected at entry with an inline error stating the actual sum, never silently rescaled; all money uses Decimal.

6. **Settle-up (genuine debt-simplification)** — *As a trip owner, I open settle-up and see the fewest possible payments to zero every balance.* Acceptance: 5-traveler scenario with mixed split methods (including a non-100%-summing percentage rejected at entry) produces the mathematically minimal transaction count; shown amounts sum exactly to the original totals; remainder cents deterministically go to the payer; an in-code sum-identity assertion enforces this.

7. **Trip date-range shrink guard** — *As a trip owner, if I shrink my trip's dates, I'm told exactly which stops would be orphaned instead of losing them silently.* Acceptance: shrinking a range that would remove days with stops blocks the edit and lists the affected days/stops; extending the range is unrestricted.

8. **Demo trip toggle (singleton, honestly marked)** — *As a reviewer/first-time user, I can turn on realistic sample data without it being confused for my real trips.* Acceptance: toggle on creates the demo trip only if absent; toggle off deletes exactly that trip (keyed by stable identifier, never by name/date matching) and touches nothing else; the demo trip and its data carry a visible "Demo" marker everywhere it appears; it includes at least one stop with a deliberately unresolvable route so the approximate fallback is actually observed.

9. **Honest degradation as its own acceptance bar** — *As a user who denies a permission or runs on an unsupported device, I never see a fake success state.* Acceptance: Live Activity, Calendar access, MapKit routing without network, and location permission (if used) each have an observed — not just coded — denied/unavailable state: no crash, no fabricated success, a clear in-app explanation.

10. **Packing checklist + packed % (checklist itself, not templates)** — *As a trip owner, I check off packed items and see my packed percentage.* Acceptance: percentage recalculates correctly as items are checked/unchecked/added/removed, including 0-item and 0%-checked edge cases.

11. **Calendar export with idempotent dedup** — *As a trip owner, I export a day's stops to Calendar without permission and get one event per stop; exporting twice doesn't duplicate.* Acceptance: each stop's EventKit event identifier is stored at export time; re-export looks it up and updates in place; an externally-deleted event or revoked Calendar permission is handled as an explicit, non-crashing, non-lying state.

12. **iPad two-pane split view** — *As an iPad user, I see itinerary and map as genuinely independent panes, not a stretched phone layout.* Acceptance: verified as independent-pane interaction (not just NavigationSplitView usage) across at least two iPad sizes and both orientations.

### Should-have

- Live Activity / Dynamic Island (current/next stop + time-until, updates as stops are checked off) — verification is bounded by simulator/no-hardware limits; degrades to no-crash/no-Live-Activity on unsupported devices or denied permission.
- Home-screen widget (WidgetKit) showing active trip's next stop or an honest "no active trip" — same verification ceiling as Live Activity.
- Packing templates (save/reapply across trips).

### Could-have

- StoreKit/Pro-tier paywall (annual subscription + lifetime purchase, single active-trip-count gate).
- Trip Snapshot export (PDF/text/.ics, itinerary-only by default).
- Settlement audit-log / category-spend-breakdown reporting.

### Won't-build (named in Gaps, not silently absent)

- CloudKit/iCloud trip sync (any form).
- Any AirDrop/share-sheet mechanism resembling live sync.
- Real-time traffic data, live flight tracking, real-time weather.
- Cross-device collaborative editing.
- Destination-timezone-aware itineraries (stop times are device-local-timezone only).
