## Original Prompt

```
Build a polished, fully offline iOS trip-planning app called "Waypoint".
Native Apple stack only: SwiftUI + SwiftData for persistence, MapKit for
all mapping, ActivityKit for Live Activities, EventKit for calendar
export. No backend, no accounts, no third-party SDKs, no network calls
except on-device MapKit/local geocoding (which works offline-cached but
may need network for tile fetch — if a feature would require live
network for correctness, don't fake it; record it as a gap). Follow the
ios-app-factory-rules.

Core features (complete over broad — ship fewer things fully working):

1. Trips & itinerary: create trips with a date range; each trip has
   multiple days; each day has an ordered list of stops (place name,
   address, optional MapKit-resolved coordinate, time window, notes,
   category icon). Reorder stops via drag-and-drop within a day AND
   across days. Get date math right across the trip's date range,
   including a trip that starts and ends on the same day and a
   single-day trip.

2. Map view: a MapKit view per day showing all of that day's stops as
   annotations connected by a route line (MKDirections walking/driving,
   gracefully degrading to a straight-line polyline with a visible
   "approximate" indicator if MKDirections has no network). Tapping a
   stop centers the map and highlights it; tapping a map pin selects
   the corresponding itinerary row (two-way binding).

3. Expense splitting: a per-trip list of travelers (name, no accounts).
   Log expenses (amount, payer, split method: equal / exact amounts /
   percentage) against any subset of travelers. A settle-up screen
   computing the minimum set of payments to zero every balance (the
   classic debt-simplification graph problem — get this genuinely
   correct, including rounding remainders so amounts always sum
   exactly). Use Decimal, never Double, for money.

4. Packing lists: per-trip checklist, templates the user can save and
   reapply to future trips, a "packed %" indicator.

5. Live Activity: while a trip is "active" (today falls within its date
   range), a Live Activity / Dynamic Island showing the current or next
   stop and time until it, updating as stops are checked off. Must
   degrade gracefully (no crash, no Live Activity) on devices/OS
   versions without support, and when the user denies the permission.

6. Calendar export: export a day's stops as EventKit calendar events
   (with the user's explicit permission), one event per stop honoring
   its time window; must not create duplicate events if exported twice
   for the same day — detect and either skip or update existing ones.

7. Home-screen widget (WidgetKit, separate target): shows the active
   trip's next stop, or "no active trip" honestly if none.

8. iPad: itinerary list and map must work as a genuine two-column split
   view on iPad, not just a stretched phone layout.

Priorities: the debt-simplification math, the drag-reorder data
integrity (no duplicate/lost stops across days), and honest degradation
of every system-permission-gated feature (Live Activities, Calendar,
location) — never fake success when a permission is denied or a
capability is unavailable in the Simulator. Explicitly call out in a
Gaps section anything requiring infrastructure this project can't
provide (live traffic data, real-time flight tracking, iCloud trip
sync). Seed a "demo trip" toggle in Settings with realistic multi-day
sample data so no screen is empty on first review. Provide a clear way
to run it in the iOS Simulator via Xcode.
```

### Round 1


**Codex (Design Lead · Systems Thinker) — Round 1**

Waypoint is for a small group trip owner—the person actually carrying the phone for family, friends, or a couple—who needs one local decision surface for “where are we now, what comes next, and who owes what,” especially when signal is weak and plans keep changing.  
The app’s paid value is practical reliability: it removes the fragile dependency chain of Notes + spreadsheets + half-worked maps + ad hoc chat math by making itinerary, map status, packing, and settlement come from one trusted local trip model with no fake sync, no cloud required, and clear fallback behavior when system permissions or network-assisted features are unavailable.  

Paid users should subscribe because they receive capabilities that materially reduce trip risk, not cosmetics: unlimited trips and reusable trip templates (not just one-off demos), advanced template-based packing sets by trip archetype, traveler-limit extensions for large groups, settlement audit logs with category-level spend breakdowns and exact rounding traceability, and a “trip resilience bundle” of stronger offline confidence (e.g., multiple route modes, saved route quality flags, and widget/activity diagnostics that call out when fallbacks are being used). This can be a monthly subscription with annual discount, while keeping a genuinely usable free tier that still handles core planning for one trip.  

The core loop is intentionally simple: open day view for the active trip, review the ordered stop list and map for today, check off progress, tap a stop to center it and inspect context, log expense events when they happen, and finish with settle-up that produces the minimal payment set; packing and calendar export sit one level down as the maintenance loops that run before departure and after travel days.  

The competitive wedge is not “more features,” it is correctness under real use: atomic cross-day stop operations, deterministic monetary calculations with cent-accurate balances, and honest offline-first behavior with visible route fallbacks instead of pretending everything succeeded; that reliability is what differentiates it from cloud-first competitors where no signal equals no app.  

Growth should come from niche pull, not generic virality: the app grows because one coordinator in a group trusts it enough to make it the default trip source of truth, then every repeated trip increases confidence and word-of-mouth within that travel circle; a tiny “handoff” prompt on closeout (“Export today’s plan to Calendar”) plus a short review loop encourages that coordinator to re-use and recommend the app without ever implying real-time multi-device sync.  

Local-first behavior is the default contract: all data lives in local SwiftData, no background services, no account requirement, no hidden sync, explicit permission degradation for location/calendar/live features, and clear user-facing status when capabilities are unavailable. The cloud-ready path is an explicit opt-in v2 direction: optional encrypted iCloud-backed migration/sync through a new storage layer with explicit conflict rules and explicit per-user authorization, but never as a prerequisite for day-one usefulness.  

The main risk is that monetization can quietly weaken trust if premium features ever look like hidden “pay-to-work” gates on core reliability; this brief must preserve that free users still get a trustworthy baseline and paid users get extra operational power, plus an explicit “single-device, no auto-sync” honesty line wherever expense collaboration might be implied.

## Final Output

**Target user & use case:** The trip owner — the one person in a couple/family/friend group who plans and carries the phone during a multi-day trip — specifically one who takes more than one such trip a year. They pay not for dashboards but to keep using one trusted local tool across repeat trips instead of re-improvising with Notes/spreadsheets/Splitwise each time.

**Paid value / subscription gate (single lever, not a feature menu):**
- **Free, forever:** one active trip at a time, with everything on that trip fully correct — all stops, all days, unlimited travelers, real Decimal-based minimum-transaction settlement math, honest MapKit routing with visible "approximate" fallback labeling, packing checklist, and the full iPad two-pane split view.
- **Pro (annual subscription or lifetime non-consumable, same unlock, same StoreKit product group):** unlimited concurrent trips, saved/reusable packing templates, EventKit calendar export, the Live Activity, the home-screen widget, and settlement audit-log/category-level spend-breakdown reporting (a read layer on top of the already-free, already-correct settlement math).
- **Never paywalled, at any tier, no exceptions:** settlement correctness itself, traveler count, the iPad split view, and the honest map-degradation fallback with its visible indicator — these are the app's trust story, not upsell surface.

**Downgrade/lapse rule:** if a subscription lapses or restore fails, existing trip data (stops, order, settlement history) is never deleted, hidden, or corrupted — only new-trip creation past the free cap and the Pro-only surfaces (templates, export, Live Activity, widget, audit reporting) lock.

**Core loop:** open app → land on today's day in the active trip (synced stop list + map) → check off / reorder stops → log expenses in-context → settle up → packing and calendar export as one-level-down, pre/post-trip maintenance actions. This is a trip command center, not a tab-per-feature app.

**Competitive wedge:** not feature breadth — provably correct behavior under adversity (deterministic settlement, atomic cross-day reorder, honest degradation when permissions/network/capabilities are unavailable) versus cloud-account-dependent competitors (TripIt, Wanderlog, Splitwise-style tools) that degrade badly offline.

**Growth mechanic:** a one-way, clearly labeled "Trip Snapshot" export (PDF/text/.ics via the share sheet) a coordinator hands off to trip-mates — explicitly a static snapshot, never implying live sync. Default export scope is itinerary-only (stop names, times, notes, map snapshot); expense/settlement data is excluded unless the owner explicitly opts in, to avoid an accidental privacy leak of who-owes-what to non-paying recipients.

**Local-first / cloud-ready plan:** all state lives in local SwiftData by default, CloudKit off by default, no account, no background upload, explicit visible status whenever MapKit/Live Activity/Calendar permissions are denied or unavailable. Cloud sync is a documented, explicit v2 opt-in only (schema kept sync-ready today via optional relationships/no unique constraints/default values), never a default or an assumed future.

## Final Output

**Target user & use case:** The trip owner — the one person in a couple/family/friend group who plans and carries the phone during a multi-day trip — specifically one who takes more than one such trip a year. They pay not for dashboards but to keep using one trusted local tool across repeat trips instead of re-improvising with Notes/spreadsheets/Splitwise each time.

**Paid value / subscription gate (single lever, not a feature menu):**
- **Free, forever:** one active trip at a time, with everything on that trip fully correct — all stops, all days, unlimited travelers, real Decimal-based minimum-transaction settlement math, honest MapKit routing with visible "approximate" fallback labeling, packing checklist, and the full iPad two-pane split view.
- **Pro (annual subscription or lifetime non-consumable, same unlock, same StoreKit product group):** unlimited concurrent trips, saved/reusable packing templates, EventKit calendar export, the Live Activity, the home-screen widget, and settlement audit-log/category-level spend-breakdown reporting (a read layer on top of the already-free, already-correct settlement math).
- **Never paywalled, at any tier, no exceptions:** settlement correctness itself, traveler count, the iPad split view, and the honest map-degradation fallback with its visible indicator — these are the app's trust story, not upsell surface.

**Downgrade/lapse rule:** if a subscription lapses or restore fails, existing trip data (stops, order, settlement history) is never deleted, hidden, or corrupted — only new-trip creation past the free cap and the Pro-only surfaces (templates, export, Live Activity, widget, audit reporting) lock.

**Core loop:** open app → land on today's day in the active trip (synced stop list + map) → check off / reorder stops → log expenses in-context → settle up → packing and calendar export as one-level-down, pre/post-trip maintenance actions. This is a trip command center, not a tab-per-feature app.

**Competitive wedge:** not feature breadth — provably correct behavior under adversity (deterministic settlement, atomic cross-day reorder, honest degradation when permissions/network/capabilities are unavailable) versus cloud-account-dependent competitors (TripIt, Wanderlog, Splitwise-style tools) that degrade badly offline.

**Growth mechanic:** a one-way, clearly labeled "Trip Snapshot" export (PDF/text/.ics via the share sheet) a coordinator hands off to trip-mates — explicitly a static snapshot, never implying live sync. Default export scope is itinerary-only (stop names, times, notes, map snapshot); expense/settlement data is excluded unless the owner explicitly opts in, to avoid an accidental privacy leak of who-owes-what to non-paying recipients.

**Local-first / cloud-ready plan:** all state lives in local SwiftData by default, CloudKit off by default, no account, no background upload, explicit visible status whenever MapKit/Live Activity/Calendar permissions are denied or unavailable. Cloud sync is a documented, explicit v2 opt-in only (schema kept sync-ready today via optional relationships/no unique constraints/default values), never a default or an assumed future.
