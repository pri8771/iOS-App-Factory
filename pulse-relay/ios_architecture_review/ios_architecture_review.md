### Round 1


**Codex (Backend / Systems Engineer · Systems Thinker) — Round 1**

For this phase I would lock the iOS product architecture around a server-authoritative relay core with a very thin, deterministic SwiftUI client. The client should render from a local cache immediately, but every meaningful outcome state must come from a confirmed server write so we never show “covered”, “withdrawn”, “complete” or any terminal state without server proof.

I would pick a custom REST backend over third-party realtime frameworks because this use case needs strict state transitions, idempotent actions, and auditability. A good fit is Swift or Node as an API service backed by PostgreSQL, with one push-worker service per change and optional Redis lock cache only if needed. PostgreSQL is the critical piece because we need compare-and-swap-safe transitions (first-accept-wins, mutually exclusive release/withdraw state changes), stable pagination/order, and transactional write logs for receipts/evidence. I would keep the external contract simple and explicit: versioned `/api/v1` endpoints, strong DTOs, and deterministic responses. Core endpoints: auth bootstrap, `POST /pods`, `POST /pods/join`, `GET /pods/{podId}/state`, `POST /requests` with action IDs, `POST /requests/{id}/actions` for accept/release/complete/withdraw, and `GET /requests/{id}` for deep-link reconciliation, plus `/requests/{id}/receipt`. Every action endpoint must be idempotent and return either the updated request row or a conflict payload (“already covered”, “not open”, “stale”) and never silently succeed on duplicate retries.

On-device architecture should be two-layered: a pure domain/state layer (no network/UI dependencies) and a SwiftUI presentation layer. Use `Observation`/`ObservableObject` stores plus async repositories: one for session/auth, one for pod membership, one for request feed and outbox. Keep action execution in a command/reducer-like state machine that can express `queuedOffline`, `awaitingConfirmation`, `reconciling`, and the latched terminal states. This is where the two-phone proof lives, so state transitions should be testable as pure functions.

For local persistence, use SwiftData for cached board/request/receipt snapshots, queued outbox actions, and sync cursors, then Keychain for auth credentials/session refresh secrets. `URLSession` with `async/await` should be the network layer. Don’t add a network abstraction library: it’s unnecessary overhead and conflicts with the no-bloat direction. SwiftData is acceptable for app persistence under the target policy, and it gives us robust “cached continuity + freshness banner” behavior. Keep sensitive tokens in Keychain only, and avoid storing user-entered notes or member metadata beyond what is displayed; this product already avoids child identifiers and location.

Permissions should be intentionally minimal: Sign in with Apple (required), remote notifications (required), background remote notifications (recommended so push-triggered refetch can run when user taps or receives content-available wake), and optionally user-notification authorization at first feature touchpoint. There is no location, no photos, no contacts, no camera, no mic. For deep links, a custom URL scheme is simplest and avoids associated-domain work; if the team wants universal links later, add that later after baseline is stable. Privacy-by-design requirements should be explicit in API terms too: no child PII fields, no implied background checks, no trust badges unless real verification is performed, and placeholder member names only where needed.

Offline behavior must be first-class in architecture, not only in UI copy: maintain a durable action outbox in SwiftData with generated `client_action_id`, exponential retry with backoff, and idempotent replay against the server endpoint that enforces idempotency keys. On launch/foreground and after forced crash/quit, render stale cache first for continuity, then block high-confidence terminal display until freshness sync completes. A top-level board refresh banner is right here. If push is missing or delayed, explicit user-facing uncertainty copy should remain accurate rather than faking success.

Push architecture should be hard-coded into backend contract as wake-up-only: payload contains request/pod identifiers and event hints, never authoritative state. The client always refetches the request or pod slice before changing UI state. This avoids out-of-order push corruption and preserves CAS correctness.

For StoreKit/subscriptions: v1 should be explicitly non-monetized and include only placeholders for future fields. Do not add StoreKit 2 now; no entitlement checks, no paywall paths, no SKProduct calls. Keep the three future unlock ideas as schema placeholders if needed, but keep them inert and out of runtime behavior.

Dependency/license policy: keep iOS dependency surface to Apple frameworks and no prohibited packages. On the app: `AuthenticationServices`, `UserNotifications`, `BackgroundTasks` if needed, `SwiftData`, `OSLog`, `Combine`/`Observation`, `CryptoKit` if needed for signature checks. No Alamofire, no SwiftyJSON, no Realm, no third-party design systems. If backend needs one extra helper library, keep it small, actively maintained, and permissive (prefer Foundation-native/first-party where possible).

Test strategy should prioritize behavior failures, not cosmetic checks. Use protocol injection and pure state-mapper tests for the request FSM, acceptance race transitions, elapsed-time formatting, deep-link branching, and outbox replay semantics. Add parser tests for action/result decoding and a contract test around accept/release/withdraw CAS race outcomes. One UI smoke test should drive the core loop: seed two accounts in one pod, post request, race accept, observe deterministic winner/loser transition, release/reopen, withdraw, then receipt render. **SwiftUI architecture:** Root the app in a single `@Observable` `AppSession` (auth + current pod + board state) driving `AppGate`'s three-way routing (AuthGate / PodOnboarding / RelayBoard). Every outcome-affecting endpoint (accept/release/withdraw/complete) takes a client-generated idempotent action ID and returns either the updated row or an explicit conflict payload, never a silent success on retry.
