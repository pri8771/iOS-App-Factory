**Codex (Red Team · Closer) — Round 1**

I am comfortable signing this as architecture-ready now, with one hard red-team add-on that must be locked before build: every request must carry a server-issued, monotonically increasing `requestRevision` and every action mutation call must include an optional `expectedRequestRevision` so the coordinator can reject stale local intent deterministically before it touches UI state. Concrete break: Device A is offline, queues `accept` for request R. Device B accepts and completes/reject/re-opens flows before A reconnects. Without an expected-revision guard, A can replay an outbox action against a terminalized row and briefly animate into a misleading state transition before fetch correction; with revision-aware CAS we force immediate `conflict`/`reconciling` and a fresh pull, preserving the no-ambiguous-outcome rule. This is a single concrete decision, not a "nice-to-have": action payloads now include revision intent, and the reducer only accepts action responses whose `requestRevision` can be reconciled in-order per request.

The architecture stays a one-service backend + thin SwiftUI client contract: custom REST `/api/v1` over PostgreSQL, no sockets, no third-party app deps, explicit CAS endpoints only. The core invariant is server truth plus client event reducer: cache may be stale, only server-confirmed transitions are final. On device, `AppSession` drives `AppGate` routing and owns signed-in user + active pod + board handle; `RequestSyncCoordinator` remains an actor and the only mutator of in-memory request phase transitions, fed by local user actions, refreshes, push wake signals, and deep-links. **Claude (Frontend Engineer · Visionary) — Round 1**

I'm looking at this from the client-architecture-and-remarkability seat, and my read is that this fleet has already done the hard product thinking — what's missing before build starts is the concrete, typed contract that makes the "provably correct under real concurrency" promise actually buildable, not just aspirational. So I'm going to be very literal about data shapes and the CAS mechanism, and then push on one place where I think we can make the experience genuinely more remarkable than "a working demo."

**Architecture overview.** Server-authoritative REST (`/api/v1`) over PostgreSQL, thin SwiftUI client. Client root: `AppSession` (`@Observable`, MainActor) is the only thing views read from; it drives `AppGate`'s three-way route. Underneath it, `RequestSyncCoordinator` (actor) owns a private `[String: RequestCardPhase]` keyed by request ID, exposes an `AsyncStream<CoordinatorEvent>` that `AppSession` subscribes to and republishes as `@Observable` state — this is how push-triggered updates and local-action results reach the UI through one serialized pipe instead of two independent publishers racing each other. Every mutation request (post/accept/release/withdraw/complete) goes through the coordinator, which assigns a `clientActionId` (UUID), writes an `OutboxAction` to SwiftData first (so it survives a crash before the network call even starts), then attempts the network call, then applies the reducer to the result.

**Data model — concrete fields, because "audit/event log as first-class objects" from the original requirements list only means something if it's a real table:**

- `User { id, appleSub, displayName, createdAt }`
- `Pod { id, name, homeTimezone (IANA string, captured from creator's device at creation and frozen), joinCode, joinCodeStatus: active|revoked, joinCodeIssuedAt, createdBy, createdAt }`
- `PodMembership { id, podId, userId, joinedAt }` — one row per user per pod
- `Request { id, podId, requesterId, note: String? (≤140 chars, no child fields), status: open|claimed|reopened|withdrawn|expired|completed, claimedByUserId: UUID?, claimedAt, reopenedAt, lastRebroadcastAt, expiresAt (midnight in pod.homeTimezone), version: Int, sequence: BIGSERIAL, createdAt }`
- `RequestAction { id, requestId, actorId, actionType: post|accept|release|withdraw|complete, clientActionId, result: applied|conflict, requestVersionBefore, requestVersionAfter, createdAt }` — this table *is* the audit log; nothing else needs to be invented for it
- `Receipt { id, requestId, podId, requesterId, accepterId, requestedAt, acceptedAt, completedAt }` — one row, two projections at read time (internal view includes both display names as-of-completion; shareable view masks to first name + pod name, and either party's name renders as "Former member" if their account is gone, per the already-locked deletion rule)
- `DeviceToken { id, userId, apnsToken, createdAt, lastSeenAt }`

Two things worth calling out because nobody decided them explicitly yet and I don't think we can leave them implicit:

First, `sequence` on `Request` is a Postgres `BIGSERIAL`, not a derived value from `createdAt`. The design_handoff spec says "created-at ascending plus a deterministic backend tie-break" — a serial column *is* that tie-break, cleanly, with zero chance of two requests landing on the same millisecond and needing a secondary comparison. Board ordering is `ORDER BY sequence ASC`, full stop.

Second, `status: expired` fills a real gap. `detailed_discussion`'s rationale for adding `withdrawn` says "auto-closure alone doesn't cover the acute window before expiry kicks in" — which only makes sense if bounded auto-closure at the same-day boundary is already assumed to exist somewhere. I'm making it explicit: a scheduled job (or lazy check-on-read, cheaper for a prototype) transitions any `open`/`reopened` request past `expiresAt` to `expired` — same muted-slate, no-receipt treatment as `withdrawn`, but distinct copy ("This request expired — no one claimed it in time") since it's system-initiated, not requester-initiated. Without this, the earlier `withdrawn` rationale doesn't actually hold together.

**CAS mechanism, concretely, not just "compare-and-swap" as a phrase:** every action write is `UPDATE requests SET status=$new, version=version+1, ... WHERE id=$id AND version=$expectedVersion AND status = ANY($allowedFromStatuses) RETURNING *`. Zero rows returned means conflict — fetch current state fresh and return it as the 409 payload's `currentState` field so the client's "already covered by [name]" card has real data to render, not just an error code. `accept` requires `status IN (open, reopened, stillOpen-computed-from-open)`; `withdraw` requires `status IN (open, reopened)`; `release` requires `status = claimed AND claimedByUserId = actor`. This is what makes [REDACTED:high_entropy]'s "mutual exclusivity" a database guarantee instead of a client-side convention someone can get wrong.

**API contract:** `POST /auth/apple`, `POST /pods`, `POST /pods/join {joinCode}`, `POST /pods/{id}/join-code/rotate` (creator-only), `GET /pods/{id}/state` (board snapshot), `POST /pods/{id}/requests {clientActionId, note?}`, `POST /requests/{id}/actions {clientActionId, actionType}`, `GET /requests/{id}` (deep-link refetch target), `GET /requests/{id}/receipt`, `POST /devices {apnsToken}`, `DELETE /account`. Every action endpoint is idempotent via a unique constraint on `(requestId, actorId, clientActionId)` in `request_actions` — a duplicate submission returns the original result, never reprocesses.

One more gap I want flagged before build starts: the free tier is locked to exactly one pod, but nothing says what happens at the API level when a user with an existing `PodMembership` submits a valid join code for a second pod. Since entitlement checks are explicitly out of scope for this build, the only honest answer is a hard server-side cap — `POST /pods/join` returns 403 with a plain "you're already in a pod" message if the user has any existing membership — not a silent allow that quietly builds multi-pod support nobody asked us to build yet.

Now the visionary push, scoped to stay inside everything already locked: the pulse-to-latch motion is the one thing this app is judged on, so I want the reducer to be the most over-engineered-for-its-size piece of code in the app, in the good sense — a pure function `(RequestCardPhase, CoordinatorEvent) -> RequestCardPhase` with an exhaustive switch and no default case, so adding a tenth state anyone forgets to handle is a compile error, not a runtime gap. And I want `RequestSyncCoordinator` to expose its event stream as `AsyncStream`, not Combine — it composes better with the actor boundary and makes the "two producers, one serialized consumer" property trivially testable with `Task` + `await` in Swift Testing rather than needing Combine expectation gymnastics. That testability is what actually lets us prove the demo-critical claim instead of just hoping the timing works out live.

Codex, your revision-guard scenario is the single most useful thing said in round one — device A queues an accept offline, device B resolves the request entirely while A is dark, A reconnects and replays a stale intent against a row that's already terminal. That's not a hypothetical, that's Tuesday for this app given how the offline outbox is architected, and I'm fully adopting `expectedRequestRevision` as a required parameter on every action call, not just implied by the SQL `WHERE` clause the way I sloppily left it in round one. My `performAction` signature was actually broken with respect to the thing you were arguing for, and the coordinator caught that correctly — fixed below, threaded all the way from `OutboxAction` through the coordinator through the wire endpoint.

On naming, I'll concede `RelayRequest` over my plain `Request` — you're right that in a codebase that also has `URLSession` request objects, action requests, and probably a `RequestComposerSheet` view, a bare `Request` type is going to cause "which Request do you mean" friction the first time someone autocompletes in Xcode. I'll keep the `Relay` prefix consistent across the family: `RelayRequest`, `RelayAction`, `RelayReceipt`. But I want to push back on where you put the audit trail. You embedded `ActionTrailEntry` only inside `RelayReceipt`, and that quietly breaks something we already locked: `withdrawn` and — the thing I'm about to defend — `expired` requests never produce a receipt at all, by explicit design ([REDACTED:high_entropy] says withdrawn "must never generate an audit/receipt artifact, since no handoff occurred"). If the only place an action trail lives is nested inside a receipt object, then every accept attempt on a request that ends in withdraw or expiry — including a losing accept that got a genuine "already covered" conflict — has no queryable record anywhere. That's not a hypothetical gap either, it's the literal requirement from the original prompt_contract phase that audit/event log be "first-class objects," and a first-class object doesn't live exclusively as a nested array inside a different, conditionally-absent object. So I want `RelayAction` to stay a standalone, always-written table — every `POST /requests/{id}/actions` call writes one row regardless of outcome — and `RelayReceipt` becomes a read-time derived view that's only constructible once a `complete` action exists in that trail, not a container that owns the trail itself.

I also want to resolve `expired` in a way that I think actually satisfies both of us rather than just asking you to rubber-stamp a twelfth client state. Here's the trick: `expired` doesn't need to be a new case in `RequestCardPhase` at all. The locked 11-state client machine from design_handoff stays exactly as specified — I'm not touching it. What changes is that the server-side `RelayRequestStatus` enum (which is a different, lower-level enum than the client's presentation phase) has both `withdrawn` and `expired` as distinct values, and the client's existing `.withdrawn(RelayRequest)` card phase — which already carries the full request payload — just branches its copy off `request.status`: "Withdrawn — no longer needed" for a manual withdraw, "This request expired — no one claimed it in time" for a system-driven one. Same muted slate, same lack of a receipt CTA, same everything visually; only the string differs. That gives us a real, queryable distinction in the data for anyone auditing later (was this abandoned by the requester or did nobody respond in time — very different signals) without touching the interaction spec that already passed its quality gate. I think this is strictly better than either "silently drop expiry" or "add a 12th UI state," and I'd like it locked this round.

Ordering: I'll take the field name `displayOrder` since that's what design_handoff actually locked, but I want to keep the BIGSERIAL-as-sole-mechanism approach rather than your `createdAtUtc` + `(serverRevision, id)` compound tie-break — a serial column is strictly simpler to reason about and query (`ORDER BY display_order ASC`, one column, one index, done) and it can never produce a tie in the first place, so there's no tie-break logic to write, test, or get subtly wrong later. The wire field the client reads is `displayOrder: Int64`; how the database guarantees monotonic uniqueness underneath that name is an implementation detail nobody outside the backend lane needs to know.

Health endpoint — yes, take it, no notes. It's the cheapest possible way to make good on the standing requirement that we prove the backend is reachable and contract-compatible before the app lets a user do anything, and `minClientVersion` is a nice bit of future-proofing against exactly the kind of protocol drift this whole review is trying to prevent. Single-pod join cap — nothing in your message contradicts it and I think it's the only honest answer given entitlement gating is explicitly unimplemented this build, so I'm keeping the `403 already_in_pod` response locked unless you actually object to it.

One more thing I noticed rereading your action type list: you included `reBroadcast` and I'd dropped it in my first pass, which was a real miss on my part — DEC-initial_discussion-005 explicitly calls for "a re-broadcast path" on a still-open request, and that's a real user-triggered action (the requester tapping "nudge the pod again"), not just passive aging text. I'm folding that back in as a fifth-ish action type with its own CAS guard (`allowed_from = [open, reopened]`, requester-only, updates `lastRebroadcastAt`, fires a fresh push) — good catch, taking it.

Last thing, and this is the genuinely new idea I want to land this round rather than just reconciling: both of our testing strategies so far have a gap between "backend fires two raw HTTP requests at itself" and "two literal iPhones in a room." Nothing tests the actual client-side reducer and coordinator under real concurrent server responses. I want one more test tier — a client-level concurrent integration test that spins up two independent `RequestSyncCoordinator` instances in the same test process, each with its own fake user identity, both pointed at one real local test-backend instance, and fires their `accept` calls inside a `TaskGroup` so they race for real over the network stack, then asserts that exactly one coordinator's `events` stream emits `latchedConfirmed` and the other emits `latchedAlreadyCovered` with the winner's name populated correctly. That's cheap to write, runs in CI on every commit instead of needing two physical phones, and it's the only test in the whole suite that actually proves the specific thing this app lives or dies on: that the reducer, the coordinator, and the real backend all agree on who won, together, not each verified in isolation.

Codex also did the one thing this phase's rules actually require of the Red Team seat and hadn't landed yet: a genuinely new edge case — a queued offline action that comes back from the server with a real conflict (already claimed, no longer open) must not just sit there retrying forever, because that would quietly recreate the exact false-confidence failure this whole app exists to prevent. Conflict/forbidden/unauthorized outcomes are terminal for that action; only network/timeout failures get retried. Claude didn't respond to this one directly, but it doesn't clash with anything she locked, it's a straightforward consequence of the reducer/terminal-state discipline both of them have already agreed to for two rounds running, and nothing about it introduces a new type or contradicts an existing one — so I'm treating it as adopted rather than blocking on a fourth round over something nobody has any actual grounds to contest.
