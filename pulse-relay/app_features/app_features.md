**Codex (Design Lead · Skeptic) — Round 1**

Here’s the first-pass feature contract for app_features, with strict scope discipline for pulse-relay’s v1 slice.

In-scope for this phase is only the full end-to-end relay slice in one pod and two-device verification, no side-apps, no extra product lanes, and no delayed “nice-to-have” complexity. Out of scope are all flows that do not materially reduce ambiguity in the same-day pickup rescue moment.

Must has explicit intent: if a feature is not directly preventing false certainty or missed coverage in this loop, it is out.

Must features (non-negotiable):
- Secure auth bootstrap on iOS with session persistence across force-quit, so a fresh user can complete login and return with real state.
- Zero-state onboarding path that never dead-ends: create a pod or join one by invite code/link; no “no pod, no action” trap.
- Pod trust boundary enforcement: all visibility and actions are limited to pod members from join codes and membership checks.
- Realtime request posting with no child PII: same-day request card with optional short note only, and a mandatory “sending / awaiting confirmation” pre-ack state.
- Honest delivery feedback on post: show “Sent to N pod members” from real token reachability, with warning when delivery certainty is weak.
- Real APNs delivery with deep link into request card for seeded pod devices.
- Multi-open request model: multiple active requests per pod with independent IDs and server-owned ordering.
- Server-side CAS for accept and outcome transitions; no polling or client-side arbitration as stand-in.
- Deterministic race result: one confirmed winner and one explicit already-covered-by-[name] outcome sourced from CAS.
- Explicit outcome states and non-optimistic transitions on all mutating taps (post, accept, release, complete, withdraw) only after backend ack.
- Release flow for claimed requests, with re-open and re-notify target under 30-second practical target.
- Withdrawn terminal state for requester-only open/unclaimed requests only, with CAS arbitration, push re-notify, and no receipt/audit emission.
- Still-open aging state with elapsed timer and re-broadcast action, not just stale “pending.”
- Completion emits one immutable audit/receipt record with shareable privacy-filtered projection.
- Account deletion does not delete audit/receipt records; departed members render as placeholders.
- Time logic is server-owned in UTC plus pod home timezone; clients do not compute same-day cutoffs locally.
- Four-state UX on core funnels (loading/empty/error/success) and visibly distinct empty states for pod of one versus pod members-unresponsive.
- Idempotency on outcome-affecting actions via client action IDs and deterministic reconciliation after restart/crash.

Should features (important but not required to prove core reliability):
- Mutual exclusion enforcement for release vs withdraw by state and role in both API and client UI logic.
- Pull-to-refresh and push reconciliation behavior to recover drift across reconnects.
- Copy that explicitly says accepted means claimed responsibility, not guaranteed arrival.
- Lightweight onboarding help copy documenting scope limits (no moderation, no location, no child PII, no guarantees beyond responsibility claim).
- Basic haptics and motion for acknowledged transitions and terminal states.
- Theme token system in one Theme.swift file and guaranteed dark-mode semantic rendering for all core screens.
- Deterministic sort/filter for active requests by urgency then age.

Could features (deferred polish within v1 only):
- A richer onboarding tutorial card cycle on first login.
- Optional request templates for recurring household routines (without scheduling engine, just text templates).
- Per-user notification status panel (non-blocking) showing registration state and last push time.
- Mild post-success confirmation animations (subtle only, never used as “success” without server ack).

Won’t-build list for this phase:
- Any paid UI or paywall flow in the core loop.
- Multi-pod support, advanced pod analytics, response-time configuration.
- Child identity fields (name/photo/face), maps, live location, ETA, geotracking.
- Recurring/future-dated requests or calendar engine.
- In-app chat/DM, messaging thread, mentions, or push-back-and-forth coordination.
- Moderation tools: report, mute, remove, temporary bans.
- Payments or reward features.
- Persistent aggregate request history feed.
- Admin console beyond create pod + rotate/reissue code.
- Any background check, identity verification badge, trust scoring, or safety claim beyond declared trust-graph model.

The biggest risk in this direction is not feature bloat but infrastructure truthfulness: if APNs and CAS are not truly wired as the source of truth, this becomes a UI simulation and breaks the fundamental “ambiguous no longer happens” claim. That failure is worse than missing a pretty screen, so acceptance must stay tied to server-confirmed, two-device race/relability behavior.

Acceptance criteria per must feature:
- Fresh account can sign in and either create or join a pod, with a persisted signed-in state after force-quit.
- A user without pod membership always lands in an actionable onboarding state with copy and one tap path to proceed.
- Backend reject path works for non-member request access, and request lists never include non-members.
- Request posting returns loading, then terminal success/error only after backend ack, never optimistic complete.
- Posted request copy includes no child name/photo/face data and no hidden identifying fields.
- Post screen shows sent-to count tied to token registration status and a warning when delivery is uncertain.
- APNs delivers deep-linked request payload to a second real device and opens the correct request card path.
- Concurrent accept from two devices resolves to one winner and one already-covered transition every run.
- No user-facing “claimed,” “complete,” or “withdrawn” label appears before backend confirmation for that action.
- Withdraw only appears for requester on unclaimed open/still-open/reopened requests and is never available after acceptance.
- Release is available only to current accepter and correctly reopens and notifies pod.
- Still-open state includes elapsed age, and re-broadcast function performs a new server-visible alert cycle.
- Force-quit during posting/accept/release/complete/withdraw does not create duplicate records and recovers to server truth via action IDs.
- Complete creates exactly one audit/receipt artifact; withdraw creates no artifact.
- If any party deletes their account, existing records remain with placeholder identity.
- Same-day/aging fields are identical across devices and align with pod timezone + UTC source.
- Empty/loading/error/success states are implemented and testable on both post and resolve/completion funnels.
- Pod-of-one and pod-populated-but-unresponsive are visually different states with different CTA behavior.
- Two-device acceptance demo passes with side-by-side confirmed vs already-covered-by display and no manual reconciliation.

**Claude (QA & Risk · Pragmatist) — Round 1**

Coming into this as the person who has to sign off "yes this actually works" at the end, my instinct is to treat the MVP slice locked in next_steps_small as the raw material for the must-have list rather than starting from scratch — that slice already survived three rounds of stress-testing, so re-deriving priorities from zero would be wasted motion and risks quietly softening something that was fought for. But "the whole slice is must-have" isn't actually a priority order, it's a scope boundary, and those are different things. If I had to bet on where this build runs out of time, it's late, after auth and pod join and post are done and looking good, and I don't want release/withdraw/still-open-aging to get silently thinned out because nobody said out loud which of the must-haves are load-bearing for the actual two-phone demo versus which are must-have but survivable-if-rough. So I'd split the must list into two tiers internally, both still "must" for grading purposes, but ordered: tier one is auth persistence, pod create/join with the two distinct empty states, posting a request with no child PII, real APNs delivery with deep link, and the accept-race CAS resolving to exactly one confirmed and one already-covered-by-name — that's the whole demo, and if build time runs short, everything else gets cut before any of this gets rushed. Tier two is release/reopen, withdraw, still-open aging with elapsed time and re-broadcast, and complete producing the shared receipt — these are locked must-haves too and the acceptance bar explicitly includes them, but they're less catastrophic if they ship a day later or with rougher edges, because none of them alone breaks the "who's got my kid" trust promise the way a broken race or a silent notification would.

For acceptance criteria, the ones I'd insist get written precisely rather than left as vibes: the accept-race criterion has to specify that both devices reconcile purely from the server's CAS write result, never from local optimistic state, and that this is testable by literally killing network on one device mid-tap and confirming it doesn't show a false confirmed state on reconnect. The withdraw criterion needs to specify it's invisible the instant a request is accepted (state-machine invariant, not a UI convention I can fudge by just hiding a button client-side while the server still allows the call). The still-open criterion needs an actual numeric elapsed-time display, not a vague "still waiting" chip — because a fuzzy timestamp is exactly the kind of thing that looks done in a screenshot but fails a real product review. And every one of these screens needs its four states — loading, empty, error, success — actually built and reachable, because the fleet history I'm looking at shows this exact team pattern failing before: blank placeholder screens passing as "done," hardcoded font/color literals instead of using the theme file, which is a recurring visual-QA and design-lint failure mode here, not a hypothetical.

Where I want to push back before we lock anything: the subscription tier (multi-pod, receipt export, critical-alert bypass) was locked as product direction two phases ago, but next_steps_small explicitly cut all paywall UI from the MVP slice. I think this phase needs to say plainly, not by omission, that those three unlocks are should/could at best for this build — meaning the data model can leave room for an entitlement flag, but no StoreKit integration, no paywall screen, and no gated behavior is in scope for what gets built and graded now. If we don't say this explicitly, there's a real risk someone treats "subscription value is locked" from the product brief as a build requirement and burns a day on in-app purchase plumbing that produces zero improvement to the actual two-phone trust demo, which is the only thing that matters for whether this app is any good.

Should/could beyond that: a minimal profile/sign-out screen (needed for the app to feel complete and to support the deletion-preserves-audit-record behavior, but not part of the core loop), and the shareable receipt card's visual polish — it should exist and work (tap complete, get a receipt), but its design investment is explicitly subordinate to the already-covered-by-name transition, per the locked decision, so if I have to choose where visual craft time goes, the receipt card loses.

Won't-build stays exactly what's already been carved out across every prior phase, and I don't think this phase should relitigate any of it: no chat/DM, no location/GPS, no child PII fields, no payments, no recurring/scheduled requests, no scrollable history/feed, no pod-admin console beyond the one revoke/reissue capability, no daycare/activity pod types, no analytics, no moderation/reporting/removal. I'd also explicitly won't-build: any StoreKit/paywall implementation, multi-pod switching UI, and critical-alert notification entitlement — since I just argued those down to should/could, I want the record to also say they're not expected in the delivered build, so nobody's surprised when they're absent from the final review.

The failure mode I'm most worried about isn't feature creep, it's the opposite — a team that treats "post and accept" as the finish line because that's the visibly demo-able part, and quietly ships withdraw or still-open-aging as a half-wired stub because nobody wrote down that they're graded requirements with the same weight, not polish. Whatever comes out of this phase as the requirements-json contract needs numbered, independently-testable line items for every one of: auth persistence across force-quit, pod join with both empty states, request post with no PII, push delivery with deep link, the accept-race CAS test (exactly one winner, one explicit loser, sourced from server ack), release/reopen timing, withdraw's state-exclusivity with release, still-open aging display, complete producing the dual-view receipt, and the four-state requirement per screen — so that "done" has an actual checklist behind it instead of being whatever felt finished when time ran out.
