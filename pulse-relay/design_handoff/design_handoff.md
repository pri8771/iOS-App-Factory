**Claude (Frontend Engineer · Systems Thinker) — Round 1**

Let me put this together as a complete client-architecture-first pass at the design spec, since nobody's spoken yet this phase.

I want to start from the thing that will actually break if we get it wrong: how the client learns about state changes it didn't cause. The push notification payload must never be treated as data — Apple doesn't guarantee delivery order, a payload can arrive stale or duplicated, and treating it as truth would recreate exactly the false-confidence failure this whole app exists to eliminate. The correct pattern is: push arrival is a wake-up signal only, which triggers a targeted GET on that specific request, and the UI transitions only after that authoritative fetch resolves. That means every BeaconCard transition — whether caused by this device's own tap or a push-triggered refetch — goes through the same single reconciliation path into view state, which also means "awaiting-confirmation" (my own action, in flight) and "reconciling" (someone else's action, just learned about) can share the identical pulse visual but need to be distinct internal states, because if we collapse them a build agent will wire the reconcile path to skip the pulse and jump straight to the terminal card, which breaks the demo's whole point of watching both phones resolve in real time. I'd also add a client-side foreground refresh — on scenePhase becoming active, refetch the board — as a backstop for the honestly-documented case where APNs silently drops a push on a fresh pod's first incident; this isn't a websocket, it's a cheap correctness net, and it should not be confused with the still-open elapsed timer, which should tick locally off a stored server timestamp so we're not hammering the network just to advance a clock.

Two data-model consequences fall out of the multi-open-request decision that I don't think anyone's pinned down yet. First, ordering: if a pod can have two simultaneously open requests, the board needs a server-defined, stable sort (I'd propose oldest-created-first, since age is already the thing we're surfacing as the urgency signal) and the client must render server order verbatim rather than re-sorting locally — otherwise two devices with slightly different fetch timing show cards in different positions, which is a subtle but real ambiguity bug in an app whose entire premise is zero ambiguity. Second, offline compose: the brief already locked a "will send once connected" draft state, so the client needs a real local outbox — action IDs generated and queued the moment the user taps send/accept/release/withdraw offline, replayed in order on reconnect via NWPathMonitor, each queued action rendering a distinct "queued — sending when back online" chip that is visually and semantically different from "awaiting confirmation," because awaiting-confirmation implies an active round-trip is happening right now and queued does not. Skipping this distinction would mean either lying about network state or leaving users staring at a spinner that's actually just... waiting for wifi.

On architecture: root of the app is a state-driven switch, not a TabView — SessionGate resolves to AuthView (signed out), PodOnboardingView (signed in, no pod), or LiveBoardView (signed in, has pod) as the actual root, so there's no tab bar wasting chrome on an app with essentially one screen that matters. LiveBoardView presents the composer and request-detail as sheets; pod settings and profile are reachable via small toolbar affordances, not tabs. Deep links resolve through a single router that maps a push's request ID to "present RequestDetailSheet for X," with three sub-states of its own worth naming explicitly: the request is already synced locally (show immediately), the request isn't synced yet (show a brief loading state while fetching), and the request 404s because it was withdrawn/expired before the user opened the link (a distinct "this request is no longer open" state, not a generic error — this will happen constantly in practice since push and user attention are never perfectly synced).

**DESIGN SPEC - Push/sync architecture rule (non-negotiable):** push payloads are never rendered as state. On launch/foreground and after a force-quit mid-action, show a single top-level "Syncing latest pod state…" banner (not per-card) until the first fresh fetch of the session lands; stale cache still renders underneath for continuity, but no terminal card is shown with full confidence before that first sync completes.

**DESIGN SPEC - Per-screen states:**
- *AuthGate*: signed-out ready (Apple Sign-In CTA) · signing-in loading (disabled UI, "Checking sign-in…") · error with inline banner + retry · success routes by session token.
- *PodOnboarding*: podless empty ("You're not in a pod yet" + Create pod / Join with code) · create/join in-progress (disabled, honest copy, no fake success) · invalid/expired code error + retry · success routes only after server ack.
- *RelayBoard*: all-clear pod-of-one (pod name, member count, "Share the invite") · all-clear populated ("No active requests" + Post CTA) · active stack (BeaconCards in server `displayOrder`) · loading shimmer · syncing banner · error banner + retry, never blank.
- *RequestComposer*: edit (note + optional short note, no child fields) · queuedOffline · awaitingConfirmation (disabled inputs) · success only on ack · failed + retry, no optimistic post.
- *RequestDetail*: open/unclaimed with visible timer + accept CTA · awaitingConfirmation / queuedOffline / reconciling (each distinct) · latchedConfirmed / latchedAlreadyCovered (identical motion, no red/shake/alert icon on loser) · reopened · stillOpen + re-broadcast · withdrawn (requester-only, muted slate, no receipt) · completed (muted slate + receipt action) · error + retry. Deep-link entry has 3 branches: `alreadySynced` (render immediately), `syncing` (spinner), `noLongerOpen` (respectful close copy, no alarm tone/icon — this will happen routinely).
- *Receipt*: loading · loaded (internal + masked share projection, "Former member" placeholders for deleted accounts) · unavailable + reload.
- *Profile* / *PodSettings*: plain, token-driven, zero custom transitions/motion/illustration; PodSettings has code chip + revoke/reissue with its own error+retry.

**DESIGN SPEC - Motion & haptics:** open→awaiting pulse: scale 0.99→1.02 + border alpha oscillation, 0.9s ease-in-out, repeating. Resolution latch (winner or loser, identical): 0.45s spring, response 0.45, damping 0.82 — no shake, no alert icon, no red on the loser. Reduce Motion collapses both to a ~0.15s crossfade, preserving all text/icon state changes. Haptics: neutral/soft on server-confirmed landing for both winner and loser — never a warning/error haptic for "already covered." Elapsed-timer format: MM:SS under one hour, then "Xh Ym."

**DESIGN SPEC - Accessibility:** every icon-only control has an explicit VoiceOver label + hint; each card reads as one composed sentence ("Request from {member}, status {status}, elapsed {time}, {available action}"); color never carries state alone — every chip pairs icon + text; 44×44 minimum hit targets; Dynamic Type reflows to a vertical stack at AX3–AX5 rather than clipping/truncating; AA contrast against all semantic surfaces in both appearances; connection/session banner carries two distinct copies (offline-with-queued-actions vs. uncertain-delivery) rather than one vague string.

**Craft-budget priority under time pressure:** (1) open→awaiting pulse, (2) winner/loser latch, (3) completed/withdrawn terminal clarity — everything else, including the resting state and secondary screens, stays plain and correct.

**Claude Design:** not used for this build. The spec above is implemented directly in SwiftUI; the previously drafted upload prompt is kept on file only as a future static-asset fallback (e.g. App Store imagery), generated after interaction implementation is complete, never before.
